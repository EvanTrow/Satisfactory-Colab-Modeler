# Job 028: i18n wiring (55 locales)

**Phase:** 7 · Polish & deploy
**Status:** Done
**Depends on:** 027 (polish batch)

## Context

Read [`PLAN.md`](../PLAN.md) section **1. Resource Inventory** (the `resources/languages/languages.json` + `translations/*.json` row — "55 locales; `en-US.json` has ~600 keys" — "**The single most valuable file** — the complete UI string table") and **3. Feature Scope → Later phases** ("55-locale i18n (string tables are already in the repo)"). The string tables already exist in `resources/languages/`; this job's work is wiring an i18n framework to consume them, not producing translations.

## Scope

In scope:
- Choose and integrate a standard React i18n library (e.g. `i18next`/`react-i18next` — use judgement, but prefer whatever integrates most simply with Vite and the existing Tailwind/component structure).
- Ingest `resources/languages/languages.json` (locale metadata/list) and `resources/languages/translations/*.json` (the actual key→string maps) into the app's i18n runtime, either by copying into `apps/web/src/locales/` at build time (with a documented sync step, matching the pattern used for `game_data.json` in Job 003) or loading them directly — pick whichever avoids drift and document the choice.
- Replace hardcoded UI strings across everything built in Jobs 008-027 with i18n key lookups, starting with `en-US` (~600 keys already available) as the baseline — this is a large mechanical refactor; prioritize correctness and completeness over speed, and it's acceptable to do it incrementally file-by-file as long as it's tracked to completion.
- Locale switcher UI, persisting the chosen locale (localStorage is sufficient, consistent with Job 014's theme-preference approach).
- Per-locale number formatting awareness: PLAN.md §1 mentions "per-location number formatting (fraction vs decimal, digits, rounding mode)" as part of the feature surface revealed by the string table — confirm `packages/rational`'s formatter (Job 002) and the settings UI (Job 019) correctly account for locale-specific conventions where the string table specifies them (e.g. decimal separator conventions), rather than assuming en-US formatting universally.

Out of scope:
- Producing or correcting translations — the string tables are pre-existing localization content from the reference tool's data extraction; this job wires them up, it doesn't author or QA the linguistic content itself.
- RTL layout support, unless one of the 55 locales requires it and it's trivial to add — flag as a follow-up if it surfaces significant layout rework rather than blocking this job on it.

## Deliverables

- i18n framework integrated into `apps/web`.
- All hardcoded UI strings from prior jobs replaced with key lookups, backed by `en-US.json` at minimum, with the framework structured to support all 55 locales once/if their translation files are wired in the same way.
- Locale switcher with persisted preference.
- Locale-aware number formatting verified against `packages/rational`.

## Acceptance criteria

- Switching locale in the UI updates all wired strings without a page reload.
- A grep/audit of `apps/web/src` for hardcoded user-facing string literals (outside of i18n key lookups) turns up no remaining instances in the components built by Jobs 008-027 (some judgement calls acceptable for dev-only/debug text).
- `en-US` locale renders identically to the pre-i18n UI (no regressions from the refactor).
- `pnpm --filter web test/build/typecheck` pass.

## Handoff notes

**Library choice & sourcing (both open questions the job left open):** `i18next` + `react-i18next` (pinned `^26.3.6`/`^17.0.11`), the natural Vite/React choice per the job's own wording — no other i18n library was evaluated, since there was nothing existing to conflict with and this pairing is the de facto standard. `resources/languages/languages.json` (locale metadata) and `resources/languages/translations/*.json` are read **directly from `resources/`, no copy step** — the same "single source of truth, no drift risk" precedent Job 003 set for `game_data.json` (confirmed again here: Vite's dev server and `vite build` both resolve the relative import/glob outside `apps/web/src` with zero `server.fs.allow` config needed, matching Job 010's earlier confirmation for gamedata). `apps/web/src/i18n/locales.ts` does this two ways: `en-US.json` is a plain **eager** `import` (every boot needs it synchronously before any locale choice is known); the other 54 locales are loaded via `import.meta.glob(["…/translations/*.json", "!…/translations/en-US.json"])` — Vite code-splits each into its own chunk (confirmed in a real `pnpm --filter web build`: `de-*.js` 36KB, `ja-*.js` 40KB, etc., each a separate chunk, none in the main bundle), and the `!en-US.json` exclusion is only there to silence a Vite "ineffective dynamic import" build warning (en-US is already covered by the eager import) — `SUPPORTED_LOCALES`'s membership test was written to special-case `en-US` back in explicitly, so this is purely a build-noise fix, not a behavior change.

**Two namespaces — this is the load-bearing design decision for the whole job:**
- `translation` (i18next's default namespace) — the real, **unmodified** ~600-key `en-US.json` (and, lazily, each other locale's own file). Every `@scm/gamedata` display name (part/machine/recipe — e.g. `"Iron Ore"`, `"Miner Mk.2"`) is looked up **directly as a flat key in this namespace** (`i18n/gameTerm.ts`'s `useGameTerm()` hook, `t(name, {defaultValue: name})`) — a genuinely valuable discovery not anticipated by the job file's own wording: the original string table already carries a real translated entry for every part/machine/recipe name (verified live: `de.json` maps `"Iron Ore"` → `"Eisenerz"`, `"Miner"` → `"Miner"`, etc.), so switching locale live-retranslates every recipe/part/machine name on screen, not just static UI chrome. `keySeparator: false` is set globally in `i18n/i18n.ts` because 9 real keys contain a literal `.` (`"Miner Mk.1"`, `"Mk.1 Belt"`, …) that i18next's default `.`-as-nesting-separator would otherwise mis-parse.
- `app` — new keys for UI genuinely novel to this reimplementation, in `apps/web/src/i18n/app-en-US.json` (English only — translating this namespace is explicitly out of this job's scope; every other locale reaches it via i18next's `fallbackLng: "en-US"`, so nothing ever renders a raw missing-key placeholder).

**Reuse-vs-new-key judgement calls actually made** (the single most important thing for a later job/translator to understand about the string table's shape after this job):
- **Clean 1:1 reuse** (original key's value used completely as-is): `EVERYTHING`/`CURRENT_OUTPOST`/`SELECTED` (summary scope tabs — PLAN.md's own "scoped operations" list names this exact trio), `PART`/`MADE`/`USED`/`UNMADE`/`UNUSED` (summary table headers), `POWER_MADE`/`POWER_USED`/`SINK_POINTS`/`COST_TO_BUILD`/`SUMMARY`/`SUMMARY_PANEL` (summary panel), `SETTINGS`/`LANGUAGE`/`MACHINES`/`DIGITS`/`STYLE`/`UNDO`/`REDO`/`DIRECT`/`CURVES`/`HORIZONTAL`/`VERTICAL`/`ALTERNATE_RECIPE` (settings menu, toolbar, Recipe Chooser, connection-style dropdown — `apps/web/src/canvas/edges/connectionStyle.ts`'s `CONNECTION_STYLE_OPTIONS` now carries `labelKey`s into this same table instead of literal English), `INPUT`/`OUTPUT` (port tooltips, composed with new suffix text), every `@scm/gamedata` display name via `gameTerm()`.
- **Reused with knowingly different original wording** ("close enough," per the job's own explicit sanction): `AVERAGE_NET_POWER` ("Average Net Power") reused for the summary panel's "Power net" row; `NUMBER_SETTINGS` ("Number Settings") reused for the number-format section heading (previously "Number format"); `CLOCKSPEED`/`CLOCKSPEED_HELP` reused for the node card's "Clock"/± button tooltips (`CLOCKSPEED_HELP`'s one full paragraph now covers BOTH ± buttons, replacing two separate hand-written one-liners — the original documents both buttons' behavior in one help text, so this is a consolidation, not a loss); `AUTO_ROUND`/`AUTO_ROUND_HELP` reused verbatim for the auto-round toggle (the original help text is strictly more complete than this app's prior one-liner — it even documents the black-background treatment `RecipeNode.tsx`'s `autoRoundFieldClass` already implements); `NEAREST`/`DOWN` reused for the `round`/`truncate` number-format rounding modes (`NUMBER_SETTINGS_HELP`'s own prose literally defines "Nearest" as standard half-away-from-zero rounding and "Down" as truncation — exact matches to this schema's `"round"`/`"truncate"` semantics); `LIMIT` reused for the node card's limit label (the "(ppm)"/"(machines)" unit suffix stays a literal, untranslated abbreviation — a deliberate call that technical unit codes aren't "English text" the same way prose is, matching common practice in other technical tools).
- **Deliberately NOT reused, kept as new `app` keys, with the specific reasoning**: `floor`/`ceil` rounding modes — the original's own vocabulary is a 3-way Nearest/Up/Down choice where "Up" is magnitude-based (away from zero regardless of sign), a genuinely different concept from either of this schema's two directional (toward ±∞) modes, so reusing "Up" for just one would misrepresent the other (see `SettingsMenu.tsx`'s `ROUNDING_MODES` comment). `APP_NAME` ("Satisfactory Modeler") was **not** reused for this app's own title — it's the original *desktop* tool's own name, and using it here would render the wrong app name entirely; `app.title` = "Satisfactory Colab Modeler" instead. `UNMADE_TOOLTIP`/`UNUSED_TOOLTIP` ("Red labeled inputs"/"Green labeled outputs") were **not** reused for the summary balance-table tooltips — this app's own unmade/unused highlighting uses danger/mismatch colors (red/orange), not the original's red/green scheme, so the wording would misdescribe this app's actual visual treatment; new `summary.unmadeTooltip`/`summary.unusedTooltip` describe the underlying concept without asserting a specific color.
- **Genuinely novel, no reasonable original-app analogue** (new `app`-namespace keys, documented namespaces below): multiplayer presence avatar tooltips, `ConnectionStatusIndicator`'s connected/reconnecting/offline transport states (distinct from the original's single-user save model), the Splurger/priority-routing UI strings, blueprint-specific strings (not yet localized — see "not covered" below), auto-round's own on-screen state text beyond the reused `AUTO_ROUND`/`AUTO_ROUND_HELP`, the solve-in-progress/STOP status text, the pop-out summary window's own chrome, and every project-list (create/rename/duplicate/delete/error) string — the original single-user desktop tool has no multi-project list at all, so none of `ProjectsPage.tsx`'s copy has a table analogue.
- **New-key namespace layout** (all in `apps/web/src/i18n/app-en-US.json`, flat keys with `.`-separated logical prefixes — remember `keySeparator: false` means these dots are cosmetic grouping only, not real nesting): `app.*` (top chrome/login), `projects.*` (project list), `theme.*`, `locale.*`, `canvas.*` (toolbar, Recipe Chooser), `settings.*` (settings menu labels without a table analogue), `node.*` (RecipeNode card's own novel strings), `summary.*` (summary panel's novel strings), `status.*` (save/connection/solve indicators).

**Locale switcher mechanism/persistence** (`apps/web/src/i18n/`): `useLocale()` wraps `react-i18next`'s `useTranslation()`; `<LocaleSwitcher>` is a plain native `<select>` (55 options, `localeDisplayName()` reading `languages.json`'s native names) mounted in three places — `App.tsx`'s header, `CanvasView.tsx`'s toolbar (both next to `<ThemeToggle>`, matching Job 014's "app-level chrome, mounted wherever the relevant header is" precedent), and inside `SettingsMenu.tsx`'s popover for discoverability. Persistence is `localStorage["scm-locale"]`, explicitly modeled on `theme/useTheme.ts`'s `"scm-theme"` mechanism (Job 014): no stored preference → best-effort match against `navigator.languages` (exact match first, then bare-language fallback, e.g. `de-CH` → `de`) → `en-US` as the final fallback. `setLocale()` lazy-loads the target locale's translation table on first use via `loadLocaleTranslation()`, calls `i18next.addResourceBundle` + `changeLanguage`, and only then persists — verified live in a real browser (not just Vitest, since `apps/web` still has no DOM-rendering test infra, per the job file's own noted gap) that switching locale re-translates every wired string **instantly, with no page reload**, including live re-translation of recipe/part/machine names inside an already-open Recipe Chooser and an already-created node card, and that switching back to `en-US` restores byte-identical text (see the two "known, deliberate copy changes" below).

**`en-US` renders identically to pre-i18n, with two known, deliberate exceptions** (both are direct, intended consequences of the "reused with different original wording" judgement calls above, not regressions): the node card's clock-speed label reads "Clock Speed" instead of the pre-i18n literal "Clock" (reusing `CLOCKSPEED`), and the auto-round toggle reads "Auto Round" instead of "Auto-round" (reusing `AUTO_ROUND`). Every other string was confirmed unchanged for `en-US`, both by direct source diff and by live browser comparison before/after.

**Number formatting — the "per-location" phrasing is a false lead, confirmed by direct inspection:** PLAN.md §1's "per-location number formatting (fraction vs decimal, digits, rounding mode)" and the original `NUMBER_SETTINGS_HELP` string it's paraphrasing are both about **UI-field location** ("the first column is the location of the number" — i.e., which field: limit, clock, sink, etc. — a per-field-type format table), not geographic/language locale. This job checked all 55 `translations/*.json` files directly (`grep` for `DECIMAL`/`FRACTION` and every numeric-looking key) and confirmed **none of them carry any decimal-separator, digit-grouping, or other locale-numeric-convention data** — they are purely translated UI label strings (e.g. `de.json`'s `"DECIMAL": "Dezimal"` is just the German word for "decimal," not a formatting rule). So there is nothing in the string table to wire into `@scm/rational`'s `formatRational`/`toDecimalString`, and this job did not change either — `toDecimalString` still always renders `.` as the decimal separator regardless of the active UI locale. Separately, `packages/ydoc`'s `Settings.numberFormats` remains the single **global document-wide** setting Job 019 built (not per-field-location either) — this job did not touch that gap (already flagged by Job 027's Handoff notes as a Job 010 ± -button-adjacent concern, unrelated to i18n). **Flagged for Job 029 or later**, should locale-aware digit grouping/separator ever become a real requirement: it would need to be built from `Intl.NumberFormat(locale)` driven off the new `useLocale()` hook, entirely independent of the string table (which genuinely has nothing to contribute here) — not a blocker for anything in this job's own scope.
