## Scope

In scope:
- The integrity reducer, as a function in `packages/ydoc` (extending Job 007's package — this is the payoff of the `origin: 'integrity'` hook reserved there): run after every transaction, on **both client and server**, inside a transaction tagged `origin: 'integrity'`:
  - Delete edges whose `fromNode` or `toNode` no longer exists.
  - **Reparent** orphaned nodes to the root container rather than deleting them (Job 013 already implemented this for single-user outpost deletion — generalize/reuse that logic here for the concurrent case, e.g. container deleted by user A while user B has a node inside it).
  - Clamp `shards` to the current machine's `MaxProductionShards`; drop ports the current recipe doesn't have (handles: user A changes a node's recipe while user B has an edge wired to a port that no longer exists on the new recipe).
  - Deduplicate edges (a no-op given Job 007's deterministic `edgeId`, but keep it as an explicit backstop per PLAN.md's own framing).
- Wire the reducer into `apps/web`'s local transaction pipeline (client-side pass) and into `apps/realtime`'s `onStoreDocument`/document lifecycle (server-side pass, from Job 020) — "running it on the server too means a malicious or buggy client can't persist a corrupt document."
- **CRDT convergence fuzz test** per PLAN.md §9: generate random concurrent operation sequences across N in-memory `Y.Doc`s, apply in randomized orders, assert (a) all docs are byte-identical (`Y.encodeStateAsUpdate` comparison) and (b) every integrity invariant holds (no dangling edges, no orphaned nodes, shards within range).
- Sharing UI (the piece deliberately deferred from Job 006): invite creation (`project_invites` — token, role, expiry, max-uses), a share-by-link flow, and a role-management view (list `project_members`, change role, remove member) in `apps/web`, wired to `apps/api` routes.
- Connection-status UI: a visible indicator for connected / reconnecting / offline state on the live WebSocket connection from Job 020.

Out of scope:
- Anything already covered by Jobs 020/021 (transport, presence).

### The four repair rules, and how they're wired

1. **Dangling edges** (`deleteDanglingEdges`): any edge whose `fromNode`/`toNode` no longer exists in `nodes` is removed outright.
2. **Reparent orphaned things to root, never delete** (`reparentOrphanedContainers`/`reparentOrphanedNodes`/`reparentOrphanedEdgeContainers`): generalizes `apps/web/src/canvas/outposts/reparent.ts`'s `deleteOutpost` pattern (Job 013) — which only fires from one user's own explicit "delete this outpost" click — into a rule that fires for *any* dangling `containerId`/`parentId`, from any cause (a concurrent delete, a corrupt document, anything). Covers nodes, edges (their `containerId` only — the edge itself is kept, via the existing `reparentEdge` mutation helper), and non-root containers (their `parentId`). Root is found via `kind === "root" && parentId === null`; if no root exists at all (a malformed/empty doc), these three sub-rules no-op rather than guessing a destination — everything else still runs.
3. **Clamp shards / drop invalid ports** (`clampShardsAndDropInvalidPorts`): resolves each node's `machine` against `@scm/gamedata`'s `machinesByName` for `MaxProductionShards` (0 if unresolvable), and its `recipe` against `recipesByName` for the valid port-id set (`${"in"|"out"}:${part}`, the exact convention `RecipeNode.tsx`'s `PartRow` established in Job 011 — duplicated as a small private `recipePortId` helper in `integrity.ts` rather than imported, since `packages/ydoc` must never depend on `apps/web`). A node with an unresolvable `recipe`/`machine` (e.g. a stale reference from a future `game_data.json` version bump) is left alone by this rule specifically — there's no valid port set to compare against, and this rule shouldn't also decide what to do about that separate failure mode.
4. **Dedupe edges** (`dedupeEdges`): a genuine no-op given Job 007's deterministic `edgeId` under every path this app's own code takes (`addEdge` always computes the same id for the same tuple) — kept as a literal backstop that detects two *different* top-level `edges` map keys describing the same `(fromNode, fromPort, toNode, toPort)` tuple (only reachable via non-conforming/corrupt writes) and keeps the lexicographically-smaller id, deterministically, so every replica running this rule independently converges on the same survivor.

Both client and server call the exact same `runIntegrityReducer`/`repairDocument` from `@scm/ydoc` — no reimplementation on either side, per PLAN.md §7's "packages/ydoc is the only place that knows the CRDT shape."

**A cross-package build gap this job found and fixed, not scope creep**: `apps/realtime` (`NodeNext` module resolution) importing `@scm/ydoc` for the first time surfaced the same class of problem Job 020's own Handoff notes flagged for `@scm/doc-storage` ("a plain `node dist/*.js` can't execute a JIT `packages/*`-style dependency once it has internal relative imports") — except this time transitively, since `packages/ydoc/src/integrity.ts` needs `@scm/gamedata` (for `MaxProductionShards`/recipe ports), which needs `@scm/rational`. Deliberately did **not** flip these three packages to `doc-storage`'s "ship a real `dist/`, `main`/`types` point there" pattern — all three still have `apps/web` as a real Bundler/JIT-from-`src/` consumer (unlike `doc-storage`, which had none), and converting them would mean every future `apps/web` dev session needs an explicit `pnpm --filter <pkg> build` (or a `turbo`-driven `dev`) before a source edit is visible, a real workflow cost across three foundational Phase-0 packages that this job's actual scope doesn't need to pay. **One genuine, still-open gap left for whoever next touches deploy/production packaging (Phase 7)**: `apps/realtime`'s own `pnpm --filter realtime build` now typechecks/emits cleanly, but a plain `node dist/index.js` in production would still fail at the moment it tries to load `@scm/ydoc` (whose `package.json` `main` still points at `./src/index.ts`, a file plain Node can't execute) — this was already true before this job for any hypothetical `apps/realtime` dependency on a JIT `packages/*` package with internal relative imports; this job just makes it a real, reachable path for the first time (previously only `@scm/doc-storage` was on that path, and it was already fixed). ### CRDT convergence fuzz test — approach and coverage

`packages/ydoc/src/fuzz.test.ts`: 4 independent in-memory `Y.Doc`s (`gc: false` — see below) start from one identical seed (a doc with just a root container). Each of 5 "fuzz rounds" has every replica perform 0-3 random local mutations (a weighted mix of add/remove node, add edge — 70% of the time wiring a genuinely valid port pair, 30% deliberately maybe-invalid — add/remove container, move node, change a node's recipe, set shards possibly out of range) using a real recipe pool (`Iron Ingot`/Smelter, `Iron Rod`/Constructor, `Iron Plate`/Constructor, `Plastic Smart Plating`/Manufacturer — the last one specifically for shard-clamp coverage, `MaxProductionShards: 4`), then runs `runIntegrityReducer` locally, then every replica's diff-since-last-broadcast is applied to every other replica in a **freshly shuffled per-target order** (the "apply in randomized orders" requirement) via `Y.applyUpdate`. After the fuzz rounds, a bounded settle phase (repair + broadcast, no new ops) runs until a full round repairs nothing anywhere — this is a genuine fixed point, not just "stopped complaining": since every replica ends up receiving the literal union of every op+repair item that ever existed (full-mesh single-hop gossip each round), once merged content is identical and independently-run repair finds nothing new on every replica, no further divergence is possible. Then asserts (a) `Y.encodeStateAsUpdate()` bytes are pairwise identical across all replicas, and (b) every PLAN.md §5 invariant holds directly against the converged state (no dangling edges/containerId refs, shards within range, valid ports, no duplicate edges) — checked independently of `validate.ts`, which doesn't know about shards/ports/dedup. Runs 300 sequences (`hundreds`, per the acceptance criteria), plus one dedicated hand-aimed delete-vs-connect test. Total suite time: well under a second.

**One non-obvious, worth-knowing-about fix**: the first version of this test failed intermittently with "replica N's encoded state differs from replica 0's" even though every invariant check passed and every repair was confirmed a no-op. Root cause: Yjs's default garbage collection (`gc: true`) discards deleted items' content once it decides they're no longer reachable, and *when* that decision fires can depend on merge history/timing — two replicas with logically-identical content but different merge histories can produce different `Y.encodeStateAsUpdate()` bytes for reasons that have nothing to do with application-level correctness. Fixed by constructing every fuzz replica (and, later, `apps/realtime/src/integrity.test.ts`'s two live provider connections) with `new Y.Doc({ gc: false })` — keeps full tombstone history, making the encoded bytes a pure function of "which operations did this replica's causal history receive." Worth remembering if any future job adds another byte-identical-convergence assertion anywhere in this codebase.

### Invite token format and redemption flow

Same pattern `apps/api/src/auth/session.ts` established for `sessions.token_hash`: `crypto.randomBytes(32).toString("base64url")` for the raw token (returned to the caller exactly once, at creation — `createProjectInvite`'s response, embedded in the shareable link as `${origin}/i/${token}`), `sha256(token)` as a `Buffer` for `project_invites.token_hash` (`bytea`, `unique not null` — collision handled by catch-and-retry, same as `createSession`). Nothing else ever sees the raw token; `listProjectInvites`/the list route never include it.

Redemption (`redeemInvite` in `invites.ts`) is one Kysely transaction: an atomic `UPDATE project_invites SET uses = uses + 1 WHERE token_hash = ? AND (expires_at IS NULL OR expires_at > now()) AND (max_uses IS NULL OR uses < max_uses) RETURNING *` — Postgres's own row-level locking is what makes this safe under real concurrent redemption (verified with an actual `Promise.all` of two simultaneous redeem requests against a `maxUses: 1` invite in `inviteRoutes.test.ts`: exactly one gets `200`, the other `410 invite_exhausted`, exactly one `project_members` row is created). If the update matches zero rows, a follow-up `SELECT` inside the same transaction distinguishes "not found" from "expired" from "exhausted" for a precise error. On a successful increment, a `project_members` row is inserted **only if the user isn't already a member** — an existing member's role is never downgraded by redeeming a lesser invite link (tested explicitly); `alreadyMember: true` on the response lets the UI/caller know.

`GET /api/invites/:token` (no auth) is the public preview the redeem page shows before/without login — `{valid, projectId, projectTitle, role}` or `{valid: false, reason}`. `POST /api/invites/:token/redeem` requires login (any authenticated user, not project-scoped by role — possessing the token is what authorizes it) and, on success, calls the existing `notifyRealtimeMembershipChanged` webhook (Job 020) for symmetry with the role-change/removal call sites, though nothing currently needs to react to a brand-new member the way a downgrade/removal needs a force-disconnect.

**Client-side share-by-link flow, given this app has no router** (`App.tsx`'s own long-standing `View` comment: plain React state + manual `pathname`/`pushState` handling, not React Router): a `/i/:token` link is detected on `App` mount via `pathname` regex, the token is stashed in `sessionStorage` and the URL is immediately replaced with `/` (`extractInviteTokenFromPath` + `PENDING_INVITE_STORAGE_KEY` in `App.tsx`). This exists specifically because `authRoutes.ts`'s `/auth/discord/login` → `/auth/discord/callback` round trip has a **fixed** `postLoginRedirect` (`"/"`, no redirect-target plumbing) — an anonymous visitor clicking a share link has to leave for Discord and always lands back on `/`, so the token has to survive that hop client-side. `App` renders `InviteRedeemPage` (preview + accept/log-in prompt) whenever a pending token exists, ahead of both the login-prompt and the project-list branches; a successful redemption clears the stored token and re-fetches the project list to jump straight into the newly-joined project's canvas.

### Connection-status UI — the decision the job left open

Kept **both** indicators, as two deliberately distinct signals, rather than folding one into the other: `SaveStatusIndicator` (`saved`/`saving`/`offline`, unchanged since Job 016/020) answers "are my edits durably synced"; the new `ConnectionStatusIndicator` (`connected`/`reconnecting`/`offline`) answers a narrower, purely transport-level question — "is the live WebSocket itself up right now." `computeConnectionStatus(wsStatus, navigator.onLine)`: `!navigator.onLine` → `"offline"`; `wsStatus === "connected"` → `"connected"`; anything else → `"reconnecting"` (covers both "first-ever connect attempt" and "lost, currently retrying" — `HocuspocusProvider` retries indefinitely on its own, so there's no distinct "gave up" state to surface, and there's no meaningful UI difference between the two from the user's point of view). Verified live in a real browser: killing and restarting the `apps/realtime` process while a project was open showed `ConnectionStatusIndicator` flip to "Reconnecting…" (and `SaveStatusIndicator` to "Offline — reconnecting") within ~2s, then both recovered to "Live"/"Saved" within ~3s of the server coming back — the provider's own reconnect-with-fresh-ticket logic (Job 020) needed no changes.
