### Part 1 — Auto-round

**Files:** `apps/web/src/canvas/nodes/autoRound.ts` (+`.test.ts`, pure decision math), `apps/web/src/canvas/nodes/useAutoRound.ts` (the wiring hook), `apps/web/src/canvas/nodes/recipeNodeMath.ts` (refactored to export a shared `deriveClockForTargetCount`/`floorToBigInt`/`isIntegerRational` that both the manual ± buttons and auto-round now call — `snapClockToWholeMachineCount`'s own behavior/tests are unchanged, just factored), `apps/web/src/canvas/nodes/RecipeNode.tsx` (toggle checkbox + black-field-background styling + the three manual-edit call sites that now also clear `autoRound`), `apps/web/src/canvas/CanvasView.tsx` (mounts `useAutoRound(sfmDoc, solver.nodeResultById, solver.staleness)` once, right next to the single `useSolver` call).

**The sentinel convention** (Job 010's own flag, "if Job 027 needs a different sentinel scheme, this is the one place it lives"): **no change was needed.** `NodeRecord.autoRound: boolean` (Job 007's schema) already exists and was never touched by anything; `limit`/`clock`'s existing `null` = "never explicitly set" convention was already exactly what "manually touching switches it off" needs — see the write-source mechanism below.

**★ The "manual touch disables it" mechanism — call-site separation, not transaction-origin inspection.** `RecipeNode.tsx`'s three real user-edit paths (`commitLimit`, `commitClock`, and the ± buttons' `handleClockStep`) each set `autoRound: false` in the _same_ `updateNode` call as the value write (unconditional, a harmless no-op when already `false`). `useAutoRound.ts`'s own write is the _only_ code path in the app that writes `clock` _without_ also writing `autoRound: false`, and it lives in a completely different file none of those three functions call into — so there is no possible ambiguity between "the user touched this" and "auto-round corrected this" without ever needing to inspect a Yjs transaction's `origin`. `AUTO_ROUND_ORIGIN = "auto-round"` is still attached to `useAutoRound`'s own writes, but as a deliberate belt-and-suspenders addition, not the load-bearing mechanism — see the next paragraph for what it actually buys.

**Why tagging the origin anyway was worth doing, for free:** `packages/ydoc/src/undo.ts`'s `createUndoManager` defaults `trackedOrigins` to `new Set([null])` — _any_ non-null origin is already excluded from the undo stack with **zero `@scm/ydoc` changes needed**, the same way `INTEGRITY_ORIGIN` is excluded (Job 022) except that one needed an explicit forced-delete because tests could otherwise reintroduce it; auto-round's tag needed nothing extra since it was never in the default set to begin with. This means pressing Undo after auto-round nudges a clock undoes the user's own last real edit, not a fight against a correction that would just reapply itself anyway.

**★★★ The convergence/stability argument, in full — read this before touching either `autoRound.ts` or `useAutoRound.ts` again ★★★**

The mathematical claim (see `autoRound.ts`'s own header for the derivation): a recipe node's own clock speed changes how many machines are needed for a given target rate, but can **never** change what that target rate itself is — `rate_p = targetRate_primary × ratePerMachineAtFullClock(p) / referenceRate_primary`, with the `clock/100` term cancelling out completely. This holds identically whether `targetRate_primary` comes from a pinned `limit` or from Basic/Full-mode graph propagation, because `nodeProfile.ts`'s per-node formula is shared, unmodified, across all three real solver modes (confirmed by reading `manual.ts`/`basic.ts`/`full.ts` — all three call the identical `pinnedMachineCount`/`machineCountForTargetRate`). Consequence: writing a new clock can never change any node's own or any neighbor's propagated rate on the next solve, so the fixed point holds — re-evaluating against the settled post-write state either finds an already-whole count (done) or, in the clamped-at-a-bound case, re-derives the _exact same_ clamped clock (caught by `useAutoRound.ts`'s `equals()` value-equality guard, so no further write ever fires). `autoRound.test.ts` proves this directly, not just narratively: `computeAutoRoundClock(result.clockPercent, result.machineCount)` returns `null` immediately after a normal correction, and re-running the clamped case against its own output reproduces the identical clamped clock.

**★ A real, pre-existing semantic gap this analysis surfaced (not introduced by this job) — read before assuming auto-round "just works" everywhere:**

`packages/solver/src/nodeProfile.ts`'s `pinnedMachineCount` returns `{ count: limitValue }` **literally, with no clock term at all**, for a pinned `"machines"`-mode node (`node.limitMode === "machines" && node.limit !== null`) — this is the _default_ limit mode for every machine except Miner/AWESOME Sink (`defaultLimitMode`, Job 010), so it's the common case, not an edge case. This is genuinely different from `recipeNodeMath.ts`'s own `computeMachineCount` (the Job 010-era, pre-solver stopgap math the manual ± buttons' `handleClockStep` _still_ uses), which treats "machines" mode as clock-dependent (`machineCount = limit × 100/clock`). The solver's convention is the real, tested, intentional one ("Limit (machines)" means "this many machines, full stop; clock only scales each machine's own throughput") — `manual.ts`/`basic.ts`/`full.ts` all call the identical `pinnedMachineCount` — but it means **clock is structurally unable to change the solved machine count for a pinned machines-mode node**, so "snap the clock to make it whole" is a non-sequitur there: if such a node's `limit` itself is non-integer (a user can type `"5/2"`), no clock value can ever fix that, and repeatedly trying (as auto-round would, absent a guard) drags the clock down to `MIN_CLOCK_PERCENT` for zero benefit — **confirmed empirically live** before the guard was added (see Verification below) — then stabilizes there (not an infinite loop, since the clamped value itself becomes a fixed point once reached, but a useless, confusing one). **The fix:** `useAutoRound.ts` explicitly skips any node where `limitMode === "machines" && limit !== null` — auto-round is correctly a no-op there, full stop, rather than drifting the clock for no reason. It works correctly (verified live) for: any `"ppm"`-mode limit (Miner/AWESOME Sink, pinned or not), and any **unpinned** node in Basic/Full mode (`limit === null`, count from graph propagation) — both go through the clock-dependent `machineCountForTargetRate`. **Flagged for Job 028+:** the pre-existing ± buttons (`RecipeNode.tsx`'s `handleClockStep`, unchanged since Job 010) share the _same_ blind spot — for a pinned machines-mode node, clicking ± changes the OLD stopgap math's local count but has **zero effect on the real solved count** once a solve exists, which is a real, user-visible "the buttons don't do what they imply" gap that predates this job and wasn't fixed here (out of this job's stated scope, and touching `handleClockStep`'s math carries its own regression risk against Job 010's existing, still-passing tests) — a natural fix would be disabling/hiding the ± buttons (and possibly the whole auto-round toggle) for a pinned machines-mode node, or reworking them to operate on `limit` instead of `clock` for that specific case.

**Nearest vs. directional rounding:** `nearestWholeMachineCount` (ties round up) is a deliberate, new function — _not_ a call into `snapClockToWholeMachineCount` with a hardcoded direction — because auto-round has no click to read a "−"/"+" preference from; both functions now share `deriveClockForTargetCount` (the actual clock-solving core) so there's no duplicated math, just a different `targetCount` derivation feeding the same shared solver.

**Black-background signal:** literal `bg-black`/`text-white` (`autoRoundFieldClass` in `RecipeNode.tsx`), applied to _both_ the limit and clock `<input>`s (PLAN.md's plural "field*s*") when `node.autoRound` is true — deliberately not a themed `--surface-*` token, same "fixed regardless of theme" treatment `index.css`'s `--node-header` already uses. **Caveat found during verification:** in this app's _dark_ theme, the normal input background (`--surface-sunken`, `rgb(10,10,10)`) is already so close to true black (`rgb(0,0,0)`) that the signal is hard to distinguish by eye in a screenshot, even though it's a real, distinct, computed-style-confirmed difference (verified via `getComputedStyle` directly, not just visually). In light theme the contrast is obviously strong. Flagged as a polish item, not fixed here — PLAN.md's literal wording ("black field backgrounds") was followed exactly rather than reinterpreted as "a theme-appropriate strong-contrast color," so this is a faithful-but-imperfect implementation of the letter of the spec.

### Part 2 — Connection styles

**Files:** `apps/web/src/canvas/edges/connectionStyle.ts` (+`.test.ts`, 19 tests — pure path-command generation, no DOM), `apps/web/src/canvas/edges/ConnectionEdge.tsx` (now calls `buildStyledPathD(points, resolveConnectionStyle(record.style, settings.connectionStyle))` instead of the old always-straight `toPathD`), `apps/web/src/canvas/SettingsMenu.tsx` (new "Connections → Style" dropdown).

**Name mapping (documented in `connectionStyle.ts`'s own header, the single source of truth — `SettingsMenu.tsx` imports `CONNECTION_STYLE_OPTIONS` from it rather than hardcoding labels):**

| PLAN.md label | Schema value | Shape                                                                                                                                                       |
| ------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Direct        | `straight`   | Job 011's original plain polyline through every waypoint — unchanged.                                                                                       |
| Curves        | `bezier`     | Catmull-Rom-derived cubic Bezier, passes exactly _through_ every waypoint (not merely near it — critical for "remains compatible with existing waypoints"). |
| Horizontal    | `step`       | Orthogonal routing, sharp right-angle corners, first/last leg out of each point is horizontal.                                                              |
| Vertical      | `smoothstep` | Same orthogonal shape, rounded corners (small quadratic-Bezier cut), first/last leg vertical.                                                               |

This is a **deliberate reinterpretation** of `@xyflow/react`'s own `step`/`smoothstep` naming (which differ only in corner rounding, not axis) — chosen so the schema's four enum values map to four _visually and semantically distinct_ options instead of two near-duplicate pairs. If a future job wants literal xyflow-identical step/smoothstep behavior, `connectionStyle.ts` is the one file to change; nothing downstream depends on the specific shape.

**Precedence:** a valid per-edge `EdgeRecord.style` override always wins over the document-wide `Settings.connectionStyle` default (`resolveConnectionStyle`, tested for null/undefined/unrecognized-string fallback). **No UI was built to actually _set_ a per-edge override** — `SettingsMenu.tsx` only controls the document-wide default. This is a deliberate scope call (PLAN.md's own wording only asks for the document-wide selector), not an oversight; a future job wanting per-edge overrides just needs a UI (e.g. a context-menu entry) calling `updateEdge(sfmDoc, edgeId, { style })`, which `@scm/ydoc` already supports with zero further changes.

**The one non-obvious invariant this job's tests lean on:** for every style, every ORIGINAL point (source, each waypoint, target) appears as some path command's exact anchor, in order — never approximated, never skipped — proven directly in `connectionStyle.test.ts`'s "every style routes through every original point, in order" describe block. This is what "correctly routes through existing waypoints" concretely means and is what makes it checkable without a DOM.

**Verification:** all 19 unit tests pass; live in the browser, cycled through all four styles via the real Settings dropdown against a real 3-edge graph (a Priority Splitter's Top/Bottom connections) and read the live `<path d="...">` attributes directly off the DOM for each: `straight` → pure `M/L`; `bezier` → `M` + one `C` per segment; `step` → `M/L` only with a sharp vertical-midline bend; `smoothstep` → `M/L/Q` with a horizontal-midline bend and rounded corners. ### Part 4 — Pop-out summary window

**Files:** `apps/web/src/panels/summary/usePopoutWindow.ts` (new — the `window.open` + poll-for-close mechanism), `apps/web/src/panels/SummaryPanel.tsx` (extracted a `SummaryBody` sub-component shared by the inline popover and the portaled content; added `handlePopOut`/`handleSummaryButtonClick`/a theme-sync effect; `theme` is now a required prop, threaded from `CanvasView.tsx`).

**★ Deliberate refinement over PLAN.md's own suggested approach:** PLAN.md says "`window.open` with a mounted React root is the simplest approach." This job uses `window.open` + **`ReactDOM.createPortal`** into that window's own DOM node instead of a second React root. A portal keeps the popped-out content inside the _exact same_ React tree as `SummaryPanel` — so `SolverResultContext`/`useSettings()` are automatically, live, available with **zero context-bridging machinery**, because `createPortal` only cares that its target is a valid DOM node, not which `window` global owns that node's document. A second root would have needed some mechanism to forward context/props across the window boundary (a subscription, a manual re-render trigger, etc.) that the portal approach makes entirely unnecessary. `usePopoutWindow.ts`'s own header explains this in full.

**Mechanism:** `window.open("", name, features)` → copy every `<link rel="stylesheet">`/`<style>` from the main document into the new window's `<head>` (this is what makes Tailwind's build output — and therefore every `--surface-*`/`--text-*` token — resolve identically there) → create a mount `<div>` → hand its ref back as `containerEl` → `SummaryPanel` portals a `SummaryBody` + its own small header (staleness indicator + a "← Return" close button) into it. `SummaryPanel`'s own theme-sync `useEffect` re-applies the `dark`/`light` class to the popout's `<html>` (`containerEl.ownerDocument.documentElement`) whenever the main window's theme changes — the stylesheet copy happens once at open time, but the _class_ driving those tokens is separate document state that has to track live.

**Closing cleanly, both directions:** (a) the popout window closed by the user (native close button) — detected by polling `.closed` every 500ms (the standard, documented workaround; there's no reliable opener-side `onclose` event) and tearing down `containerEl`/the poll interval; (b) the owning component unmounting (e.g. the whole canvas view torn down) — a `useEffect` cleanup calls `windowRef.current?.close()` unconditionally, so the popout window never outlives the React tree it depends on. Both paths reset `containerEl` to `null`, which un-portals the content (React unmounts it) and the main window's own "Summary" button reverts from "Summary (popped out)" to plain "Summary."

**★ A real sandbox limitation hit during verification, and how it was worked around:** this session's Browser MCP tool blocks `window.open()` entirely — confirmed directly (`window.open("", "test", "...")` returns `null`/`false` even from a genuine click handler, not just from a script running with no user gesture). `usePopoutWindow.ts`'s own `if (!win) return;` guard means this degrades gracefully (no crash, no console error) — but it also means **the actual separate-OS-window behavior could not be verified as a real second window in this sandbox.** Worked around by monkey-patching `window.open` (from the page's own console, not app code) to return a real, same-origin `<iframe>`'s `contentWindow` instead of a real popup — since a portal only needs _some_ other window's document/DOM node, this exercises the exact same `usePopoutWindow`/`createPortal` code path end to end: confirmed the portaled `SummaryBody` rendered fully and correctly-styled inside the iframe's own document (verified via `iframe.contentDocument.body.innerText`), confirmed it stayed **live** (edited a node's `limit` in the main window via the doc directly, and the iframe's content updated to the new made/used/power values within one debounce cycle, with zero manual refresh), and confirmed the "← Return" button closed it cleanly (the iframe's content unmounted, the main window's button reverted, zero console errors). This is strong evidence the mechanism is correct, but **a real cross-window OS-level check (a genuinely separate window staying on screen while the main window is used, surviving an alt-tab, etc.) was not possible in this sandbox and is worth a follow-up manual spot-check in an unrestricted browser** if any doubt remains.
