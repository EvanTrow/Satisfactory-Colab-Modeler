# Job 009: Recipe Chooser

**Phase:** 2 · Solo canvas editor
**Status:** Done
**Depends on:** 008 (canvas skeleton), 003 (`packages/gamedata`)

## Context

Read [`PLAN.md`](../PLAN.md) section **2. The Interaction Model to Reproduce** ("Add a machine" row) and **3. Feature Scope → MVP → Canvas & editing** (Recipe Chooser filtering requirements). This job adds the entry point for populating the canvas — it doesn't add the full node UI yet (Job 010), just the modal/picker and the "an empty recipe node gets created" wiring.

## Scope

In scope:
- Double-click or right-click on empty canvas opens the Recipe Chooser (per PLAN.md §2's exact interaction — both gestures, not just one).
- Two-pane picker UI: specialty machines on the left (from `packages/gamedata`'s machine list — note MultiMachines like Miner/Oil Extractor/Resource Well Extractor/Geothermal Generator/Space Elevator need their variant selection, e.g. Mk.1/2/3 × purity, exposed here or immediately after selection), filterable recipes on the right.
- Filtering by: name (text search), machine, tier, and an alternate-recipe toggle — all four filters from PLAN.md §3 must work and compose (e.g. text + tier + alternate-only simultaneously).
- Selecting a recipe/machine creates a new node in the current container (root, for now — outpost-scoped placement is Job 013) via `packages/ydoc`'s `addNode` mutation, positioned at (or near) the click location, using a minimal placeholder visual (Job 010 fleshes out the real node card).
- Closing the chooser without selecting (Escape, click-outside) does nothing.

Out of scope:
- The full recipe node visual (ports, limit field, clock, shards) — Job 010.
- Generators-specific UI beyond correctly creating a generator-kind node when a generator recipe is picked (the *rendering* of that distinctly is Job 010's concern).
- Outpost-scoped placement / breadcrumb awareness (Job 013) — chooser always targets whatever the "current container" concept resolves to, which for this job can simply default to root.

## Deliverables

- `apps/web/src/panels/RecipeChooser.tsx` (or similar) implementing the modal, two-pane layout, and all four filters.
- Wiring: double-click and right-click handlers on the canvas background open the chooser at the cursor position.
- On selection, a call into `packages/ydoc`'s node-creation mutation with the correct `recipe`/`machine`/`kind` fields resolved via `packages/gamedata`.
- Tests: filter composition (name + tier + alternate together narrows correctly), MultiMachine variant selection produces the correct resolved `machine` field on the created node.

## Acceptance criteria

- Double-clicking or right-clicking empty canvas opens the chooser at that point; selecting a recipe creates a node at that position and closes the chooser.
- All four filters (name, machine, tier, alternate toggle) work individually and in combination against the real `game_data.json` recipe list (332 recipes, 110 alternates).
- Choosing a MultiMachine-backed recipe (e.g. Miner) correctly prompts for or defaults to a model/purity combination and stores the resolved machine variant on the node.
- `pnpm --filter web test/build/typecheck` pass.

### How the chooser is triggered and closed

- **Right-click:** `onPaneContextMenu` on `<ReactFlow>` (a real prop, fires on right-click of the empty background only — React Flow doesn't call it for right-clicks on a node). The handler calls `event.preventDefault()` (suppresses the native browser context menu) and opens the chooser immediately at `(event.clientX, event.clientY)`.
- **Double-click:** there is no `onPaneDoubleClick` prop in `@xyflow/react` v12 (confirmed against its shipped `.d.ts` files) — `onPaneClick` fires on every single click on the empty background, and `CanvasFlow` does its own manual double-click detection: a `useRef`-held `{ time, x, y }` from the previous `onPaneClick` call is compared against the new one; if the gap is ≤400ms and ≤12px, it counts as a double-click and opens the chooser (the ref is then cleared so a third click starts a fresh count rather than immediately re-triggering). Because `onPaneClick` already only fires for background clicks (not node clicks), this gets "double-click the *empty* canvas" for free with no extra target checks. `<ReactFlow zoomOnDoubleClick={false}>` is set so a background double-click doesn't *also* zoom the canvas while the chooser opens (its default is `true`).
- **Coordinates:** the triggering click's `clientX`/`clientY` are captured twice — once verbatim as `screenPosition` (used only to position the modal on screen, clamped to stay within the viewport via `clampModalPosition` in `RecipeChooser.tsx`) and once converted via React Flow's own `useReactFlow().screenToFlowPosition({ x, y })` as `flowPosition` (the document/canvas coordinate the created node's `x`/`y` will use). Both are computed once at open time and held in `CanvasFlow`'s `chooser` state for the lifetime of the modal — reopening filters/re-selecting doesn't recompute them.
- **Closing:** Escape (a `window`-level `keydown` listener inside `RecipeChooser`, added/removed via `useEffect`), clicking the backdrop (the fixed full-screen `<div>` behind the modal box; the box itself calls `event.stopPropagation()` on its own `onMouseDown` so clicks inside it don't bubble to the backdrop), or the ✕ button — all three just call the `onClose` prop, which `CanvasFlow` wires to `setChooser(null)`. None of these call `addNode`. Successfully selecting a recipe (or confirming a MultiMachine variant) calls `addNode` *and then* `onClose()` — from the caller's side, `onClose` doesn't distinguish "closed after creating a node" from "closed without selecting," which is fine since nothing extra needs to happen either way per this job's acceptance criteria.
- **Left pane machine selection is a filter, not a direct "create" action** — clicking a machine name sets/clears `filters.machine`, narrowing the right pane's recipe list; it does not by itself create a node. A node is only ever created by clicking a specific recipe on the right (or confirming the variant picker that follows for a MultiMachine-backed one). This interpretation was chosen over a competing reading of PLAN.md §2/§3's "specialty machines on the left" wording that might imply direct-selectable machine entries; see Deviations below.

### Node field contract — what Job 010 needs to read back

Every node this job creates has `kind: "recipe"` (uniform — see Deviations below for why generator recipes don't get a different `kind`) and `recipe: <Recipe.name>` verbatim (e.g. `"Iron Ore"`, `"Iron Plate"`). `title` is also set to the recipe name (that's what ends up in `data.label` via `useYjsSync.ts`'s existing `nodeRecordToFlowNode`, so the plain default-styled box shows something readable). `limit`/`clock` are `null`, `limitMode: "machines"`, `autoRound: false`, `shards: 0`, `beltTier: null`, `storageMode: null`, `priorityOrder: []`, `color: "#4b5563"` — all placeholder/neutral values for Job 010 to own.

The field that matters most for Job 010 is **`machine`**, and it's resolved differently depending on the recipe:

- **Plain machine** (19 of the 24 machine names any recipe actually uses — everything except Miner/Oil Extractor/Resource Well Extractor/Geothermal Generator/Space Elevator): `machine` is `recipe.machine` verbatim (e.g. `"Assembler"`, `"Refinery"`). `purity` is `null`. Directly `gameData.machinesByName.get(machine)`-able.
- **MultiMachine-backed recipe** (the 5 special names): `machine` is the **resolved concrete machine name for the chosen variant** — e.g. `"Miner Mk.3"`, not `"Miner"`. For MultiMachine families with no model list (Oil Extractor, Resource Well Extractor, Geothermal Generator, Space Elevator), `machine` is just the family name itself (e.g. `"Geothermal Generator"`), since those families' single flat `Machines` entry is keyed by the family name. `purity` is set from the chosen capacity **only when** that capacity is named `"Impure"`/`"Normal"`/`"Pure"` (true for Miner/Oil Extractor/Resource Well Extractor/Geothermal Generator — the only capacity-bearing families a recipe's `machine` field ever actually resolves to) — lowercased to match `NodeRecord.purity`'s `"impure"|"normal"|"pure"` enum. Space Elevator has neither models nor capacities, so both `machine` (family name) and `purity` (`null`) are set accordingly.
  - **Important: `NodeRecord` (packages/ydoc/src/schema.ts) has no dedicated "model" field.** The chosen model (Mk.1/2/3, when applicable) is only recoverable by reading it back out of `machine` itself — Job 010 (or anything else that needs to know "this is a Miner Mk.3 node") should do `gameData.machinesByName.get(node.machine)` to get that variant's own `Machine` record (cost/power/etc.), and/or match `node.machine` against `resolveMachine(node.recipe, gameData)`'s (if `kind === "multiMachine"`) `.variants[].machine.name` to find which specific variant it is. There is no need to re-derive `purity` separately from `machine` — both fields together fully identify the variant.
  - Concrete example verified in both the unit tests and live manual testing: picking the "Iron Ore" recipe (which has `recipe.machine === "Miner"`) and confirming Mk.3 × Pure in the variant picker produces `{ recipe: "Iron Ore", machine: "Miner Mk.3", purity: "pure" }`. Picking it with no variant change (the picker's own defaults) produces `{ machine: "Miner Mk.1", purity: "normal" }` — `defaultVariant()`'s pick (Mk.1 is the `Default: true` model, Normal the `Default: true` capacity).
- `containerId` is always whatever `useCanvasDoc()` returns (the root container id from Job 008 — there's no outpost drill-in yet, per this job's explicit scope).

### MultiMachine variant picker UX

When the chosen recipe's `resolveMachine(recipe.machine, gameData).kind === "multiMachine"`, `RecipeChooser` swaps its two-pane view for a small step-2 view (`VariantPicker`, same file) instead of creating the node immediately: a `<select>` for the model dimension (only rendered if `multiMachine.models.length > 0` — Oil Extractor/Resource Well Extractor/Geothermal Generator/Space Elevator have none) and one for the capacity dimension (only rendered if `multiMachine.capacities.length > 0` — Space Elevator has none), both pre-populated to `defaultVariant(resolved)`'s pick, a "← Back" button (returns to the recipe list, filters preserved) and an "Add to canvas" button (calls `buildNodeInputForRecipe` with the current `{ model, capacity }` choice, then `addNode`, then closes). This is deliberately plain `<select>` elements, not a polished picker — Job 010 owns polished node/variant UI, this only needs to produce a *correct* choice.

One implementation detail worth flagging for whoever next touches `buildNodeInputForRecipe`: it deliberately does **not** call `@scm/gamedata`'s `findVariant(resolved, variantChoice)` when `variantChoice` is entirely omitted (falls back straight to `defaultVariant` instead). `findVariant`'s options object treats an `undefined` field as "match any value for that dimension," and because `MultiMachineVariant`s are built model-major/capacity-minor, an entirely-empty options object resolves to the *first* variant in that ordering (e.g. Miner Mk.1×Impure) rather than the actual default (Mk.1×Normal) — a real footgun if naively wired up. `buildNodeInputForRecipe` sidesteps it by only calling `findVariant` when a caller actually supplies a `variantChoice`.

### Filters

`RecipeChooserFilters = { search: string; machine: string | null; tier: string | null; alternatesOnly: boolean }`, all four ANDed together in `filterRecipes`. `search` is a case-insensitive substring match on `recipe.name`; `machine` is an exact match against `recipe.machine` (set by clicking a left-pane entry, click again to clear back to "All machines"); `tier` is an exact match against `recipe.tier.raw` (e.g. `"6-1"`, via the tier `<select>`); `alternatesOnly` keeps only `recipe.alternate === true`. Results are sorted by tier then name. Verified against the real dataset (332 recipes total, 110 alternates) both in `filters.test.ts` and live in the browser (search "iron" + machine "Assembler" + tier "5-2" + alternates-only narrowed to exactly "Adhered Iron Plate" and "Coated Iron Plate").

### Deviations from the spec / things flagged for later jobs

- **All recipe-created nodes use `kind: "recipe"` uniformly, including generator recipes** (e.g. picking the "Geothermal Generator" recipe, or a Coal-Powered Generator fuel recipe, still produces `kind: "recipe"`, not a distinct `"generator"` kind). The job file's own Out-of-scope line ("Generators-specific UI beyond correctly creating a generator-kind node when a generator recipe is picked... is Job 010's concern") is ambiguous about whether "generator-kind node" meant a literal `kind: "generator"` value or just "a node that is correctly identifiable as a generator recipe." This job took the latter reading — `NodeRecord.kind`'s `KNOWN_NODE_KINDS` (`packages/ydoc/src/schema.ts`) doesn't list `"generator"`, and `recipe.isGenerator` (from `@scm/gamedata`, keyed off the recipe name already stored on the node) is sufficient for Job 010 to detect and render generators distinctly without a schema-level `kind` split. If Job 010 (or a design review) decides a real `kind: "generator"` is wanted after all, that's a small, isolated change confined to `buildNodeInputForRecipe`'s `kind:` line.
- **The left pane ("specialty machines on the left" per PLAN.md §2) is implemented as a machine-name filter for the right pane, not a set of directly-selectable/creatable entries.** PLAN.md's wording ("Two lists: specialty machines on the left... filterable recipes on the right") is compatible with either reading; this job treated the left pane as populated by `listChooserMachines` (the 24 machine names that at least one recipe actually uses, derived from `gameData.recipesByMachine`) purely as a way to set the `machine` filter, with node creation always happening by picking a specific recipe on the right (recipe or, for MultiMachines, recipe + variant). No other "specialty" node types from PLAN.md §2's broader list (Splurger, Storage Container, AWESOME Sink, Priority Splitter/Merger, Outpost, Blueprint, Dimensional Depot Uploader) are creatable from this chooser — none of those are recipe-driven and none were named in this job's Deliverables/Acceptance criteria (which only ever mention `recipe`/`machine` fields resolved via `@scm/gamedata`), so they're left for whichever future job actually owns each of those node kinds.
- **Modal position is clamped to the viewport, not pinned exactly under the cursor when that would overflow the screen** (`clampModalPosition` in `RecipeChooser.tsx`, margin 12px, modal size 640×480 fixed). This matches the job's own "at (or near) the click location" wording for node placement, extended to the modal's own on-screen position for consistency; the *node's* `x`/`y` always uses the exact, unclamped `flowPosition` regardless of where the modal itself ended up rendering.
- Added `apps/web`'s first-ever automated test infra (`vitest`, `vitest.config.ts`, `"test"` script) rather than treating "no test infra yet" as a blocker — the job file's own Deliverables section explicitly asked for filter-composition and MultiMachine-variant tests, and the filtering/node-building logic was written as plain, React-free functions (`filters.ts`) specifically so it could be tested this way without pulling in React Testing Library or jsdom. Only pure-logic tests exist so far; no component-level/DOM tests were added, and `vitest.config.ts` deliberately has no React/jsdom setup yet — a future job adding component tests will need to extend it.
- No changes were needed to `packages/gamedata` or `packages/ydoc` — both packages' Job 003/007 public APIs already exposed everything this job needed (`resolveMachine`, `findVariant`, `defaultVariant`, `recipesByMachine`, `addNode`, etc.) with no gaps.
