## Scope

In scope:
- Click-to-select a single node/edge.
- **Right-click-drag marquee** for multi-select (note: right-click-drag, not left — this is called out specifically in PLAN.md because left-click-drag is reserved for panning/other gestures).
- Standard keybinds: cut, copy, paste, delete (and select-all) for the current selection, operating on nodes, their internal edges, and edges between selected nodes.
- Copy/paste must correctly regenerate IDs for pasted nodes (new `nodeId`s) while preserving relative position offsets and internal edge topology (edges between two copied nodes should also be copied with new deterministic `edgeId`s derived from the new node IDs; edges to non-copied nodes should not be pasted).
- **Per-user undo/redo** using the `Y.UndoManager` set up in Job 007 — this is the first job that actually surfaces undo/redo in the UI (keybinds + wiring), and per PLAN.md it must be per-user (each collaborator's undo stack only undoes their own changes, which `Y.UndoManager`'s `trackedOrigins` mechanism supports — tag each local transaction with the local user/session as its origin).

Out of scope:
- Snap-to-grid (Job 014, unless trivially bundled here — worker's call).
- Multiplayer-aware undo semantics beyond what `Y.UndoManager`'s local `trackedOrigins` already gives you for a single local user — true multi-client undo isolation is exercised for real in Job 020+ once there are multiple clients; this job just needs the mechanism correctly wired for one user.

## Deliverables

- Selection state (single + marquee) wired into the canvas.
- Cut/copy/paste/delete keybinds operating correctly on nodes + their edges.
- Undo/redo keybinds wired to the `Y.UndoManager` from Job 007.
- Tests: paste produces new IDs with correct relative positions and correctly-scoped internal edges; undo after a multi-node delete restores everything in one step; redo re-applies it.

## Acceptance criteria

- Marquee select via right-click-drag selects exactly the nodes/edges under the marquee.
- Copy-paste of a group of connected nodes preserves their internal wiring with fresh IDs, and does not duplicate edges to nodes outside the copied set.
- Undo/redo correctly round-trips through node moves, adds, deletes, and edge changes, matching the granularity a user would expect (one user action = one undo step, even if it touched multiple Yjs maps — verify the transaction grouping from Job 007 achieves this).
- `pnpm --filter web test/build/typecheck` pass.

### Marquee mechanics, precisely

**Why this is hand-rolled instead of `@xyflow/react`'s `selectionOnDrag`/`selectionKeyCode` props:** traced through the installed `@xyflow/react@12.11.2`'s own bundled source (`dist/esm/index.mjs`) — `Pane`'s `onPointerDownCapture` handler, which is what starts React Flow's own built-in marquee, has a hardcoded `event.button !== 0` early bail with no prop to change it. Separately (and conveniently, since it meant zero prop tuning was needed on `<ReactFlow>` itself), `@xyflow/system`'s own pan/zoom filter (`createFilter`) already rejects the right mouse button for panning whenever `panOnDrag` is left at its default `true` — its `buttonAllowed` check is `!event.button || event.button <= 1`, i.e. button 0 or 1 only. So a right-button drag on the canvas does *nothing* in stock React Flow, and this hook owns it outright.

**Right-click-vs-marquee disambiguation:** `useMarqueeSelection`'s pointer handlers track a `dragStateRef` (start point + a `dragging` bool that flips true once the pointer moves past a 4px threshold) from `pointerdown` (button 2) through `pointermove`/`pointerup`. If the drag threshold was never crossed, nothing happens on `pointerup` — it was just a plain right-click, and the browser's native `contextmenu` event fires afterward exactly as before this job, reaching `CanvasView.tsx`'s `handlePaneContextMenu` unimpeded (confirmed live: quick right-click still opens the Recipe Chooser, no regression from Job 009). If the threshold *was* crossed, `pointerup` finalizes the selection and sets a `justDraggedRef` flag. The browser's `contextmenu` event still fires after a right-drag release on most platforms — it is **not** reliably suppressed by drag distance, so `handlePaneContextMenu` has to actively check for this: it calls `consumeJustDragged()` (which reads-and-resets the flag) and returns early, skipping `openChooserAt`, whenever it's `true`. The flag is also defensively reset to `false` at the very top of every new `pointerdown`, in case a previous drag's `contextmenu` never fired at all (e.g. a platform that *does* suppress it) — so a stale `true` can never leak into suppressing some later, unrelated quick right-click.
- Confirmed live via the Browser MCP's synthetic `PointerEvent`/`MouseEvent` dispatch: a right-drag across two connected nodes selected both nodes and their connecting edge, and the immediately-following synthetic `contextmenu` event did **not** open the chooser; a separate no-movement right-click-then-`contextmenu` sequence did.

**Node/edge hit-testing:** a node is selected if its bounding rect (`position` + `measured.width`/`.height`, falling back to `256×160` — `RecipeNode.tsx`'s fixed card width plus a rough average height — for the brief window before a node's first paint) intersects the marquee rect at all (`rectsIntersect`, `Partial`/touch-counts semantics, not full containment). An edge is selected if **either** both its endpoint nodes were hit, **or** its `[sourceCenter, ...waypoints, targetCenter]` polyline itself crosses the rect (`polylineIntersectsRect`) — the first condition is almost always what actually fires in practice, since an endpoint node being hit means that node's *center point* (which every edge's polyline starts/ends at) is by definition inside the node's own bounding rect, which was just found to intersect the marquee; live-verified this reads as "the edge counts as under the marquee whenever either connected node is," which is the natural reading of "nodes/edges under the marquee" for a connected edge, not a bug. Marquee-selecting only one of two connected nodes was confirmed live to select just that node (not its neighbor), while still also selecting the shared edge, per the above.

### Paste ID-regeneration algorithm

See `pasteClipboard`'s own doc comment in `clipboard.ts` for the full write-up; the short version, live-verified end to end:
1. For each copied node (in clipboard order), call `@scm/ydoc`'s `addNode` with **no `id`** — it self-generates one — passing every other field through unchanged except `x`/`y`, which get the paste offset (`{dx:40, dy:40}` by default) added. Record `oldId → newId` in a `Map` as each node is created.
2. For each copied edge (already filtered by `buildClipboard` to only edges between two copied nodes), look up its `fromNode`/`toNode` in that map and call `addEdge` with the **new** endpoints — `addEdge`'s id is itself `computeEdgeId(fromNode, fromPort, toNode, toPort)` (Job 007), so a correct, fresh, deterministic id falls out automatically, no separate generation step needed for edges. The edge's waypoints (absolute canvas coordinates, per Job 011) get the same `{dx,dy}` offset as the nodes, so a pasted group's internal wiring looks identical to the original, just shifted.
3. The whole thing runs inside one `sfmDoc.doc.transact()` call. Live-verified via `window.__sfmDoc`: pasting two nodes at `(594,236)`/`(919.75,428.25)` connected by an edge with one waypoint produced two new nodes at exactly `(634,276)`/`(959.75,468.25)` (i.e. `+40,+40` on both, preserving the `(325.75, 192.25)` relative offset between them) and one new edge with a fresh id connecting *only* the two new node ids (never the originals), with its waypoint also shifted by `+40,+40`.
- Acceptance criterion "does not duplicate edges to nodes outside the copied set" is enforced at `buildClipboard` time, not at paste time — `pasteClipboard` trusts its input payload completely (also unit-tested directly: a payload built from a single-node selection has zero edges even when a same-shaped edge exists elsewhere in the doc).
- After a paste, the previously-selected nodes/edges are deselected and the newly-pasted ones are selected instead (conventional "paste replaces selection with what you just pasted" behavior, and what makes an immediate follow-up drag/delete act on the new group). This is implemented as an explicit list of `{id, selected}` changes for exactly the ids that changed (old selection → `false`, `pasteClipboard`'s returned new ids → `true`), **not** a full-array remap — see `useSelectionKeybinds.ts`'s `handlePaste` doc comment for why: by the time `pasteClipboard` returns, its `transact()` has already synchronously triggered `useYjsSync.ts`'s `.observeDeep` resync (Yjs's own `transact()` runs its cleanup/observer phase before returning to the caller), so the Zustand store already has the new node/edge ids in it even though the `nodes`/`edges` arrays closed over by this keydown handler are one render behind — an explicit id list sidesteps needing that freshness at all, since `applyNodeChanges`/`applyEdgeChanges` (in `useYjsSync.ts`) resolve against the *live* store via `useStore.getState()`, not against whatever array of "current elements" the caller happens to hand it.

### Undo/redo — how it's wired into the UI

- **One `Y.UndoManager` per document**, created in `CanvasView.tsx`'s `createLocalCanvasDocument` via `createUndoManager(sfmDoc)` (Job 007's defaults: `trackedOrigins = new Set([null])`, i.e. only local, `origin`-less transactions — which is every mutation this app's UI makes, since nothing anywhere in `apps/web` passes an explicit `origin` to a `@scm/ydoc` mutation helper). Per this job's brief and Job 007's own handoff notes, that alone satisfies PLAN.md's "per-user undo" for this phase: there's exactly one local user per open browser tab until Job 020 introduces real multiplayer origins, so "per-user" and "per-document" currently coincide. No user/session-id `trackedOrigins` machinery was built — Job 007 deliberately left `trackedOrigins` overridable for whenever that becomes necessary.
- **Keybinds:** Ctrl/Cmd+Z (undo; +Shift for redo), Ctrl+Y (redo) — wired in `useSelectionKeybinds.ts`, calling `undoManager.undo()`/`.redo()` directly.
- **Toolbar buttons:** `CanvasView.tsx`'s header bar, next to "Back to projects" — Undo/Redo buttons whose `disabled` state comes from `useUndoRedoState(undoManager)`. Both entry points (keybind and button) call the identical `Y.UndoManager` methods; there's no separate "undo logic" anywhere in this job's own code, by design — Job 007 already owns all of the actual undo/redo semantics.
- **One user action = one undo step:** relies on Yjs's own `transact()` behavior (verified directly against `yjs@13.6.32`'s source, not assumed): calling `doc.transact()` while a transaction is already active reuses the existing transaction instead of starting a nested one, and only commits (fires the single resulting update / `Y.UndoManager` stack entry) once the *outermost* `transact()` call returns. `pasteClipboard` and `deleteSelection` each wrap their entire multi-`addNode`/`addEdge`/`removeNode`/`removeEdge` body in one outer `sfmDoc.doc.transact()` call for exactly this reason, so e.g. "delete 3 nodes and their 2 connected edges" is guaranteed to land as a single undo step regardless of timing (not relying on `Y.UndoManager`'s own `captureTimeout`-based merge-window coincidence, which would have worked too in practice but is a strictly weaker guarantee). Live-verified: undoing a multi-node delete (via Delete after a marquee-select) restored every node and edge in one `Ctrl+Z`; redo re-deleted them in one `Ctrl+Shift+Z`. Also live-verified for a plain single-node drag (`moveNode`, called by `useYjsSync.ts`'s pre-existing `onNodeDragStop` — untouched by this job): one `Ctrl+Z` reverted the drag to the exact prior `x`/`y`.

### The selection-loss bug (found and fixed, not anticipated going in)

`useYjsSync.ts`'s `.observeDeep` resync (`syncNodes`/`syncEdges`, Job 008) rebuilds the *entire* `nodes`/`edges` array from scratch on **every** doc mutation, including ones with nothing to do with the current selection — e.g. editing a different node's clock field, or another node's drag committing. Before this job, `nodeRecordToFlowNode`/`edgeRecordToFlowEdge` never set `selected` at all (implicitly `undefined`/falsy), so any such unrelated mutation would silently clear the whole canvas's selection out from under the user — invisible until this job's marquee/multi-select work actually needed selection to survive more than one render. Fixed by having `syncNodes`/`syncEdges` read the store's *previous* snapshot's `selected` ids (by id, via `useStore.getState()`) before rebuilding, and passing that through to the now-parameterized `nodeRecordToFlowNode(record, selected)`/`edgeRecordToFlowEdge(record, selected)`. Live-verified: selected a node, then triggered an unrelated `addNode` via the dev harness — the original node's `selected` class survived the resync.

### What Job 013 (outposts) needs to know

- **`deleteSelection(sfmDoc, nodeIds, edgeIds)` (`apps/web/src/canvas/selection/clipboard.ts`) is the reusable "delete these nodes and every edge touching them, as one undo step" primitive.** If deleting/moving an outpost container needs to also clean up the nodes inside it, this is very likely the function to call (with the container's own child node ids) rather than reimplementing the "find and remove dangling edges" scan — it already handles the Job 007 "`removeNode`/`removeContainer` don't cascade" gap for nodes/edges. It does **not** currently touch `containers` at all (out of this job's scope — no outpost UI existed yet); Job 013 will need its own `removeContainer` call alongside it, and should decide what happens to nodes still inside a deleted container (PLAN.md §5 reserves "reparent orphaned nodes to root" for the Job 022 integrity reducer, so per Job 007/011's established convention, immediate local cleanup vs. leaving it for the reducer is Job 013's own call).
- **`CanvasDocContextValue` now carries `undoManager`** (`apps/web/src/canvas/CanvasDocContext.ts`) — already document-wide (its `scope` is `[settings, containers, nodes, edges]`, not scoped to any one container), so drilling into an outpost and moving/editing nodes there will already undo/redo correctly with zero changes needed on Job 013's part. Nothing about this job's undo wiring is aware of "current container" at all.
- **Selection is a Zustand-store-only concept (`node.selected`/`edge.selected` on `CanvasNode`/`CanvasEdge`), never written to the Yjs doc.** If Job 013 adds a "current outpost" concept that changes which nodes/edges `useYjsSync.ts` even lists (e.g. filtering to the current container), be aware that a node's selection state is carried across `.observeDeep` resyncs purely by id-lookup against the *previous* rendered list (see "The selection-loss bug" above) — a node that disappears from the list (e.g. because the user drilled into a different outpost) simply won't have its `selected` flag carried forward if it reappears later; this wasn't tested and may need revisiting once "which nodes are even listed" can change out from under the user.
- **The in-memory (not OS) clipboard (`clipboardRef` inside `useSelectionKeybinds.ts`) is a plain `useRef`, scoped to one `CanvasView` mount** — see "Deviations" below. If Job 013 (or a later job) wants copy/paste *between* two open outposts within the *same* document, that already works today (paste just needs a different `containerId`, and the hook only receives whichever `containerId` `CanvasFlow` currently has) — but copy/paste across two different open *documents/tabs* would need a real OS-clipboard-backed implementation, which this job deliberately didn't build.
- **The marquee's node-size fallback (`FALLBACK_NODE_WIDTH`/`HEIGHT` in `useMarqueeSelection.ts`) assumes `RecipeNode.tsx`'s current fixed `w-64` card.** If Job 013 introduces a differently-sized outpost/container node type, this fallback (only used for the brief pre-first-paint window before `measured` populates) may want a per-kind adjustment, though it's a minor cosmetic edge case, not a correctness one.

### Deviations from the spec / things flagged for later jobs

- **The clipboard is in-app (a `useRef`), not the real OS clipboard.** Using `navigator.clipboard` would add permission-prompt friction (and, per this environment's own safety rules, writing arbitrary structured data to the real system clipboard silently is the kind of thing worth being deliberate about) for a feature PLAN.md only specifies as "standard cut/copy/paste/delete keybinds" without calling out cross-application interoperability. If a later job needs OS-clipboard interop (e.g. copying a node group out of the app entirely), the natural extension point is `clipboard.ts`'s existing `ClipboardPayload` shape — serialize it to JSON for `navigator.clipboard.writeText`/parse it back on paste — without touching the id-regeneration logic itself.
- **Marquee selection uses `Partial` (touch-counts) containment, not `Full` (must-be-entirely-inside)** — React Flow's own default for its built-in marquee is `Full`; this job picked `Partial` as the more common "brush select" expectation and because the job file/PLAN.md don't specify either way. Easy to flip (`rectsIntersect`'s own semantics would need to become "b fully contains a") if a later job's UX pass wants the other convention.
- **A right-click-drag marquee can start on top of a node, not just the empty pane** — deliberate (see `CanvasView.tsx`'s wrapper-div comment), since PLAN.md doesn't restrict the marquee's start point and requiring an empty-pane start would make "marquee starting near a cluster of nodes" needlessly fiddly. This does *not* conflict with node dragging (which is left-button-only) or with right-clicking a node's own part row (which still `stopPropagation`s its own `onContextMenu`, from Job 011, independent of this job's pointer handling).
- **No `Escape`-to-cancel-marquee-mid-drag was built** — not in this job's scope/acceptance criteria (which specify the drag-to-completion gesture, not a cancel path), and `onPointerCancel` already handles the platform-level cancellation case (e.g. a touch gesture or window blur interrupting the pointer sequence).
