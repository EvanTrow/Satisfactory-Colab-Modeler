## Scope

In scope:

- **Accessibility pass** across the whole app: keyboard navigation for the project list, auth flow, and as much of the canvas as is reasonably achievable (full canvas a11y for a node-graph editor has real limits — focus on what's practical: modal focus trapping in the Recipe Chooser, ARIA labels on icon-only buttons, sufficient color contrast in both themes from Job 014, screen-reader-reachable summary panel data). Document known limitations rather than claiming full WCAG compliance if the canvas interactions genuinely can't get there.
- **Production deploy**: `infra/Dockerfile` and deploy config for the "single container host with managed Postgres" decision (Fly.io/Railway/Render, per PLAN.md §10's confirmed-decisions list — pick one if not otherwise specified, Fly.io is a reasonable default) — build, deploy `apps/web` (as static assets or SSR, whichever the Vite setup produces), `apps/api`, and `apps/realtime` (co-deployed with api in one container, per PLAN.md §7's project structure note) against a managed Postgres instance.
- **Backups**: automated Postgres backups (daily snapshot at minimum) via whatever the chosen host provides natively, documented in `infra/`.
- **Error tracking**: integrate a basic error-tracking service (e.g. Sentry, or whatever's available/preferred) across `apps/web`, `apps/api`, `apps/realtime`, capturing unhandled exceptions and, ideally, the CRDT integrity-reducer firing (Job 022) as a signal worth tracking (since a repair firing often indicates a real bug elsewhere, even though the reducer's job is to make it non-fatal).
- Production environment variable/secrets handling (Discord OAuth secrets from Job 005, database URL, session signing keys, error-tracking DSN) — documented, not committed.

Out of scope:

- Any new product features — this is exclusively hardening/ops work on top of the complete MVP+Phase 6/7 feature set from Jobs 001-028.

## Handoff notes

### The scope boundary — read this first

**This job produced a genuinely deploy-ready application, not a deployed one.** No real cloud hosting account, no real Discord OAuth application beyond what earlier jobs already registered for local dev, no real Sentry project, and no real backup exist anywhere as a result of this job — none were created, per this job's own explicit instructions (creating cloud accounts and entering billing information are actions outside what an autonomous agent may take without a human's direct, in-the-moment involvement). Everything below was built and, wherever technically possible, **proven working entirely locally** — see "Verification actually performed" below for exactly what was and wasn't (and couldn't be) tested. The root `README.md`'s new "Production deploy" section is the authoritative, concrete, numbered list of what a human still has to do (create the Fly.io/Discord/managed-Postgres/Sentry accounts, set which secrets where, run which commands) — this section here summarizes it but that's the one to actually follow.

### Deploy-readiness

- **`infra/Dockerfile`** — multi-stage (`build` then `runtime`), producing one image with `apps/web`'s static build, `apps/api`, and `apps/realtime` all present. **Genuinely built and run locally** (`docker build`/`docker run`) against a throwaway Postgres container multiple times over the course of this job, most recently after every other change in this job had already landed (Sentry wiring included) — not just once early on.
- **The real, non-obvious blocker this job had to solve**: `apps/api`/`apps/realtime`'s compiled `dist/index.js` cannot run under plain `node` in production. This is the exact gap Job 020/022's own Handoff notes flagged and deferred to "Phase 7's eventual deploy/production-packaging work" — `packages/ydoc`/`packages/gamedata`/`packages/rational` are deliberately still JIT-consumed (`"main": "./src/index.ts"`, no `dist/`) so `apps/web`'s Vite dev server keeps its no-build-step-needed workflow (root `README.md`'s own "Workspace conventions" section). `apps/realtime` imports `@scm/ydoc` directly; `apps/api` transitively imports both `@scm/ydoc` and `@scm/rational` via `@scm/doc-storage`'s `projection.ts` (a real, non-type-only import — confirmed by grep, this surprised the initial Dockerfile draft, which assumed `apps/api`'s doc-storage dependency was migration-safe under plain `node` and had to be corrected after a live container actually hit `ERR_UNKNOWN_FILE_EXTENSION ".ts"`). Fixed by running the already-built, already-typechecked `dist/index.js` (and the migration runner, `apps/api/dist/db/migrate.js`) through `tsx` instead of plain `node` — `tsx` is already what `apps/api`/`apps/realtime`'s own `dev` scripts use, so this costs a small startup-time transpilation hit and touches no package's `main`/`exports` field, meaning `apps/web`'s dev-time JIT consumption of the same three packages is completely unaffected. `infra/docker/entrypoint.mjs`'s header comment has the full trail, including the two live failures encountered (kysely not found — because pnpm's per-workspace `node_modules` weren't all being copied by an earlier draft's curated `COPY` list; fixed by copying the WHOLE built `/app` as one unit — and the `.ts` extension failure above).
- **Single-container "same origin" shape**: `infra/docker/proxy/proxy.mjs` (a small, deliberately-not-a-pnpm-workspace-member Node script using `http-proxy`) is the reverse proxy that makes `apps/web/src/canvas/persistence/realtimeTicket.ts`'s existing `getRealtimeWsUrl()` default (same-origin `/collab`, unchanged since Job 020) actually true in production — it fans one public port out to `apps/api` (everything else, including the static SPA — see `apps/api/src/staticSite.ts`, new) and `apps/realtime` (`/collab*`, including genuine WebSocket upgrade proxying, verified live via a raw `curl` Upgrade handshake returning `101 Switching Protocols` through the full proxy chain, not just a health-check-level check). `infra/docker/entrypoint.mjs` supervises all three processes (api/realtime/proxy) as one unit — if any one exits, the others are killed and the whole container exits non-zero, verified live by `pkill`-ing the api process inside a running container and observing the teardown cascade in the logs; graceful `SIGTERM`/`docker stop` was also verified to shut down cleanly (exit code 0).
- **`apps/api/src/staticSite.ts`** (+ `staticSite.test.ts`, 6 new tests) — serves `apps/web`'s built `dist/` from the same Fastify instance, gated entirely behind `WEB_DIST_DIR` being set (a no-op in every existing dev/test environment — proved by a real regression: `index.html`'s cache-control initially leaked the plugin's own long-lived `max-age` header onto the SPA-fallback path too, caught and fixed via `@fastify/static`'s `setHeaders` option, verified against real header output both via the test suite and a live `curl -D-` against the running container).
- **`infra/fly.toml`** — one `[[services]]` block (port 8080, the proxy's port) rather than exposing `apps/api`/`apps/realtime`'s ports separately, matching the same-origin-proxy design above. Never run against a real Fly account (none exists) — the TOML was written carefully against Fly's documented schema but not validated with `fly config validate` or a real `fly launch`; flag this as the one piece of this job's deploy config that's "written correctly" rather than "proven correct," pending a human's first real deploy attempt.
- **`infra/BACKUPS.md`** + **`infra/scripts/backup.sh`** (the plain-`pg_dump` fallback, only needed if the chosen host has no native backup feature) — the fallback script was **genuinely run** against the real local dev Postgres (a true, if unusually large, database — see below) and its output **genuinely restored** into a scratch database (`scm_restore_test`, created and dropped in the same verification pass) with a real row count confirmed non-zero — this is as much "verifiably running" as a backup mechanism can be proven without a real managed-host account to point it at.
- **`.dockerignore`** (new) — keeps host `node_modules`/`dist`/`.env` files out of the Docker build context; without it, a first Dockerfile draft risked either leaking secrets into an image layer or letting a Windows-built `node_modules` silently skip a correct Linux reinstall inside the container.
- **Deliberately NOT size-optimized**: the runtime image copies the ENTIRE built workspace (`COPY --from=build /app ./`), including every workspace's own `node_modules` (needed — see the `tsx` reasoning above) and `apps/web`'s own dev-toolchain `node_modules` (not strictly needed at runtime, since its `dist/` is self-contained, but not worth the risk of a curated copy list missing something again). Flagged as a legitimate future optimization, not a correctness gap.

### Error tracking

- `apps/api/src/monitoring/sentry.ts`, `apps/realtime/src/monitoring/sentry.ts`, `apps/web/src/monitoring/sentry.ts` — `@sentry/node`/`@sentry/react`, each with a `SENTRY_DSN`/`VITE_SENTRY_DSN`-gated `enabled` flag so every capture call is a real no-op (not just "probably fine") until a real DSN exists. Verified two ways: (1) real unit tests in all three (`sentry.test.ts`, `@sentry/node`/`@sentry/react` fully mocked via `vi.mock` — no real DSN, no real network call, ever) proving both the no-op path and the "reports once configured" path; (2) **live**, by the simple fact that `apps/api`/`apps/realtime`'s dev servers have been running this exact code with no `SENTRY_DSN` set throughout this whole job with zero crashes or errors, and the freshly-rebuilt Docker image (see above) booted and served real HTTP traffic cleanly under the same unconfigured state.
- Wired: unhandled exceptions/rejections in all three apps (Node: `process.on('uncaughtException'|'unhandledRejection')`, explicitly re-`exit(1)`ing after reporting to preserve each app's existing crash-don't-limp-along behavior — confirmed live that Node 20+'s actual default for an unhandled rejection with no listener is to crash, not "log a warning," correcting a first draft's comment that assumed the older Node<15 behavior); every Fastify 5xx route error via a non-invasive `onError` hook (an observer, not `setErrorHandler` — cannot change any response, confirmed by the full `apps/api` suite staying green); a browser-side `SentryErrorBoundary` around `<App>` plus `window.onerror`/`unhandledrejection` listeners in `main.tsx` (the boundary and the window listeners cover disjoint failure classes — a render-time throw never reaches `window.onerror`, see that file's own comment).
- **The specific signal PLAN.md/this job's scope called out**: the CRDT integrity reducer (Job 022) firing is reported via a shared `captureIntegrityRepairSignal(context)` at all FOUR of its real call sites — `apps/realtime/src/server.ts`'s `afterLoadDocument` (a document already corrupt in Postgres) and `onStoreDocument` (a live client's edits needed a fix) previously discarded `runIntegrityReducer`'s return value entirely; `apps/web`'s `useProjectDocument.ts` repair-on-load and `clientIntegrity.ts`'s ongoing `afterTransaction` listener did too. All four now check `isNoopRepair(summary)` and report (`warning` level, not `captureException` — a repair firing is explicitly non-fatal by the reducer's own design) only when something actually changed.

### Accessibility pass

**Fixed:**

- **Focus trapping** — a single reusable `apps/web/src/a11y/useFocusTrap.ts` hook (Tab/Shift+Tab containment, auto-focus-on-open, Escape-to-close, focus-restore-on-close) applied to all four panels the job's own scope named (`RecipeChooser`, `SettingsMenu`, `SharingPanel`, `VersionPanel`) plus two more found to have the identical dropdown-panel shape and gap (`SummaryPanel`, `NodeContextMenu`) — all six previously let Tab walk focus straight out into the canvas/toolbar behind an open panel, with no way for a keyboard/screen-reader user to know a panel was even open. **Verified live** (not just by reading the code): opened Settings via the real running app, confirmed focus auto-landed inside, Tab through its 9 real focusable controls wrapped back to the first one, and Escape closed it and returned focus to the Settings button — the exact same pattern independently re-verified for Sharing and the Recipe Chooser. **A real regression was found and fixed during this same live check**: `RecipeChooser`'s trap initially stole focus from the search input (which already had Job 009's own `autoFocus`) onto the "+ New Outpost" button instead, since that button sits earlier in the DOM — fixed via the trap's `initialFocusRef` option, added specifically for this case; re-verified live that the search box gets focus correctly now, then confirmed the whole keyboard flow end-to-end (Tab into the search box → type "Iron Ingot" → Tab to the recipe button → activate it → a real node was created → Tab to the Summary Panel button → activate → the panel opened with its own focus trap and real, screen-reader-reachable text content for made/used/power/sink-points/cost-to-build, none of it canvas-only pixels).
- **ARIA labels on icon-only buttons** — the minimap toggle (`CanvasView.tsx`, previously title-only) and four clock-speed/somersloop ± stepper buttons on `RecipeNode.tsx` (previously no accessible name at all beyond the visible glyph) plus three icon-only tier/reorder/disconnect buttons on `SplurgerNode.tsx`. Undo/Redo, Settings, Share, Version history, the theme toggle, and both save/connection status indicators already had real accessible names or visible text from earlier jobs (Job 014/016/019/020/022/027/028's own prior work) — audited directly by reading every `<button>` in `apps/web/src/canvas`, `panels`, `sharing`, `routes`, `theme`, `collab`, and confirmed the icon-only ones above were the actual gap, not a hypothetical one.
- **Color contrast** (`apps/web/src/index.css`, building on Job 014's token system) — a real, reproducible WCAG 2.1 contrast-ratio audit (`apps/web/src/a11y/contrastAudit.ts` + `contrastAudit.test.ts`, a genuine regression test asserting every real text/background token pair used in this app clears 4.5:1, not a one-off script) found and fixed FIVE real failures in the light theme (`--text-muted` at 2.64-2.84:1 against its own surface tokens; `--blueprint`/`--outpost`/`--splurger` at 2.84-4.13:1 as text against their own `-soft` badge backgrounds) and one in dark (`--text-muted` at 3.81-4.10:1) — all measured well under WCAG AA's 4.5:1 minimum for normal-size text before this job, all now 4.5-6.3:1. The unavoidable side effect, documented in `index.css`'s own token comments: on this palette's very pale light-theme backgrounds, an AA-passing "muted" tone ends up close to "secondary" in darkness — accepted as the honest tradeoff (real contrast over visual separation) rather than shipping a muted tone that fails AA.
- **Screen-reader-reachable summary panel** — verified live via `get_page_text` (a real accessible-text extraction, not a screenshot) that every summary figure (made/used/unmade/unused per part, power made/used/net, sink points, cost-to-build) is real DOM text content, confirmed reachable via the same focus-trap Tab sequence as everything else.
- **Keyboard-only core flow** — verified live end to end: open a project (mouse — see the tooling caveat below), Tab to reach every toolbar control with correct accessible names (confirmed via the accessibility tree, not just visual inspection), open the Recipe Chooser (double-click — a genuinely pointer-only trigger, see limitations below), Tab to and select a real recipe with the search box correctly pre-focused, confirm the created node, Tab to and open the Summary Panel, confirm its focus trap and content. The project list (`ProjectsPage.tsx`) and the Discord login link (`App.tsx`) were audited by direct code reading rather than a live logged-out pass — both are plain semantic `<button>`/`<input>`/`<a href>` elements with no custom mouse-only behavior, so a live check would only have confirmed what the markup already guarantees; logging out to test the anonymous state live was avoided specifically to not disrupt the shared dev session's live login state for the user's own concurrent use of the app.

**Known, genuine, documented limitations (not fixed — a node-graph editor has real, well-understood limits here):**

- **Drag-to-connect** (wiring a port to a port), **marquee select** (right-click-drag), **waypoint add/drag**, and **node dragging** are all inherently pointer-based gestures with no meaningful keyboard equivalent — this matches the job's own Context section's explicit acknowledgment ("full canvas a11y for a node-graph editor has real limits"). Not attempted; a genuinely accessible alternative (e.g. a keyboard-driven "select two ports, press Enter to connect" flow) would be a substantial new feature, not an accessibility fix, and is out of this job's scope.
- **`NodeContextMenu`'s trigger** (right-click a node) has no keyboard equivalent either — there is no other discoverable entry point to "move this node into an outpost" or "delete this outpost" anywhere else in the UI. Once open, though, it now behaves like every other panel (focus trap, Escape, `role="menu"`) — only the trigger itself is pointer-only, not the menu's contents.
- **`SummaryPanel`'s initial focus** lands on its "Pop out" button rather than the first scope tab (`Everything`/`Current Outpost`/`Selected`), since threading an `initialFocusRef` through to a child component (`SummaryBody`) that renders those tabs wasn't done — a minor nicety left unfixed, not a broken/untestable state (Pop out is still a real, correctly-labeled, reachable control).
- **Tooling caveat, not an app bug**: the Browser MCP's `computer` `key` action reliably moves real DOM focus via Tab (confirmed repeatedly and used throughout this job's own verification), but its synthetic `Return`/`space` keypresses did **not** reliably trigger a focused `<button>`'s click behavior in this sandbox — confirmed by dispatching Enter at a freshly-Tab-focused, plain semantic theme-toggle button and observing zero effect on `document.documentElement.className`, then confirming the identical button DOES work via a real mouse click and via `document.activeElement.click()`. This is a known, previously-documented limitation of this specific Browser MCP tool (Job 027's own Handoff notes flagged a different `window.open`-related gap in the same tool) — not evidence that any button in this app is keyboard-inoperable; every button audited in this job is a plain, semantic `<button type="button">` with no custom keydown-suppression, which is native-HTML keyboard-operable by construction. Flagged here so a future job's own manual verification doesn't waste time re-discovering this and mistaking it for a real regression.
