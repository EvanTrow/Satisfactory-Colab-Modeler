### The red-vs-orange mapping, precisely

"Invalid" (red) = a value that's individually wrong on its own terms:
- `NodeSolveResult.valid === false` (unknown recipe/machine variant, out-of-range shard count, or — Manual/Basic mode's `pinnedMachineCount` — an entered `limit` that's malformed or can't be turned into a machine count). The specific field lit up (`fields.limit`/`fields.shards`) is decided by pattern-matching the issue string for `"limit"`/`"shard"` (every message `@scm/solver` actually produces for these cases contains one of those words — see `computeValidity.ts`'s `classifyNodeIssue`); anything else (`"unknown recipe ..."`, `"could not resolve machine variant ..."`) only highlights the whole card, not a specific field.
- An edge whose `EdgeSolveResult.valid === false` for a reason OTHER than a rate mismatch (`validateEdge`'s "source/target node could not be resolved" / "recipe has no part" issues) — a downstream consequence of an already-broken neighbor, so the affected port is red, not orange.

"Mismatched" (orange) = a value that's individually fine but doesn't reconcile with a neighbor: **only** `validateEdge`'s `"rate mismatch on part ..."` issue produces this, and it colors the port (not a field) on both endpoints. This is exactly the Basic-mode "two independently-defaulted machine counts disagree across an edge" case named in the job's own acceptance criteria.

Invalid always wins over mismatched when both apply to the same node's `overall` (a node can be invalid AND have a mismatched port simultaneously — verified live, see below). A third case is deliberately left unhighlighted: Basic mode's "no limit and no resolvable neighbor — defaulted to 1 machine" fallback sets `resolved: false` but `valid: true` (not `forceInvalid`) — it isn't wrong (nothing contradicts it) and isn't mismatched (there's no neighbor to disagree with), so it gets neither color, just the existing "(unresolved — defaulted)" text suffix on the machine-count readout. Flagged below as a gap a later job could fill with a third visual treatment.

### Why validity/rates are computed locally in `RecipeNode.tsx`, not threaded through `useYjsSync.ts`'s `CanvasNodeData.validityState`

Job 010 built `validityState` as a slot on `CanvasNodeData`, populated by `useYjsSync.ts`'s `nodeRecordToFlowNode`. That resync path is triggered by **Yjs doc mutations** (`sfmDoc.nodes/edges.observeDeep`). A solve result, however, lands on a **later, independent tick** — after the ~150ms debounce plus a worker round trip — with no corresponding Yjs mutation to trigger a resync. Piping solver results through `useYjsSync` would need either a second parallel sync path keyed on solver-result changes, or forcing a full Yjs-observer re-attach on every solve completion (both worse than the alternative). Instead, `RecipeNode.tsx` reads `useSolverResult()` directly: React re-renders every Context consumer on a Provider value change **regardless of `memo()`'s prop-comparison bail-out**, so this correctly re-renders on every solve completion even though the node's own `data`/`selected` props haven't changed. `CanvasNodeData.validityState` itself is untouched — still always `null` from `useYjsSync.ts` — this is a **deliberate, documented deviation** from the literal "use the validityState prop slot" framing; nothing prevents a later job from removing that now-unused slot, or repurposing it.

### A real duplicate-scheduler bug found and fixed during manual verification

Job 018's `DevNodeTools.tsx` already had a `SolverDebugPanel` calling `useSolver(sfmDoc, {...})` directly for its own diagnostics. Adding a SECOND, independent `useSolver(sfmDoc)` call in `CanvasView.tsx` (this job's own context provider) meant **two fully independent schedulers, each with its own real `Worker` pair**, both solving the identical document redundantly — exactly the waste `SolverResultContext.ts`'s own header comment warns against. Caught via `read_console_messages` during manual browser verification: a React "change in the order of Hooks" warning on `SolverDebugPanel` followed by an uncaught `TypeError` crash in one long-lived browser tab (after many live doc mutations via the console). Root-caused to the two-scheduler duplication (confirmed by fixing it and re-testing in a **brand-new tab** — zero console errors, `nodes solved: 3 (0 invalid)`, everything rendering correctly). Fixed by switching `SolverDebugPanel` to read `useSolverResult()` from context instead of calling `useSolver` a second time; its `onDispatch`/`onCancel` counters are gone as a result (no second scheduler to own diagnostics callbacks) — `result`/`staleness` are still shown, which is all this panel's own acceptance criteria ever needed. **If a future job adds another top-level `useSolver` call anywhere in `apps/web` outside `CanvasView.tsx`, this exact bug class will resurface** — there must be exactly one real call site per open document.

### The scope-filtering/summary-recomputation approach

`nodeIdsForScope` picks the id set per scope: "everything" = every recipe node in the **whole document** (via a live `listNodes(sfmDoc).filter(kind==="recipe")` subscription in `SummaryPanel.tsx`'s own `useAllRecipeNodes` hook — deliberately NOT `useYjsSync`'s `nodes`, which is scoped to only the currently-viewed container); "outpost" = the same whole-document list filtered to `containerId === currentContainerId` (direct children only — **the "Current Outpost & Below" recursive variant from PLAN.md §2's fuller list is NOT implemented**, flagged as the one explicit scope gap this job leaves, per its own Out-of-scope note); "selected" = the live `.selected` flags off `useYjsSync`'s own (current-container-scoped) `nodes` array, which is correct by construction — you can only ever select what's currently rendered.

`summarizeScope` then re-derives made/used/unmade/unused/power/cost **from the raw per-node `NodeSolveResult.partRates`/`.power`/`.machineCount` list, restricted to that id set** — never by slicing `@scm/solver`'s own already-aggregated `SolveSummary` (its `unmade`/`unused` are each `max(0, ...)` over the whole graph's totals, and `max()` doesn't distribute over a subset — the exact same trap `apps/web/src/workers/mergeResults.ts`'s "Summary merging" section documents one layer down, for the exact same reason). Cost-to-build sums `machineCount × Machine.Cost.amount` per node (via `NodeRecord.machine` → `gameData.machinesByName`), which is why a node's build cost naturally scales with its **exact, possibly-fractional** solved machine count (verified live: a Miner Mk.1 resolved to `1/2` machines contributes exactly half its listed `Cost` array). `summaryMath.test.ts` cross-checks that running `summarizeScope` over EVERY node reproduces `@scm/solver`'s own `solve()` output's `SolveSummary.perPart`/power fields exactly, as a regression guard on that equivalence, plus a dedicated test that restricting the node-id set correctly **excludes** another node's contribution (not just includes the right one) — verified live too: viewing "Current Outpost" on an outpost containing only the downstream half of a Miner→Smelter chain shows Iron Ore as `unmade: 30` (not balanced), since the producing Miner is out of scope — a deliberately harsh but correct edge case.

### Number-format wiring

Job 007's `@scm/ydoc` `NumberFormats` (`{style, digits, rounding, trimTrailingZeros}`) and `@scm/rational`'s `FormatOptions` turned out to already match field-for-field (same names, same value unions) — the "reconcile if drifted" flag from Job 007's handoff was a non-issue by the time this job landed; `NumberFormats` is passed straight into `formatRational(value, numberFormats)` with no adapter. `SettingsMenu.tsx`'s number-format controls always patch the WHOLE `numberFormats` object (`updateSettings(sfmDoc, {numberFormats: {...settings.numberFormats, style: ...}})`) since it's stored as a plain JS value, not a nested `Y.Map` (`mutations.ts`'s existing convention). Digits/Rounding/Trim are visually disabled (not hidden) when style isn't `"decimal"`, since `formatRational` ignores them for `"fraction"`/`"mixed"` — keeps the last-used decimal settings around instead of losing them when toggling styles back and forth. Verified live: switching style to `"fraction"` immediately re-rendered every node card's rates/limit/clock/machine-count AND the open Summary panel's table/cost list (e.g. `"0.5 machines"` → `"1/2 machines"`, `"Portable Miner: 0.5"` → `"Portable Miner: 1/2"`) with zero reload.

### Deviations from the spec / things flagged for later jobs

- **`CanvasNodeData.validityState` is left unused** (always `null`, exactly as Job 010 built it) — validity is computed locally in `RecipeNode.tsx` from `SolverResultContext` instead, for the async-timing reasons explained above. Not a regression; just not the literal mechanism the job's own framing suggested. A later job is free to remove or repurpose that slot.
- **The "no limit, no resolvable neighbor" Basic-mode fallback gets no red/orange highlight** — deliberately, per the mapping above. If a future job wants a third "undetermined" visual state, `computeValidity.ts`'s header names this as the gap.
- **"Current Outpost & Below" (the recursive scope variant) is not implemented** — only direct children of the current container, per the job file's own explicit "fine to leave for later" allowance. "Selected & Below" / "Selected + Connected" are likewise not implemented (never named as MVP-required).
- **`--mismatch`/`--mismatch-soft` (the orange highlight tokens) are a distinctly different hue from `--outpost`'s amber** (see `index.css`'s comment) but they're still both "orange-ish" — a real, flagged risk that a multi-outpost factory with validity issues could read as visually confusing (is that orange a mismatch, or just an outpost?). Worth a dedicated design pass in Phase 7 polish once real factories are being built daily.
- **The drag-to-connect gesture does not appear to support originating a NEW edge directly across a container boundary** (dragging from a node at one level onto an outpost card at another level did not create a connection in this job's testing) — boundary-crossing edges in this job's manual verification were created via the pre-existing "move a connected node into a container" gesture instead (its edges naturally become boundary-crossing). This is Job 011/013 territory, not something this job changed or debugged further — flagged here only because it's exactly the kind of thing Phase 5's multiplayer testing will also need a working gesture for.
- **A genuine duplicate-scheduler bug in `DevNodeTools.tsx`** (see above) was found and fixed as part of this job, even though `DevNodeTools.tsx` isn't nominally this job's file — flagged because it's a direct, unavoidable consequence of this job's own `SolverResultContext` addition (Job 018's `SolverDebugPanel` predates that context and had no way to know about it).
- **`apps/api`'s `DEFAULT_DATABASE_URL` (port 5432 vs. the actually-running container's 5434)** was left unchanged, for the same reason every job since 015 has given: a documented, machine-local workaround, not a repo misconfiguration. Every command needing `apps/api` in this job passed `DATABASE_URL` explicitly.
