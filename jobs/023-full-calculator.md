### The LP formulation, precisely

Full mode keeps Basic mode's overall shape (pin explicit limits via `nodeProfile.ts`'s unchanged `pinnedMachineCount`; Jacobi-style fixed-point relaxation over passes; fall back to 1 machine, `resolved: false`, for anything the fixed point never reaches) and replaces only the one thing Job 017's own handoff notes flagged as Basic-specific: `edgeGroups.ts`'s flat "divide by sibling count" stand-in, at every (node, part, direction) sibling group, with a real allocation solved as an LP.

**The LP, per splitter/merger group, per tier:** maximize the minimum share (equivalently: split a fixed `amount` as evenly as possible) subject to `sum(share_e) <= amount`, `0 <= share_e <= cap_e` (`cap_e = +infinity` when the sibling's other endpoint isn't resolved yet). This is the textbook "max-min fair" allocation problem, and it has a well-known closed-form/greedy solution — progressive **water-filling**: give every still-open candidate an equal share of what's left; permanently fix any candidate whose cap is below that round's equal share at exactly its cap; recompute the equal share over the shrunken remainder; repeat. `waterFill.ts`'s `waterFillTier` implements exactly this, with a genuine `while` loop (bounded by `candidates.length` rounds) that IS the LP's iteration loop for cancellation purposes — not a cosmetic wrapper around a closed-form formula computed in one shot.

**Two-tier priority is solved lexicographically, not jointly**: `waterFillGroup` water-fills the "top" tier first against the FULL amount; whatever "top" couldn't absorb (only possible when every top candidate is capped and those caps sum to less than the total) flows to "bottom", water-filled the same way against the remainder. An uncapped top-tier candidate absorbs everything, so bottom only ever sees genuine overflow — exactly "top drains first, bottom takes overflow."

**Pivot/tie-breaking rule (the determinism requirement, extended from Basic mode's own)**: identical in spirit to `basic.ts`'s pivot rule (a resolved node's implied rate, when several candidate parts have one, prefers the recipe's own `primaryPart`, else the alphabetically-first part with an implied value), PLUS the water-fill loop's own tie-breaking: every round saturates **all** currently-under-cap candidates simultaneously (Jacobi-style — never "saturate the smallest cap first, one at a time"), and every division is exact `Rational` division, so there is never a remainder to break a tie over. `candidates` are sorted by edge id before either tier's loop runs, purely so map/JSON iteration order is reproducible too — the arithmetic result itself provably cannot depend on input order. `fullDeterminism.test.ts` verifies this directly (shuffled/reversed node+edge arrays, byte-identical `JSON.stringify` output) for both an even-split-with-capacity fan-out and a two-tier priority splitter.

**Why a closed-form algorithm instead of a generic simplex tableau**: the specific LP each group needs solved (described above) has a well-known, exact, provably-optimal closed-form solution; implementing/testing a general-purpose exact-rational simplex (Bland's rule, phase-1/phase-2, degenerate-pivot handling) to solve a problem that already has a simpler exact answer would have added real risk for zero behavioral benefit. See `waterFill.ts`'s own header comment for the full reasoning — this is a documented, deliberate scope decision, not a shortcut around the "exact-rational LP" requirement (the underlying optimization problem being solved genuinely is the LP described above; the water-filling loop is genuinely iterative and genuinely interruptible mid-solve, which is what the cancellation acceptance criterion actually cares about).

### The genuinely uncertain design call — flagged prominently, per this job's own explicit invitation not to guess silently

**How is priority represented, given the snapshot has no dedicated splitter/merger node type?** I added a single new optional field, `SolverEdge.priorityTier?: "top" | "bottom"` (see above), rather than e.g. a node-level field, or a separate `prioritySplitters: {...}[]` array alongside `nodes`/`edges`. Reasoning: PLAN.md's Full row and this job's own scope note both describe priority in terms of the edges leaving/entering a splitter/merger point ("top drains first, bottom takes overflow" — a property of which OUTPUT/INPUT wins, i.e. of the edge), and every sibling-group computation in this package (`edgeGroups.ts` before this job, `full.ts`'s `buildSplitGroups` now) is already naturally keyed by `(node, part, direction)` groups of EDGES, not by a node-level record — so an edge-level field required zero new grouping machinery and slots directly into the existing shape.

**The one thing I'm NOT confident is the right long-term answer**, and where Job 024 should look hardest before locking in its own UI model: `priorityTier` is a single, direction-agnostic property of the edge. It's used identically whether that edge is being considered as one of its `fromNode`'s **splitter outputs** or as one of its `toNode`'s **merger inputs** (`full.ts`'s `buildSplitGroups` builds both an "outgoing" group owned by `fromNode` and an "incoming" group owned by `toNode` for every edge, and both read the same `edge.priorityTier`). In the common case — a priority splitter's output feeding a single consumer, not simultaneously acting as another node's merge input from multiple sources — this is a distinction without a difference. But if Job 024's real desktop-tool-equivalent UX wants a priority splitter's "top" output to matter independently of whether that SAME edge, viewed from its target's side, should also be "top" for a merge happening there, this field cannot express that (there's only one bit, not two). I did not attempt to guess at a two-bit (`splitterTier`/`mergerTier`) design because I have no reference UI to check the real desktop tool's actual priority-splitter semantics against in this environment (see the no-reference-data note below) — extending to two fields later is a compatible, non-breaking change if Job 024 finds it's actually needed.

**A second, related scope limitation, also worth Job 024 (or a future revisit) knowing about**: a sibling group's cap for edge `e` uses the OTHER endpoint's own TOTAL resolved rate for that part, not a recursively-computed "what that node's OWN splitter/merger group would actually route through THIS specific edge." This is always a correct (never-over-allocating) bound, but not always the TIGHTEST one when two splitter/merger points sit directly adjacent on the same part (e.g. a splitter feeding straight into a node that is simultaneously a merger for the same part from multiple sources). Every hand-derived benchmark in `full.golden.test.ts` uses a single splitter or merger point at a time — matching this job's acceptance criteria and Basic mode's own precedent of not attempting a fully general simultaneous-graph solve — where this bound is always exact. A fully general treatment would require solving every splitter/merger's allocation jointly (one graph-wide LP) rather than this module's per-group, pass-propagated approach; I judged that scope not to be required by this job's acceptance criteria (which ask for even-split and priority-tier behavior on hand-checkable graphs, not a fully general multi-commodity flow solver), and flagging it here rather than either silently shipping the gap or over-building beyond what's needed.

### Cancellation/progress — checkpoints and how Job 018's worker host should wire this up

Every checkpoint is a real point where genuinely-not-yet-done work would otherwise continue:
1. The top of every propagation pass (`propagateMachineCountsFull`'s outer `while` loop) — `phase: "propagate"`.
2. The top of every iteration of `computeGroupAllocations`'s loop over splitter/merger groups (one check per group, before that group's own water-fill runs) — same phase/pass, no `waterFill` field.
3. The top of every round of every `waterFillGroup`/`waterFillTier` call within a group — `waterFill: { tier, round, activeCount }` is set.
4. Once more, at the "finalize" pass (recomputing final edge shares over the fully-resolved counts) — `phase: "finalize"`.

On cancellation, `solveFull` returns (never throws) a defined result: `{ mode: "full", nodes: [], edges: [], summary: <zeros>, valid: false, warnings: ["solve cancelled"], cancelled: true }`. Internally this is implemented by throwing `SolveCancelledError` from the checkpoint and catching it once at `solveFull`'s own top level — an implementation detail, not something a caller needs to catch (the error class is exported only so a test/caller can assert on it if useful).

**How Job 018's worker host should wire this through `postMessage`** (this package has no worker/message-passing concept of its own, same boundary Job 017 established): extend `apps/web/src/workers/protocol.ts`'s `SolveRequestMessage` with an optional `requestId`-scoped cancel message (e.g. `{ type: "cancel", requestId }`) that the worker turns into `signal.aborted = true` on a per-request `{ aborted: boolean }` object passed as `options.signal` into `solve(snapshot, "full", gameData, { signal, onProgress })`; `onProgress` should `postMessage` a lightweight `{ type: "progress", requestId, info }` message back to the main thread at whatever cadence Job 018/024 finds acceptable (every call is cheap on the worker side, but `postMessage` itself is not free at high frequency — throttling belongs in the worker's own relay code, not in this package). Job 018's existing `Worker.terminate()` + pre-warmed-spare-worker backstop (its own Handoff notes: "`terminate()` remains the backstop either way") still works unchanged and unconditionally for Full mode too — this job's cooperative cancellation is a strictly faster, additional path for the common case where a `terminate()` round-trip would otherwise be needed, not a replacement for it.

- `full.ts` exports `propagateMachineCountsFull` (mirroring `basic.ts`'s already-exported `propagateMachineCounts`) beyond the job's literal `full.ts` wording — for testability/symmetry, not a scope change.
- The water-filling closed-form algorithm, used instead of a generic exact-rational simplex tableau, is the one deliberate methodological deviation from a literal reading of "formulate this as an exact-rational linear program" — see "Why a closed-form algorithm instead of a generic simplex tableau" above for the full reasoning. The underlying optimization problem being solved genuinely is the LP described; only the SOLVING METHOD is the closed-form equivalent rather than a general-purpose tableau method.
