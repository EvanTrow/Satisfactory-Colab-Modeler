## Scope

In scope:
- Real implementation of `apps/realtime` (currently a placeholder from Job 001): a Hocuspocus server with:
  - `onAuthenticate`: validates the short-lived ticket JWT (signature + TTL + `projectId` match), attaches `{ userId, role }` to the connection context.
  - `onLoadDocument` / `onStoreDocument`: wired to the persistence logic built in Job 015 (reuse that module rather than reimplementing load/append/compact).
  - Per-connection `readOnly` flag: `role === 'viewer'` connections must be genuinely read-only — writes from a viewer connection must be dropped server-side, not merely hidden in the client UI (this is explicitly called out as a required test in PLAN.md §9).
- `GET /api/realtime/ticket?projectId=…` in `apps/api` (authenticated via the session cookie from Job 005): resolves the caller's role from `project_members`/`projects.visibility`, returns a 60-second HS256 JWT `{ sub: userId, projectId, role, jti }`.
- Client wiring: `apps/web`'s Yjs provider switches from Job 015's debounced-REST transport to a live `@hocuspocus/provider` WebSocket connection, fetching a fresh ticket before connecting (and re-fetching on reconnect, since tickets expire in 60s — the client must request a ticket right before opening the socket, not cache one).
- Revocation: when `project_members` changes (e.g. a role downgrade or removal), affected sockets should be force-disconnected. Per PLAN.md, use "a Redis channel (or an in-process bus while single-instance)" — since this is presumably a single-instance deployment at this stage, an in-process event bus is sufficient; document the Redis upgrade path in a comment but don't build it now unless trivial. Also implement the belt-and-braces hourly role re-verification mentioned in PLAN.md §6.

Out of scope:
- Awareness/presence (cursors, avatars, selection) — Job 021.
- The integrity reducer pass — Job 022 (though `onStoreDocument`/`onLoadDocument` should be structured so Job 022 can slot the reducer in cleanly).
- Cross-instance Redis awareness extension — only the revocation-bus concept needs a documented upgrade path, not a real Redis integration, unless the deployment is already multi-instance (it isn't, per PLAN.md's "single container host").

## Deliverables

- `apps/api/src/routes/realtime.ts` — the ticket-issuance endpoint.
- `apps/realtime/src/server.ts` — the Hocuspocus server with `onAuthenticate`/`onLoadDocument`/`onStoreDocument`/readOnly wiring.

### The persistence-sharing architectural decision — `packages/doc-storage`

Went with option (a) from this job's own brief: promoted `docStorage.ts` **verbatim** (only its imports changed) from `apps/api/src/projects/docStorage.ts` into a new real workspace package, `packages/doc-storage` (`@scm/doc-storage`). It carries three files, not just the one:

- `src/db.ts` — the Kysely/Postgres connection setup, moved verbatim from `apps/api/src/db.ts` (same dotenv-loading trick, same `DEFAULT_DATABASE_URL`, same `closeDb`). Necessary because `onLoadDocument`/`onStoreDocument`/`onAuthenticate` all need a `db` to query, and there's no other shared home for one.
- `src/docStorage.ts` — the actual persistence module (load/append/compact/duplicate/versions), unchanged in substance from Job 015/016.
- `src/roles.ts` — `resolveRole` only (not `canEdit`/`canDelete`/`canDuplicate`, which are REST-route-specific and stayed in `apps/api/src/projects/roles.ts`). Needed because `onAuthenticate`'s mandatory re-check ("RE-CHECK the role against Postgres so revocations apply at connect time," PLAN.md §6) needs the exact same query the ticket route used to mint the ticket in the first place — one definition, not two that could drift.
- `src/index.ts` — barrel, with a long header comment spelling out this whole reasoning for whoever touches it next (read it first if you're wondering "why does the doc-storage package also have a `db.ts`/`roles.ts`").

**Why not duplicate `docStorage.ts` into `apps/realtime` instead?** Rejected explicitly — the load/append/compact algorithm is exactly the kind of logic PLAN.md §4 is precise about (snapshot+log merge order, the lossless-compaction guarantee, the "wholesale replace, not merge" restore semantics), and Job 022's integrity reducer is *also* going to need to run "on both client and server" per PLAN.md §5, meaning inside `apps/realtime` too — a second job needing the same kind of server-side reuse would have made a "just copy it" call look worse in hindsight. One shared package is the only way neither this job nor Job 022 has to remember to patch two places.

**`apps/api`'s own files barely changed as a result** — this was a deliberate goal, to minimize risk in an already-large refactor:
- `apps/api/src/db.ts` is now a **one-line re-export** (`export { closeDb, DATABASE_URL, db } from "@scm/doc-storage"`), so every existing `import { db } from "../db.js"` across `apps/api` (dozens of call sites) needed zero changes.
- `apps/api/src/projects/roles.ts` re-exports `resolveRole` from `@scm/doc-storage` the same way, keeping `canEdit`/`canDelete`/`canDuplicate` in place.
- `apps/api/src/projects/docRoutes.ts` and `store.ts` changed their one import line from `./docStorage.js` to `@scm/doc-storage`; nothing else in either file changed.
- `apps/api/src/projects/docStorage.ts`/`docStorage.test.ts` are **deleted**, not left behind as dead re-exports — the test file moved to `packages/doc-storage/src/docStorage.test.ts` verbatim (one import fixed: it used to import a `generateShortId` helper from `apps/api`'s own `short-id.ts`; since `packages/doc-storage` has no dependency on `apps/api`, that one call site now uses `crypto.randomUUID()` inline instead — a trivial, documented deviation, not a loss of test coverage). Test counts: `apps/api` 92 → 68 (24 moved out), `packages/doc-storage` 0 → 24 (moved in) — net repo-wide test count unchanged by the move itself.

**A real, non-obvious deviation from the other `packages/*` convention, worth knowing before touching this package**: every other `packages/*` member ships `"main"`/`"types"`/`"exports"` pointing at `./src/index.ts` (Job 001's "JIT internal package" convention — zero build step for `apps/web`'s Vite/esbuild). `packages/doc-storage` does **not** — its `package.json` points at `./dist/index.js`/`./dist/index.d.ts`, and its `tsconfig.json` uses `NodeNext` module resolution (not `Bundler`, like every sibling package). Two reasons, both load-bearing:

1. **Resolution-mode mismatch.** `apps/api`/`apps/realtime` both use `NodeNext`, which requires explicit `.js` extensions on every relative import — including inside a *dependency's* source, if that dependency's own `main` points at raw `.ts`. A JIT `packages/doc-storage` (main → `src/index.ts`) would have hit the exact `TS2835` break `apps/api/src/projects/store.ts`'s own `GAME_DATA_VERSION` comment already documents for `@scm/gamedata` (worked around there by *not* importing it and duplicating a constant instead — not an option here, since `docStorage.ts` is substantial, not a one-liner). Since `packages/doc-storage` has **no browser consumer at all** — only `apps/api`/`apps/realtime` import it, both already `NodeNext` — matching their resolution mode outright (internal relative imports written *with* `.js` extensions, same as every file in those two apps) sidesteps the mismatch entirely instead of working around it.
2. **The real, empirically-confirmed one: plain `node dist/index.js` cannot execute a JIT package with internal relative imports.** Job 001's own scaffold notes flagged this as a real risk ("a plain `tsc`-built `apps/api` run via `node dist/index.js` cannot execute an imported package whose `main` points at a `.ts` file — only `tsx`/Vite/esbuild-based runners can") and left it unresolved since nothing exercised it yet. This job does. I initially assumed it was already fine, because `apps/api`'s existing single-file `@scm/db` (main → `schema.ts`, **zero internal relative imports**) genuinely does work fine under plain `node dist/index.js` — Node 26's native TypeScript type-stripping loads a lone `.ts` file with no problem. But `packages/doc-storage/src/index.ts` has *internal* relative imports (`./db.js`, `./docStorage.js`, `./roles.js`) — and Node's type-stripping does **not** rewrite a `"./db.js"` specifier to resolve against an on-disk `db.ts` file the way `tsc`'s `NodeNext` convention (and `tsx`/Vite/esbuild) assume; it only strips types from a file *directly* loaded by an already-`.ts`-aware specifier. Confirmed by literally running `node apps/realtime/dist/index.js` against the original JIT (`main: "./src/index.ts"`) setup: `Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../packages/doc-storage/src/db.js'`. Switching `main`/`types`/`exports` to the already-working `tsc -p tsconfig.build.json` output (`dist/`, which — because it's genuinely compiled — has real `.js` files at every relative-import path) fixed it immediately; re-verified both `apps/api/dist/index.js` and `apps/realtime/dist/index.js` running under plain `node` end to end against the real Postgres instance.

**This introduces a real build-order dependency that didn't exist before** (`packages/doc-storage` must be built — not just typechecked — before `apps/api`/`apps/realtime` can even *resolve* it, in dev **or** prod, since `tsx watch` also follows `package.json#main`). Two `turbo.json` changes close that gap so it's never a manual step: the `dev` task gained `"dependsOn": ["^build"]` (previously only `build`/`test` depended on `^build`; `dev` had none) and the `typecheck` task gained `"^build"` alongside its existing `"^typecheck"` (a downstream package's own `typecheck` script never emits a `dist/`, so depending on `^typecheck` alone doesn't guarantee the `.d.ts` a consumer resolves against actually exists). Verified: fresh `pnpm -r build`, `pnpm -r typecheck`, `pnpm -r test` (via `turbo`) all pass with no manual "build doc-storage first" step; `pnpm --filter @scm/api dev`/`pnpm --filter @scm/realtime dev` (via `turbo run dev`) also correctly build `packages/doc-storage` first.

### Ticket format/lifecycle

`GET /api/realtime/ticket?projectId=…` — `apps/api/src/routes/realtime.ts` (the literal path this job's Deliverables section names), gated by `{ preHandler: fastify.authenticate }`, resolving role via the same `resolveRole`/`findActiveProjectById` pair every other project route uses (404 for a non-member or soft-deleted project — never leaks existence). Mints via `apps/api/src/realtime/ticket.ts`'s `mintRealtimeTicket`, using `jsonwebtoken`'s `sign` with `algorithm: "HS256"`, `expiresIn: 60`. Payload is exactly PLAN.md §6's `{ sub: userId, projectId, role, jti }` (`jti` a random UUID — included for shape-fidelity with PLAN.md's spec; not independently used for revocation, since a 60-second TTL is already short enough that per-ticket revocation would add real complexity for negligible benefit — flagged here in case a future job disagrees and wants a jti denylist).

Secret: `REALTIME_TICKET_SECRET`, read independently by `apps/api/src/realtime/config.ts` and `apps/realtime/src/config.ts` (two separate processes, two separate `getRealtimeTicketSecret()`-equivalent functions with matching dev-only fallback strings — **not** a shared module; see "the smaller sharing decision" below). Added to `infra/.env.example` alongside two more Job 020 vars (`REALTIME_INTERNAL_SECRET`, `REALTIME_INTERNAL_URL`) plus two port vars (`REALTIME_PORT`/`REALTIME_INTERNAL_PORT`, defaulted in code so listing them is purely for discoverability).

`apps/realtime/src/ticket.ts`'s `verifyRealtimeTicket(token, expectedProjectId)` does the three checks PLAN.md §6 names by name: `jwt.verify` (signature + `exp`/TTL — throws `TokenExpiredError`/`JsonWebTokenError` on failure, both caught and normalized into a `TicketError`), payload shape validation, and `payload.projectId === expectedProjectId` (rejects a still-valid ticket for project A being replayed against project B within the same 60s window). Called from `onAuthenticate` in `server.ts`.

**The smaller "don't share" decision, distinct from the `packages/doc-storage` one above**: the ticket *type*/*mint*/*verify* logic is duplicated (not shared) between `apps/api/src/realtime/ticket.ts` (mint) and `apps/realtime/src/ticket.ts` (verify) — each is ~30-50 lines, genuinely process-local (mint only ever needs to happen in `apps/api`, verify only in `apps/realtime`), and doesn't carry the same "will drift into two different bugs" risk `docStorage.ts` did — there's no shared *algorithm* here, just a shared *shape* and a shared *secret*, both cheap to keep in sync by convention (documented in both files' header comments) rather than by a shared import. Matches this repo's existing precedent (`apps/api/src/projects/store.ts`'s duplicated `GAME_DATA_VERSION` constant, documented the same way).

### The Hocuspocus server — `apps/realtime/src/server.ts`

`createHocuspocusServer()` builds a `@hocuspocus/server` `Server<HocuspocusContext>` (`HocuspocusContext = { userId, role }`, what `onAuthenticate` attaches to every connection) and returns `{ server, stop }` — `stop()` is the real teardown (stops the hourly-reverify timer, closes the internal webhook listener, then `server.destroy()`), used by `index.ts` on `SIGINT`/`SIGTERM` and by every test.

- **`onAuthenticate`**: `verifyRealtimeTicket(token, documentName)` (documentName **is** the projectId — see "the URL doesn't literally carry `/collab/<projectId>`" below), then `resolveRole(documentName, ticket.sub)` — the mandatory Postgres re-check. `null` → throws (`TicketError`), which Hocuspocus turns into a `permission-denied` message and refuses the connection. `"viewer"` → `connectionConfig.readOnly = true` (mutating the object Hocuspocus passed in — confirmed by reading `@hocuspocus/server`'s own compiled source that this is exactly how the library expects an extension to signal read-only, not a documented-but-unverified guess). Returns `{ userId: ticket.sub, role: currentRole }`, which Hocuspocus's own hook-chaining shallow-merges into the connection's context (also confirmed against source, not assumed).
- **`onLoadDocument`**: `return loadProjectDocUpdate(documentName)` — a `Uint8Array`, which Hocuspocus `Y.applyUpdate`s into the `Document` it already created (confirmed against source: an extension may return either a `Y.Doc` or a `Uint8Array` from this hook and Hocuspocus handles both). Same function `GET /api/projects/:id/doc` calls — genuinely one code path for "how does a client's initial content get assembled," REST or WebSocket.
- **`onStoreDocument`**: **not** a naive "always persist the whole document" — that would have quietly regressed PLAN.md §4's "Write = append one row (no rewriting the document)" / O(change) property Job 015/016 built and tested for the REST transport, since Hocuspocus's `onStoreDocument` payload only ever exposes the *whole current* `Document`, not a pre-computed diff. Fixed with a module-level `Map<documentName, Uint8Array>` (`lastStoredStateVectorByDocument`) tracking each loaded document's state vector as of its last successful store, seeded right after `onLoadDocument` finishes (in `afterLoadDocument`, so the seed reflects "persisted content merged in, zero edits yet" — the correct diff base) and advanced after every store; cleared in `afterUnloadDocument` so a long-running process doesn't leak one entry per project ever opened. `appendUpdate(documentName, diff, actorUserId)` — `actorUserId` from `lastContext.userId` (the connection whose edit triggered this store), `null` if there's no context (a server-internal write with no connection behind it — not exercised by anything yet, but the type already allows it, matching `appendUpdate`'s existing signature). A zero-length diff (Hocuspocus's debounce can coalesce a store trigger with nothing new since the last one) is a no-op, not an empty row.
- **`debounce`/`maxDebounce`**: passed through from `config.storeDebounceMs`/`storeMaxDebounceMs` (env-overridable, defaulting to Hocuspocus's own built-in 2000ms/10000ms) rather than hardcoded — purely so `server.test.ts` doesn't have to wait multiple real seconds per persistence-touching test; production behavior is unchanged from Hocuspocus's own defaults unless someone sets the env vars.

**Genuine, verified server-side readOnly enforcement** (the explicit PLAN.md §9 requirement): confirmed by reading `@hocuspocus/server`'s compiled `MessageReceiver.readSyncMessage` — for `messageYjsSyncStep2`/`messageYjsUpdate`, if `connection?.readOnly`, the inbound update is **never** passed to `readUpdate`/applied to the document at all; the server just acks `writeSyncStatus(false)` back. This repo's code doesn't reimplement or "trust" this — it only sets the flag Hocuspocus already enforces internally, and `server.test.ts`'s viewer test asserts the *outcome* (persisted state unchanged), not the mechanism.

### `apps/realtime`'s ports and internal HTTP server

Two listeners, not one:
- **`REALTIME_PORT` (default `1234`)** — the real Hocuspocus `Server` (WebSocket + its own trivial built-in "Welcome to Hocuspocus!" HTTP page on the same port). Matches Hocuspocus's own conventional default.
- **`REALTIME_INTERNAL_PORT` (default `1235`)** — a **separate, plain `node:http` server** (`apps/realtime/src/internalServer.ts`), serving `POST /internal/membership-changed` (checks `x-internal-secret`, calls into the revocation controller) and `GET /internal/health`. Never exposed publicly in a real deployment — only `apps/api` should reach it (firewall/reverse-proxy rule in production; unrestricted in dev, same trust boundary as the rest of this "single container host").

**Why not Hocuspocus's own `onRequest` extension hook, which shares the WS port?** Investigated and rejected — a real, confirmed library behavior, not a guess. Read `@hocuspocus/server`'s compiled `Server.requestHandler`: after the `onRequest` hook chain resolves, it **unconditionally** does `response.writeHead(200,...).end("Welcome to Hocuspocus!")`, with no check for whether an extension already wrote/ended the response. An `onRequest` handler that fully answers a request (as the webhook needs to) would have Hocuspocus immediately try to write a *second* response on top of it, throwing `ERR_HTTP_HEADERS_SENT` as an unhandled rejection on every single webhook call. A second listener on its own port avoids fighting a library internal that isn't designed for "fully handle this request yourself," at the cost of one more port to configure.

### Revocation mechanism — the actual answer to "in-process bus, but apps/api and apps/realtime are separate processes"

The job's own Notes section flagged this precisely: PLAN.md §6 says "an in-process event bus while single-instance," but `apps/api` and `apps/realtime` are two separate Node processes even in this single-instance deployment (co-deployed, not co-located). The mechanism has two legs, documented at length in both files' own header comments:

1. **Cross-process (the part that *isn't* literally in-process)**: `apps/api/src/realtime/notify.ts`'s `notifyRealtimeMembershipChanged(projectId, userId?)` — a small authenticated `fetch` POST to `apps/realtime`'s internal webhook (above), called from the two new member-management routes (see below) after a role change/removal actually commits. Fire-and-forget from the route's perspective (`.catch()`'d, never awaited inline) — a slow/unreachable `apps/realtime` must never make a REST call to `apps/api` slow or fail. 2-second `AbortController` timeout.
2. **In-process (the part that genuinely is)**: `apps/realtime/src/revocation.ts` — `reconcileConnection`/`reconcileProject`/`reconcileAll`, operating directly on the live `Hocuspocus` instance's `documents: Map<string, Document>` and each `Document.getConnections()`. `reconcileConnection` re-resolves the connection's role via `resolveRole` (the same shared function `onAuthenticate` uses) and closes the connection (`connection.close({code: 4001, reason})`) on **any** mismatch — not just "revoked to null," a role *change* too (editor→viewer force-disconnects, same as removal), matching this job's own acceptance-criteria wording ("force-disconnects that member's active session," not "silently flips it to read-only in place"). The client's own reconnect (fresh ticket, correct role) picks it back up.

**Belt-and-braces hourly re-verification**: `startRevocationController` also starts a `setInterval` (`config.reverifyIntervalMs`, default 1 hour, `.unref()`'d so it never keeps the process alive on its own) calling `reconcileAll` — sweeps *every* live connection on *every* loaded document, independent of whether the push notification above ever fired. This is the actual backstop for "apps/realtime was down when the membership change happened" or "something bypassed `apps/api`'s routes and wrote to `project_members` directly" — verified with a dedicated test using a short-circuited interval (150ms) on a second, isolated server instance, changing a role in Postgres directly with **no** webhook call at all.

**Redis upgrade path** (documented, not built — per the job's own "don't build this now unless trivial" guidance): `notify.ts`'s header comment spells out that going multi-instance means replacing the single HTTP POST with a `PUBLISH` to a Redis channel every `apps/realtime` instance subscribes to, since a single POST to "the" realtime service stops being correct once there's more than one instance holding sockets. Nothing about the call sites (`memberRoutes.ts`) would need to change — only what's inside `notifyRealtimeMembershipChanged`.

**Minimal enabling infrastructure this job added, not originally scoped by name**: there was **no existing route anywhere that could change `project_members` after creation** — `createProject`/`duplicateProject` only ever insert an `owner` row; the "sharing" feature (invites, member management UI) is explicitly Job 022's scope per `jobs/INDEX.md`. Without *some* way to actually change a role or remove a member through the running app, this job's own acceptance criterion ("a project owner revoking a member's access force-disconnects...") would be untestable except by writing directly to Postgres, which felt like cheating the spirit of "verify it end to end." Added `apps/api/src/projects/memberRoutes.ts` — deliberately bare-bones, owner-only: `GET /api/projects/:id/members` (list), `PATCH .../members/:userId` (role → `editor`/`viewer` only, not `owner` — changing/removing the actual owner is rejected with 400), `DELETE .../members/:userId`. Both mutating routes call `notifyRealtimeMembershipChanged` after committing. **Job 022 should treat this as a starting point to extend (invite tokens, email, pending-invite state, a real UI), not as the finished sharing feature** — there's no invite flow, no way to *add* a member other than a direct DB insert (which is exactly how both this job's own tests and its manual verification added the QA editor/viewer, matching every prior job's own precedent for minting test users).

### Client transport switch — `apps/web/src/canvas/persistence/`

`useProjectDocument.ts` was **rewritten** (not incrementally patched) — read its own header comment first, it inventories exactly what changed line by line. The short version:

- **Gone entirely**: `updateQueue.ts`'s debounced push queue (`createUpdateQueue`/`UpdateQueue`), the `doc.on('update', ...)` listener that fed it, and the `RECONCILE_ORIGIN` sentinel that existed purely so that hand-rolled listener didn't mistake "bytes the server just sent" for "a local edit worth pushing back." None of that origin bookkeeping is needed with a real provider: `HocuspocusProvider` (like `y-indexeddb`) already tags its own applied updates with its own origin internally — a well-tested library behavior, not something this job's code has to reimplement — so it and `y-indexeddb` coexist correctly on the same `Y.Doc` with zero extra code here.
- **Gone**: `docApi.ts`'s `fetchProjectDoc`/`pushProjectDocUpdate` (the REST load/push wrappers) — deleted from the client. **The server routes they called are deliberately left in place, fully tested, untouched** (`GET`/`POST /api/projects/:id/doc` in `apps/api/src/projects/docRoutes.ts`) — this job's own Notes section left "stays as fallback/dead code or gets removed" as a judgement call; decision: keep the (cheap-to-keep, still-correct, possibly useful for future debugging/non-realtime consumers) server routes, remove only the now-genuinely-unused client wrappers around them. `updateQueue.ts` itself was trimmed to just the `SaveStatus` type (kept — see below) with its `createUpdateQueue` implementation and 11-test suite (`updateQueue.test.ts`) deleted, since nothing calls it anymore.
- **The hydration-ordering invariant Job 015/016 were careful about — preserved, but its *shape* changed, not just its wording.** The old invariant was "the push listener must attach before the root-container-creation mutation, or nothing would ever push a brand-new project's very first `addContainer`." With Hocuspocus, there's no separate listener to order relative to anything: `HocuspocusProvider` watches *every* mutation to `doc` for as long as it exists (constructed before hydration ever runs), and Yjs's sync protocol is a bidirectional state-vector diff, not "whatever happened after a listener was wired" — so a root container created any time relative to the provider's own connect/sync lifecycle still syncs correctly. The invariant that *does* still matter, unchanged in substance, is `hasRootContainer(doc)` gating whether `finishHydration` calls `addContainer` at all — that's what stops two clients (or one client across two reloads) from minting duplicate root containers, and it's still exactly what `load()`'s fast-path check does.
- **IndexedDB caching (Job 016) is completely untouched in mechanism** — `IndexeddbPersistence` still attaches first, `hasRootContainer` still decides the fast path, `finishHydration` still runs immediately when the cache already has content. The only thing that changed is what happens *after* the fast path (or instead of it, for a first-ever visit): the old REST fetch became waiting on the provider's first `onSynced({state: true})` event, wired through a `Promise` (`firstSync`) that resolves on sync and rejects on `onAuthenticationFailed` — awaited only when `!cameFromCache` (mirrors Job 015's "no cache, network failed → surface the error state" exactly; `cameFromCache === true` swallows a background auth failure the same non-fatal way Job 015/016 swallowed a background fetch failure).
- **`SaveStatus` (the type, and `SaveStatusIndicator.tsx`'s rendering of it) is unchanged** — only what feeds it changed. `computeSaveStatus(wsStatus, unsyncedChanges)` derives the same `"saved" | "saving" | "offline"` union from `HocuspocusProvider`'s own `onStatus`/`onUnsyncedChanges` callbacks: `"offline"` whenever the WebSocket isn't actually `"connected"` (covers connecting *and* disconnected — the provider's own built-in reconnect-with-a-fresh-ticket is what makes "will auto-retry" true, replacing `updateQueue.ts`'s old hand-rolled retry loop), `"saving"` while connected with `unsyncedChanges > 0`, `"saved"` otherwise.
- **Ticket fetch-then-connect**: `apps/web/src/canvas/persistence/realtimeTicket.ts`'s `fetchRealtimeTicket(projectId)` is passed as `HocuspocusProvider`'s `token` option in its **function** form (`() => Promise<string>`), not a plain string — confirmed against `@hocuspocus/provider`'s source that this form is called fresh on *every* connection attempt (initial connect and every reconnect), which is exactly the "never cache a ticket, fetch one right before every connect" requirement; a plain string would only ever be fetched once, at provider-construction time.
- **Every role — including `"viewer"` — now gets a live provider connection**, not just owner/editor. Deliberate improvement, not an oversight: a viewer should still *see* other collaborators' live edits even though their own writes can't persist; the pre-020 REST transport never had live sync for anyone, so this distinction didn't exist to make yet. What a viewer's connection can't do is now a genuine **server-side** guarantee (readOnly, above) rather than "the client didn't bother wiring a push listener" (Job 015/016's own documented gap, now closed for real).

**PLAN.md §6's literal `wss://…/collab/<projectId>?ticket=<jwt>` URL shape — a documented, deliberate deviation**: `@hocuspocus/provider`/`@hocuspocus/server`'s actual protocol carries the document name (`name: projectId` in the provider config) as an in-band field of the Yjs sync message itself, not as a URL path segment — confirmed against both packages' source. So the real connection URL is a single fixed origin (`getRealtimeWsUrl()`, defaulting to same-origin `/collab` — proxied by `apps/web/vite.config.ts`'s new `ws: true` proxy entry to `apps/realtime` in dev, matching the same-origin shape a real reverse-proxied deployment would have) with a different `name` per project, not a different URL path per project. The ticket travels via the provider's own `token` mechanism (an authenticated app-level message sent right after the WebSocket opens), not a `?ticket=` query string — the `token` option's function form is what makes "fetch fresh right before every connect/reconnect" possible at all; a query-string ticket baked into a static `url` string couldn't be refreshed per-attempt the same way. Functionally equivalent security (still a short-lived signed ticket, still verified in `onAuthenticate` before anything else happens), different wire shape than PLAN.md's illustrative sketch.

### Viewer read-only — the explicitly-required test

`apps/realtime/src/server.test.ts`'s `"viewer read-only enforcement"` suite is the literal PLAN.md §9 test: a raw `@hocuspocus/provider` connection (no client UI code touched at all) authenticated with a genuine viewer-role ticket, writing to the document, and asserting via `loadProjectDocUpdate` (the same function the server itself uses to answer both `onLoadDocument` and the REST `GET .../doc` route) that the **persisted** document is unchanged — not that the client-side doc *looks* unchanged, which would only prove the client's own copy didn't merge back a rejected write, not that the server ever rejected it. A real "owner baseline" write establishes what "unchanged" is being compared against, so an empty/broken load path can't accidentally pass the assertion. `viewerProvider.authorizedScope === "readonly"` is also asserted, confirming the client-visible signal Hocuspocus sends back matches the server-side enforcement.

- **A real, documented gap in version restore while collaborators are live-connected** — see `useProjectDocument.ts`'s `reloadAfterRestore` doc comment: Hocuspocus's `onLoadDocument` only runs once per document *load*, not once per *connection*. If `apps/realtime`'s in-process `Document` for a project is still loaded (any connection open, from anyone), a REST-triggered version restore's Postgres-level replace won't be reflected by that in-memory `Document` until every connection closes and it naturally unloads. In the common case (the restoring user is the only connection, or restores happen after everyone else has left) this is invisible; with active collaborators, it's a real, currently-unhandled edge case. Out of scope for this job (the task briefing explicitly framed version history as "unrelated to live sync... untouched by this job"), but worth Job 022 knowing about, since a fix would likely mean the restore route also notifying `apps/realtime` (reusing the same internal-webhook infrastructure this job built) to force-disconnect/reload that specific document.
- **The integrity reducer (Job 022) has a clean slot**: `onLoadDocument`/`onStoreDocument` in `server.ts` are two small, focused functions with nothing else jammed into them — a reducer pass would slot in as, e.g., a transaction run inside `onLoadDocument` right after applying the loaded bytes (server-side "repair on load," mirroring PLAN.md §5's "run after every transaction... on both client and server") without restructuring anything already here.
