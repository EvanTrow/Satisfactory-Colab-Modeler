### ★★★ How PLAN.md §10.3 was resolved — read this before touching blueprints again ★★★

**Decision: the copy count participates in the SAME joint solve as every other node — not a post-multiply.** This is the more conservative/correct reading PLAN.md's own phrasing leans toward ("the blueprint's calculated value is how many copies to build" — an _output_ of solving), and it's what got built, concretely:

A blueprint container is represented, inside the solver's flattened graph, as ONE synthetic `SolverNode` (id `bp:<containerId>`) whose **machine count IS the copy count**. That node is injected into the exact same `SolverSnapshot` every other recipe node lives in, and resolved by the **completely unmodified** `basic.ts`/`full.ts` fixed-point propagation — the copy count comes out of `machineCountForTargetRate`, the identical function every ordinary unpinned node's machine count already comes from, triggered by whichever real neighbor's demand crosses the blueprint's boundary. Once resolved, the compound's own rate propagates FORWARD/BACKWARD to further unresolved nodes in the SAME pass-propagation loop, exactly as a real node's resolved rate would — this is what makes it genuinely joint rather than "solve in isolation, then multiply in": a downstream node three hops past the blueprint's boundary resolves from the compound's rate in the very same fixed-point loop, with no special-casing anywhere in `packages/solver`.

**The one `packages/solver` change this required** (a "Done" package, per Jobs 017/023's precedent for small, additive, prominently-flagged extensions — Job 023's `priorityTier` is the closest analogue): a new optional field, `SolverNode.blueprintCopyBasis?: { perCopyRates: Record<partName,string>; perCopyPowerMW: number }` (`packages/solver/src/snapshot.ts`), and `nodeProfile.ts`'s new `buildBlueprintCompoundProfile` (dispatched from the top of `buildNodeProfile` when the field is set) — it builds a `NodeProfile` with a **fully-valid but synthetic `Recipe`** object (all fields real, `parts` = the per-copy rates table) so the compound node is indistinguishable, to every OTHER module, from an ordinary recipe node. **`basic.ts`/`full.ts`/`manual.ts`/`summary.ts`/`nodeResult.ts`/`edgeValidation.ts` needed ZERO changes** — confirmed via `git diff --stat -- packages/solver/src/basic.ts packages/solver/src/full.ts packages/solver/src/manual.ts packages/solver/src/summary.ts packages/solver/src/nodeResult.ts packages/solver/src/edgeValidation.ts` (empty). The only other solver-side addition is `nodeProfile.ts`'s `syntheticPowerAtOneUnit` field + a two-line `nodePower()` branch, so a compound's power scales linearly with copies without ever touching the real-machine overclock-curve formula (keeping the exact-rational-rates/float-power boundary exactly where Job 002/017 drew it).

**Why this is a genuine joint-solve variable, not dressed-up post-multiplication**: `Container.copiesLimit` (when set) is encoded as a literal `SolverNode.limit`/`"machines"` **pin** on the compound — the identical pin-vs-propagate mechanism every other node's `limit` field already uses. When it's `null` (the normal case — PLAN.md is explicit that copies is _computed_, never itself user-set), the compound is genuinely **unpinned**, so its machine count is _solved for_, exactly like any other unconstrained recipe node whose count comes from a resolved neighbor. There is no separate "blueprint solving pass" bolted onto the side — one `solve()` call resolves the compound alongside everything else, in the same fixed-point loop, and Full mode's water-filling/priority-tier logic applies to a compound's boundary ports exactly as it would to a real node's sibling edges (proven directly in `packages/solver/src/blueprint.test.ts`'s Full-mode test).

**Where the per-copy rates actually come from** (this is the piece that genuinely needed new, container-aware code, and it lives entirely in `apps/web`, never in `packages/solver`): `apps/web/src/workers/blueprintCollapse.ts` solves the blueprint's own internal subgraph **once**, in isolation, via an ordinary `solve()` call using whichever internal node has the user-placed "defining" limit exactly as authored — this needs **no new solver capability**, it's precisely what solving that container's contents already produces. The result's `SolveSummary.perPart` balance (`unused`/`unmade` — the same made/used/unmade/unused fields the summary panel already shows) is read directly for the compound's aggregate per-part rate, rather than any individual boundary-crossing edge's own `EdgeSolveResult.rate`. **This detour around edge-level rates is deliberate, not incidental** — a boundary-crossing edge's rate can NEVER be read from the one-copy sub-solve at all: `edgeValidation.ts`'s `validateEdge` unconditionally reports an edge whose other endpoint has no profile as invalid/zero, and the external endpoint genuinely has no profile inside a solve of just the internal subgraph. The summary's mass-balance is edge-independent (a pure per-node aggregate — see `summary.ts`'s own header), so it sidesteps that trap entirely and is _exact_ for a single level of blueprint nesting: at most one of `unused`/`unmade` is ever nonzero for a given part (by `computeSummary`'s own `max(0,...)` definition), so the signed net is always unambiguous. Crossing edges ARE still included in the one-copy sub-snapshot (for a different, necessary reason — so an internal node with both an internal sibling AND a crossing sibling of the same part still divides its production across all of them correctly).

**Container-awareness deliberately never reaches `packages/solver`.** Exactly the same architectural line Job 018 drew for outposts generally ("an outpost container is a UI/rendering concept only, never structural to the real solved graph") and Job 024 drew for the Splurger node type ("erase the unrepresentable thing before the snapshot reaches the solver") — `blueprintCollapse.ts` is the container-aware glue, structurally identical in spirit to Job 024's `splurgerPassthrough.ts`, generalized from rewriting ONE routing node to collapsing a whole SUBGRAPH: `collapseBlueprints()` runs _before_ the whole-document snapshot reaches `solve()`, replacing a blueprint's internal nodes/edges with the compound node + boundary-crossing edges rewritten to point at it (keeping their REAL `EdgeRecord` ids — so validity highlighting resolves correctly, unlike Job 024's own documented Splurger gap where the synthetic edge id never matched a real one); `expandBlueprintResults()` runs _after_ the result comes back, reinstating each real internal node/edge under its own id with `machineCount`/`partRates`/`power`/`rate` all multiplied by the solved copy count, so a user who drills into the blueprint sees their OWN actual, correctly-scaled values — confirmed exact and internally consistent live (see Verification below).

**`Container.copiesLimit`'s actual semantics** (the job file flagged this as needing a fresh check, since Job 007 left it typed loosely with no concrete meaning pinned down): `packages/ydoc/src/schema.ts` already carries a comment nothing in this repo's Handoff notes had surfaced before — `// Blueprint containers only: caps how many instances may be placed.` This settled it directly: `copiesLimit` is an optional **ceiling**, not the "defining limit" (which is always an ordinary `NodeRecord.limit` on some node _inside_ the blueprint, per PLAN.md's own wording). Implemented as the hard pin described above; a computed demand exceeding the cap correctly surfaces as a rate mismatch on the boundary edge, exactly like any other over-constrained pinned node already does — confirmed live (see Verification).

**Known limitations, flagged rather than papered over:**

1. **Nested blueprints (a blueprint inside a blueprint, any depth) are not collapsed at all.** `blueprintCollapse.ts`'s `isTopLevelBlueprint` detects this (walks both the ancestor chain and the descendant subtree) and skips BOTH containers, leaving their internal nodes flowing through the outer snapshot exactly as an ordinary outpost's would — never silently wrong, just not the joint-solve treatment. A fully general recursive treatment (solve innermost-out) was judged out of scope for this job; the mechanism here should generalize directly if a later job wants it (recurse `collapseBlueprints` bottom-up before the outer pass), but that wasn't attempted or tested.
2. **None/Manual mode never collapse a blueprint at all** (`collapseBlueprints` early-returns unless `mode` is `"basic"`/`"full"`) — neither mode has an "infer a value from the graph" concept in the first place (PLAN.md §2's table), so there's no copy count to compute; a blueprint's internal nodes render/solve exactly like a plain outpost's would in either mode. This is a deliberate scope decision, not an oversight — the job file's own wording flagged Manual as "if applicable to its semantics," and it isn't.
3. **The one-copy sub-solve happens synchronously on the main thread**, not inside the Web Worker Job 018 built — a deliberate, bounded deviation from that job's "all solving happens off the main thread" architecture, justified by: (a) it's bounded by a single blueprint's OWN size, not the whole document; (b) `@scm/gamedata`'s runtime (the actual thing Job 018 was keeping off the main bundle) is _already_ imported directly by several main-thread files as of Job 010/019 (`RecipeNode.tsx`, `RecipeChooser.tsx`, `SummaryPanel.tsx`, `recipeNodeMath.ts`, `filters.ts`, `assets/icons.ts` — confirmed via `grep -rl 'from "@scm/gamedata"' apps/web/src`), so this doesn't introduce the bundle-size regression it would have if Job 018's original assumption still held. If a future job pushes blueprint sizes far beyond PLAN.md §2's "tens to low hundreds" scale, moving this into the worker alongside the outer solve is the natural fix — not attempted here.
4. **`copiesLimit`'s cap is a hard pin, not a "soft maximum" with its own solver semantics** — if demand needs more copies than the cap allows, the result is a correctly-reported rate mismatch (an invalid boundary edge), not an automatically-clamped-with-a-warning value. This mirrors how every other over-constrained pin in this codebase already behaves; inventing a distinct "soft cap" mechanism was judged unnecessary scope.

### A real bug found and fixed during manual browser verification

`BlueprintNode.tsx`'s copies-limit `<input>` sits inside the card's root `<div onDoubleClick={open}>` (the same drill-in gesture `OutpostNode.tsx` uses). A double/triple-click on the input (e.g. to select its text before retyping) bubbles the `dblclick` event straight to that handler and navigates INTO the blueprint mid-edit instead of selecting text — reproduced live via a triple-click during manual testing. Fixed with a one-line `onDoubleClick={(e) => e.stopPropagation()}` on the input itself. `RecipeNode.tsx`'s own limit/clock fields never needed this because that card has no double-click-to-navigate gesture at all.

- **Blueprint creation is conversion-only** (an existing outpost's context menu → "Convert to blueprint"), matching the job file's own wording exactly ("an outpost can be marked/converted to `kind: 'blueprint'`") — no separate "+ New Blueprint" Recipe Chooser entry point was added, unlike Job 013's "+ New Outpost" precedent.
