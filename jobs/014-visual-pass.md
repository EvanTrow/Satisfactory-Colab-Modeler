### Ferrumium characterization (via live browser inspection, not just the marketing page)

Visited https://ferrumium.com, used "Try without registering" to reach the real planner UI (not just the marketing hero), and read computed styles directly off its live DOM (`getComputedStyle`) rather than eyeballing screenshots — exact measured values:
- Canvas background: `#eae5db` (warm cream). Node card body: `#f0ebe0`. Node header: `#2f4f4f` (a fixed dark slate-teal — not theme-dependent; used as-is regardless of the card body being light or dark, which is *why* it's fixed rather than swapped in this app's own `.dark` block too — see below).
- Card: `border-radius: 8px` (`rounded-lg`), `border: 2px solid rgba(0,0,0,.25)`.
- Icon badges inside a card: small rounded (`5px`) dark chips with a subtle inset shadow, white icon/text on top.
- Font: Tailwind's own default `font-sans` stack (`ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, ...`) — Ferrumium uses this unmodified, so no custom `--font-sans` override was needed here either.
- Accent color measured off its "Sign Up" button: `#da7756` (a coral/orange). **Deliberately not adopted** — this app keeps the indigo accent already established across Jobs 008-013 for primary actions/selection, and amber for outposts (Job 013). Copying Ferrumium's literal accent hue would have collided with the outpost-amber semantic. The brief asks for its *visual language* (spacing/radii/shadows/typography/restraint), not a brand-color swap; this is called out explicitly in `index.css`'s token-block comment so it doesn't read as an oversight later.
- Mechanism, not just look: Ferrumium's own `.react-flow` wrapper carries classes like `bg-[var(--theme-flow-bg)]` — i.e. it themes via CSS custom properties referenced through Tailwind arbitrary-value utilities, swapped under a `.light`/`.dark` ancestor class, exactly the technique this job adopted (see below) rather than sprinkling `dark:` on every utility.

### Design tokens & theme mechanism

- **All new tokens live in `apps/web/src/index.css`**, inside `:root, .light { ... }` and `.dark { ... }` blocks: `--surface-app/panel/card/sunken/overlay/hover`, `--border-subtle/default/strong`, `--text-primary/secondary/muted/inverted`, `--accent/-hover/-contrast/-soft`, `--outpost/-soft/-border`, `--danger/-soft`, `--success` (defined, not yet consumed — no component needed a "success" color this job), `--node-header/-text` (fixed across both themes, per the Ferrumium finding above), `--shadow-card/-modal`, `--grid-dot`.
- Every restyled component (`RecipeNode.tsx`, `OutpostNode.tsx`, `BoundaryEdge.tsx`, `ConnectionEdge.tsx`, `RecipeChooser.tsx`, `NodeContextMenu.tsx`, `Breadcrumbs.tsx`, `MarqueeOverlay.tsx`, `DevNodeTools.tsx`, `CanvasView.tsx`, `App.tsx`, `ProjectsPage.tsx`) references these via Tailwind v4 arbitrary-value utilities (`bg-[var(--surface-card)]`, `text-[var(--text-primary)]`, etc.) instead of literal `neutral-*`/`indigo-*`/`amber-*`/`red-*` classes — grepped the whole touched surface at the end (`grep -rn "neutral-[0-9]\|indigo-[0-9]\|amber-[0-9]\|red-[0-9]"`) and confirmed zero hits left. This means most components need **no `dark:` variant classes at all** — the token swap under `.dark` handles it centrally. `dark:` is still used nowhere in this app's own components as of this job; the mechanism is 100% the CSS-var-token approach. (`@custom-variant dark (&:where(.dark, .dark *));` is still declared per the job's own instruction to verify Tailwind v4's exact class-based mechanism, and is available for a future job that prefers a `dark:` utility for something a token can't express, e.g. a `dark:opacity-*` tweak.)
- **Tailwind v4 dark-mode wiring, precisely**: v4 ships no `tailwind.config.js` here (confirmed pre-existing) and its *default* `dark:` variant (undeclared) resolves to a `prefers-color-scheme` media query with no way to force a choice — there is no v4 equivalent of v3's `darkMode: 'class'` config knob. The fix is the one-line `@custom-variant dark (&:where(.dark, .dark *));` at the top of `index.css`, which redefines what `dark:` compiles to. Confirmed this is necessary (not cargo-culted) by testing without it first: the `dark:` variant silently fell back to the media query and ignored the `.dark` class entirely.
- **Toggle + persistence**: `apps/web/src/theme/useTheme.ts` (`localStorage["scm-theme"]`, `"light"`/`"dark"`, falls back to `prefers-color-scheme` when unset), `theme/ThemeToggle.tsx` (a small sun/moon SVG icon button), `theme/index.ts` barrel. Applied as an explicit `dark`/`light` class on `<html>` (never "absence implies light" — both classes are always set/removed together in `applyThemeClass`). **Deliberately app-level**, not canvas-only: `App.tsx` mounts its own `<ThemeToggle>` in its header (covers the login screen and `ProjectsPage`), and `CanvasView.tsx` mounts a second one in its own header (the canvas renders its own chrome with nothing shared above it — see `App.tsx`'s pre-existing comment on that). Both read/write the same `localStorage` key, so they stay in sync even though only one is ever mounted at a time.
- **Flash-of-wrong-theme**: `apps/web/index.html` carries a small inline `<script>` in `<head>` that applies the same class *before* `main.tsx` mounts (mirrors `useTheme.ts`'s `resolveInitialTheme` exactly — keep both in sync if the storage key or fallback logic ever changes). Verified via reload: theme persisted correctly with no visible flash in either direction.
- **The one non-obvious gotcha, found only through actual manual browser testing (would not have been caught by typecheck/build/lint)**: `@xyflow/react`'s `<ReactFlow>` has **its own, completely separate** light/dark mechanism — a `colorMode` prop, defaulting to `"light"` unconditionally, that stamps a `light`/`dark` class directly onto `.react-flow`'s own wrapper div and drives its built-in `--xy-*` variable *defaults* from that class specifically. With `colorMode` left unset, `.react-flow` always carried a hardcoded `light` class regardless of `<html class="dark">`, and `.react-flow.light`'s selector specificity (two classes) beat this app's own global `:root`/`.dark` overrides of the same `--xy-*` names (single class/pseudo-class each) — so the canvas background and `<Controls>` chrome stayed light-only under dark theme no matter what. Fixed by threading `theme` down into `CanvasFlow` and passing `colorMode={theme}` to `<ReactFlow>` (`CanvasView.tsx`). If a future job adds more `@xyflow/react` built-ins (MiniMap, etc. — Job 027), check this same gotcha again; it's not unique to `<Controls>`.
- `index.css` also overrides `@xyflow/react`'s own `--xy-background-color`/`--xy-controls-button-*`/`--xy-controls-box-shadow` inside the same `.light`/`.dark` token blocks, since `<Controls>` has no themeable class props of its own — this is the documented way to theme xyflow's built-in chrome without fighting its shipped CSS.
- `RecipeNode.tsx`'s Job 011 "no `overflow-hidden`" fix (clipped port `Handle` hit-testing) was preserved verbatim — re-read that comment before touching this file again, it's a real regression trap, not decoration.

### Snap-to-grid

- **Pure math**: `apps/web/src/canvas/snapToGrid.ts` — `snapToGrid(value, gridSize)` (rounds to nearest multiple; a `gridSize <= 0` or non-finite passes the value through unchanged rather than dividing by zero) and `snapPointToGrid(point, grid)` (independent x/y, since `gridMachine`/`gridWaypoint` aren't assumed square). Fully unit-tested (`snapToGrid.test.ts`, 8 tests), following the `nodes/recipeNodeMath.ts` precedent for pure-logic-worth-testing-standalone.
- **Values**: uses whatever `Settings.gridMachine`/`gridWaypoint` already are in the doc — Job 007's `DEFAULT_SETTINGS` (`packages/ydoc/src/document.ts`) ship `gridMachine: {x:100,y:100}`, `gridWaypoint: {x:50,y:50}`, `snapMachines: true`, `snapWaypoints: true`. **Not changed by this job** — those defaults turned out sensible as-is (100px reads well against `RecipeNode`'s 256px card width; 50px gives waypoints finer control) and this job's own scope is "wire the fields," not "pick new numbers." Configurable per-document via the new `SettingsMenu.tsx` (see below) or directly via `updateSettings`.
- **Wiring**:
  - `apps/web/src/canvas/useYjsSync.ts`'s `onNodeDragStop` — reads `getSettings(sfmDoc)` fresh at the moment of drag-stop (not a subscribed value; this is a one-off read at a specific instant), snaps via `snapPointToGrid` when `snapMachines` is true, applies to **both** branches (`moveNode` for a real node, `updateContainer` for an outpost boundary node) — an outpost's on-canvas position is just as much a plain x/y as a recipe node's, and PLAN.md's snap-to-grid wording doesn't carve out an exception for outposts.
  - `apps/web/src/canvas/edges/ConnectionEdge.tsx` — both `addWaypointAtClient` (double-click-to-add) and `handleWaypointPointerUp` (drag-to-move) now snap via `snapWaypoints`/`gridWaypoint`. Snapping the *creation* point too (not just subsequent drags) was a deliberate call — leaving a freshly-added waypoint off-grid until its first drag would read as a bug ("why did it jump on first touch"), not as intended behavior.
  - `outposts/BoundaryEdge.tsx` was **not** touched for snapping — it's read-only/non-interactive by design (Job 013's own Handoff notes explain why: stored waypoints belong to a different container's coordinate space), so there's nothing there to snap.
- **Toggle UI**: `apps/web/src/canvas/SettingsMenu.tsx` — a small gear-icon popover in `CanvasView.tsx`'s header with two checkboxes (`Machines`/`Waypoints`, each showing its current grid size read-only next to the label) bound straight to a new `updateSettings(sfmDoc, patch, origin?)` mutation helper (`packages/ydoc/src/mutations.ts` + export from `index.ts`, 2 new tests in `mutations.test.ts`). This had to be added — Job 007 defined the `Settings` schema and defaults, but **no mutation helper existed to write back to it** before this job (`getSettings` existed, nothing else did); the acceptance criteria's "disabling the setting restores free positioning" line implies a UI path has to exist to disable it. Deliberately minimal scope: two checkboxes, nothing else — a fuller settings surface (number formats, connection style, multipliers) is explicitly out of this job's scope.
- **A real bug found and fixed during manual verification, not just cosmetic**: `SettingsMenu.tsx`'s first draft had its popover backdrop close on `onMouseDown` (same pattern `RecipeChooser.tsx`/`NodeContextMenu.tsx` use) but — unlike those two — didn't `stopPropagation()` on the popover panel's own `onMouseDown`. Since `mousedown` fires (and bubbles to the backdrop, closing the menu) *before* a checkbox's `click`/`onChange` can run, the checkboxes were **completely unclickable** — every click silently closed the menu first. Confirmed via `document.querySelectorAll('input[type=checkbox]')` returning an empty array immediately after a click that should have hit one. Fixed with the same `event.stopPropagation()` on the panel div the other two floating-menu components already had; verified the fix via direct `settings.toJSON()` reads before/after toggling, and via a live drag-with-snap-off / re-enable-and-drag-with-snap-on round trip (see Verification below).
- **Verified live, not just via unit tests**: dragged a node with snap on → landed at exact multiples of 100 (`{x:800,y:600}` etc.); toggled snap off via the fixed checkbox → dragged again → landed at fractional/arbitrary coordinates (`{x:328.5,y:103.5}`); toggled back on → dragged again → snapped again (`{x:400,y:100}`). Same round trip for waypoints at the 50px grid (`{x:900,y:550}` on add, `{x:600,y:550}` after a drag).

### What Job 015 (Postgres persistence) should know

- Every `Settings` field this job exercises (`snapMachines`, `gridMachine.{x,y}`, `snapWaypoints`, `gridWaypoint.{x,y}`) is read via `getSettings(sfmDoc)` and written via the new `updateSettings(sfmDoc, patch, origin?)` — both go through the normal `sfmDoc.settings` `Y.Map`, so they'll persist automatically once Job 015 wires up Yjs↔Postgres persistence for the document as a whole. No special-casing needed on the persistence side for these fields specifically.
- The **theme preference is explicitly *not* part of the CRDT document** — it's a plain `localStorage` value (`scm-theme`), per-browser/per-device, not per-project or per-user-in-a-shared-doc. This was a deliberate scope call (this job's own Scope wording: "localStorage is sufficient for now, doesn't need to be a DB setting yet") — if a future job wants theme to sync across a user's devices or be considered a project setting, that's new schema/schema-migration work, not something Job 015's persistence layer needs to account for as-is.
- The new `SettingsMenu.tsx` popover writes `snapMachines`/`snapWaypoints` via plain, untagged local transactions (no special `origin`) — same as every other UI-driven mutation in this app so far, so it'll interact with `Y.UndoManager` exactly like any other edit (toggling snap is itself undoable, confirmed incidentally during manual testing — not a specific acceptance criterion, but worth knowing).
