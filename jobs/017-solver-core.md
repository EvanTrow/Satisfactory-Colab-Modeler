## Scope

In scope:
- A plain-data input snapshot type — deliberately **not** Yjs-shaped — representing a solvable graph: nodes (recipe, machine, limit, limitMode, clock, shards), edges (part, fromNode/Port, toNode/Port), and settings (solver mode, multipliers). This is the boundary type that `apps/web`'s worker host (Job 018) will construct from the live Yjs doc each solve.
- **None mode**: trivial — returns no computed values, instant.
- **Manual mode**: per PLAN.md's table, "entered values are the final values you want" (spreadsheet-like) — i.e. the solver in this mode doesn't infer anything; it validates the user-entered limits/clocks are self-consistent along each edge (same part, same rate in vs out at splits/merges) and reports mismatches, using exact `Rational` arithmetic throughout. "No splitter/merger preference modeling" per the table — a node with multiple output edges of the same part just divides evenly for *validation* purposes, it doesn't need to model real splitter behavior since Manual mode doesn't compute quantities from limits, it displays entered ones.
- **Basic mode**: "entered values are limits" — the solver propagates limits through the graph to compute machine counts/rates everywhere, without modeling splitter/merger even-split preference or priority (per the table, "No" on that column). Per PLAN.md §5's correctness requirement: *"the Basic calculator 'may produce inconsistent results when multiple valid solutions exist,' so we must pin a fixed variable ordering and a deterministic pivot rule, or collaborators will see different numbers for identical state."* This determinism requirement is not optional — write it into the algorithm's design explicitly (e.g. process nodes/edges in a stable sort order — by ID — and document the pivot rule in a code comment), and test it by running the same input snapshot through the solver many times / with shuffled-but-logically-equivalent input ordering and asserting identical output.
- Somersloop and generator handling per `packages/gamedata`'s (Job 003) boost formula and generator/power sign conventions — the solver must correctly account for output multiplication from shards and power generation vs consumption.
- Power is computed using the float boundary from `packages/rational`'s `power.ts` (Job 002) — rates stay exact, power is float, per PLAN.md's explicit exactness-boundary note.
- Golden-value tests exactly as specified in PLAN.md §9: 30 Iron Ore/min → 30 Iron Ingot/min; Miner Mk.3 on Pure = 480/min; Manufacturer with 4 somersloops = 2× output at 4× power; a Coal Generator chain's water draw.

Out of scope:
- Full calculator / splitter-merger priority LP (Job 023).
- Web Worker hosting, debouncing, cancellation, dirty-subgraph caching (Job 018) — this package is synchronous pure functions; the worker wrapping is a separate concern.
- Summary panel, highlighting, number formatting UI (Job 019).

## Handoff notes

**Public API — import everything from `@scm/solver`** (JIT package, same convention as every prior `packages/*`: `main`/`types`/`exports` point straight at `./src/index.ts`, no build step needed to consume it):

- **`solve(snapshot: SolverSnapshot, mode: SolverMode, gameData: GameData = defaultGameData): SolveResult`** (`./index`) — the one function Job 018 needs to call. Synchronous, pure, deterministic: same arguments in, same `SolveResult` out, no I/O, no timers, never mutates `snapshot`. The `gameData` parameter is a deliberate, backward-compatible addition beyond the job's literal `solve(snapshot, mode): SolveResult` wording — it defaults to `@scm/gamedata`'s real `defaultGameData`, so every 2-argument call the job description describes still works; the third argument exists for tests and for a future multi-`game_data_version` world (PLAN.md §10.5), not because Job 018 needs to pass anything different today.
- **Snapshot type** (`./snapshot`): `SolverMode = "none" | "manual" | "basic"` (no `"full"` — that literal doesn't exist in this package at all; Job 023 will need to add it). `SolverSnapshot { nodes: readonly SolverNode[]; edges: readonly SolverEdge[] }`. `SolverNode { id, recipe, machine, purity: Purity | null, limit: string | null, limitMode: "machines" | "ppm", clock: string | null, shards: number }` — `recipe`/`machine` are plain `@scm/gamedata` name strings (e.g. `"Iron Ore"` / `"Miner Mk.3"`); `limit`/`clock` are canonical `@scm/rational` `n/d` strings (or `null` = "never set"), `clock` a **percentage** not a 0..1 fraction — this deliberately mirrors the on-the-wire convention Job 010's `recipeNodeMath.ts` already established for `@scm/ydoc`'s `NodeRecord`, since that is what Job 018 will actually be converting FROM. `SolverEdge { id, part, fromNode, fromPort, toNode, toPort }` — ports are carried through for shape-compatibility with `@scm/ydoc`'s `EdgeRecord` but are **not used by any solver logic** in this job (grouping is by `(nodeId, part)`, not by port — see below); Job 018 can pass the real port ids straight through with no translation needed.
  - **This job only models recipe nodes.** There is no snapshot representation yet for outposts, splurgers (explicit splitter/merger), storage containers, blueprints, or AWESOME Sink (PLAN.md §2's other specialty node types). A node that isn't a plain recipe machine has no place in `SolverNode` today — whichever later job adds one of those kinds to the canvas needs to extend `snapshot.ts` (and `nodeProfile.ts`'s resolution logic) before the solver can represent it. `SolveSummary.sinkPoints` is hardcoded to `"0"` for exactly this reason (no AWESOME Sink representation to sum from yet).
- **Result type** (`./result`): `SolveResult { mode, nodes: readonly NodeSolveResult[], edges: readonly EdgeSolveResult[], summary: SolveSummary, valid: boolean, warnings: readonly string[] }`. `nodes`/`edges` are always sorted by id (via `ordering.ts`'s `idCompare` — plain code-unit comparison, not `localeCompare`) regardless of the snapshot's own array order — part of the determinism guarantee, and convenient for Job 018/019 (stable diffing, stable render order). `NodeSolveResult { nodeId, machineCount, clockPercent, resolved, partRates: Record<partName, string>, power: number, valid, issues }` — every numeric field except `power` is a canonical `n/d` string; `power` is the one deliberate float boundary (MW, signed: positive = generates). `resolved: false` only ever happens in Basic mode, for a node with no limit and no resolvable neighbor (see the algorithm below) — None/Manual never set it `false`. `EdgeSolveResult { edgeId, part, rate, valid, issues }` — `rate` is always non-negative (a magnitude, not a signed flow). `SolveSummary { perPart: Record<partName, PartBalance>, powerMade, powerUsed, powerNet, sinkPoints }` where `PartBalance { made, used, unmade, unused }` is a pure production/consumption **balance** across every node in the snapshot (not a flow-through-edges computation) — `unmade = max(0, used - made)`, `unused = max(0, made - used)`. This means the summary stays meaningful even for a graph with dangling/unconnected ports, matching how the original tool's summary panel reads.
- **None mode** (`./none`, `solveNone()`): trivial — `{ mode: "none", nodes: [], edges: [], summary: <all zeros>, valid: true, warnings: [] }`. Doesn't touch the snapshot at all, so it's O(1) regardless of graph size.
- **Manual mode** (`./manual`, `solveManual`): every node's machine count comes from its own `limit`/`limitMode`/`clock` only — **no graph inference at all**. `node.limit === null` defaults to exactly `ONE` machine (matching Job 010's `recipeNodeMath.ts` "displayed default" convention for the no-solver stopgap it was standing in for). The only thing this mode computes beyond per-node math is edge validation (see below).
- **Basic mode** (`./basic`, `solveBasic`) — **read `basic.ts`'s header comment in full**; it is the algorithm spec, written to be precise enough for Job 023 to extend without guessing. Summary for this handoff:
  1. **Pin**: every node with `limit !== null` gets an immediate machine count from `nodeProfile.ts`'s `pinnedMachineCount` (no graph).
  2. **Propagate** (`propagateMachineCounts`, exported from `basic.ts`): a fixed-point relaxation. Each pass scans every still-unresolved node (in sorted-id order, though see the determinism note below — order doesn't actually change the *result*, only bookkeeping) and asks: does any edge connect me to an already-resolved neighbor, for a part my recipe has? If so, my implied rate for that part is the **sum** of "implied shares" over every such edge, where an implied share is the resolved neighbor's own total rate for that part divided evenly across however many sibling edges the neighbor has for that same part (`edgeGroups.ts`'s even-split rule — PLAN.md §2's "No" on splitter/merger preference modeling, operationalized as "no priority, just an equal-weighted sum"). One resolved part is enough to solve for the node's machine count (`machineCountForTargetRate`), since every other part scales with the same count. Repeats pass-over-pass (Jacobi-style — each pass computes from the PREVIOUS pass's frozen state and commits all updates at once, so within-pass scan order can't matter) until a full pass resolves nothing new.
  3. **Fallback**: anything still unresolved (isolated node, or a whole component with no pinned node) defaults to exactly `ONE` machine, flagged `resolved: false`.
  4. **Determinism, precisely** (PLAN.md §5 point 4's requirement): even-split division is *exact* `Rational` arithmetic, so there is never a remainder to break a tie over. When multiple resolved neighbors imply a rate for the same part, they're combined by plain addition (commutative — order genuinely cannot matter). When a node has implied rates for *different* parts in the same pass, the **pivot rule** is: prefer the recipe's own `primaryPart` (largest-magnitude output, or largest-magnitude input for generators/pure-consumers — same convention as Job 010's `recipeNodeMath.ts`) if it has an implied rate, else the alphabetically-first part name that does — both are properties of the recipe/edge data, not of iteration order. Every id list this module touches is sorted via `ordering.ts` before use. `determinism.test.ts` verifies this two ways: (a) the same chain graph submitted with reversed/shuffled node and edge arrays produces byte-identical `JSON.stringify` output, and (b) an unconstrained fan-out (one pinned producer, two unconstrained consumers, no priority information) splits exactly in half regardless of which order the two edges appear in.
  5. **What this deliberately does NOT do** (Job 023's job): resolve an over-constrained graph via least-squares/LP, arbitrate conflicting demands from multiple *different* pinned neighbors reaching the same unresolved node through different parts, or model real splitter/merger priority. Full mode extending this should probably keep `pinnedMachineCount`/`nodeProfile.ts` as-is (the per-node math doesn't change) and replace `propagateMachineCounts` with the real solve — the even-split `edgeGroups.ts` helpers are NOT what Full mode should reuse for priority splitting, they're specifically the "no preference" stand-in.
- **Somersloop handling** (`nodeProfile.ts`): the output multiplier from shards applies to **positive-amount (output) parts only** — input consumption is untouched by shards, matching the real game (production amplification, not free extra throughput) and PLAN.md §1's Manufacturer example. Power gets the `powerMultiplier` unconditionally. `buildNodeProfile` calls `@scm/gamedata`'s `somersloopBoost(machine, node.shards)` guarded so a machine with no shard support and `node.shards === 0` never throws (verified: `somersloopBoost` returns `{outputMultiplier: ONE, powerMultiplier: ONE}` for `shards === 0` before it ever checks `maxProductionShards`).
- **Converter/Particle Accelerator/Quantum Encoder power override** (the gotcha Job 003 flagged explicitly for this job): `nodeProfile.ts`'s `NodeProfile.effectivePower` is computed as `recipe.averagePower ?? machine.averagePower` — never `machine.averagePower` alone. Covered by a dedicated test (`nodeProfile.test.ts`) that asserts the Converter `Machine` record has `averagePower: undefined` and that a Converter node's `effectivePower`/computed power nonetheless comes out correct via the recipe-level override, plus the same check for one Particle Accelerator and one Quantum Encoder recipe.
- **Generators** (`Recipe.isGenerator`): need no special-case code at all in this package — a generator recipe simply has no positive-amount part, so `primaryPart` falls through to its largest-magnitude *input* (e.g. Water, for Coal Generator), and `partRateAtMachineCount`/`machineCountForTargetRate` work unchanged. Power still comes from `effectivePower` exactly as for any other machine. Verified by the Coal Generator golden test (fuel-in/power-out, no positive output part at all).
- **A node/machine/shard resolution failure never throws** — `buildNodeProfile` (`nodeProfile.ts`) catches everything (unknown recipe name, unresolvable MultiMachine variant, invalid shard count) and returns a profile with `issues` populated instead, so one corrupt node can't crash the whole `solve()` call. This matches PLAN.md §5's "a CRDT guarantees convergence, not correctness" framing — Job 018/019 should expect `NodeSolveResult.valid: false` + non-empty `issues` on bad data, never an exception from `solve()` itself.
