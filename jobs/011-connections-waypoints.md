# Job 011: Connections & waypoints

**Phase:** 2 · Solo canvas editor
**Status:** Done
**Depends on:** 010 (recipe node UI — needs real ports to connect)

## Context

Read [`PLAN.md`](../PLAN.md) section **2. The Interaction Model to Reproduce** ("Connect" and "Waypoints" rows) closely — the gestures are specific and easy to get subtly wrong: drag output→input *or* input→output both work; remove by re-dragging or right-clicking the part label; double-left-click a connection label or waypoint adds a waypoint; double-right-click a waypoint deletes it; double-right-click a bare label deletes the connection; waypoints are draggable and stay put when their machine moves.

## Scope

In scope:
- Drag-to-connect between node ports using React Flow's edge-drawing interaction, supporting both drag directions (output→input and input→output resolve to the same logical edge).
- On successful connect, call `packages/ydoc`'s deterministic-`edgeId` edge-creation mutation from Job 007 — reuse it as-is, don't reimplement ID generation here.
- Edge removal: re-dragging an existing connection's endpoint elsewhere, or right-clicking the part label, removes the edge via `packages/ydoc`'s removal mutation.
- Waypoints:
  - Double-left-click a connection label or an existing waypoint adds a new waypoint at that position, stored in the edge's `waypoints: Y.Array<{x,y}>`.
  - Double-right-click a waypoint deletes just that waypoint.
  - Double-right-click a bare connection label (no waypoint under the cursor) deletes the whole connection.
  - Waypoints are draggable independently and do **not** move when either endpoint machine is dragged (i.e. they're stored as absolute canvas coordinates, not relative offsets — verify this explicitly, it's a common bug).
- Edge rendering must correctly route through however many waypoints exist, in order.
- Only compatible ports should be connectable (same `part` type on both ends) — reject/no-op a connect attempt between mismatched parts, since PLAN.md's data model assumes one part per edge.

Out of scope:
- Connection style options (Direct/Curves/Horizontal/Vertical) — explicitly a later-phase item in PLAN.md §3.
- Multi-select of edges, cut/copy/paste of connections — Job 012.
- Priority splitter/merger specific connection behavior — Phase 6 (Job 024).

## Deliverables

- Edge-drawing interaction wired into the canvas, both directions.
- Edge removal via re-drag and right-click-label.
- Waypoint add/delete via the exact double-click gestures above, with waypoints stored as absolute coordinates that survive endpoint drags.
- Part-type compatibility check preventing mismatched connections.
- Tests: deterministic edgeId reuse (connecting the same two ports twice doesn't duplicate — this exercises Job 007's guarantee end-to-end through the UI layer), waypoint persistence across an endpoint node drag.

## Acceptance criteria

- Both connect directions work and produce identical resulting edges.
- All four waypoint gestures behave exactly as specified in PLAN.md §2.
- Dragging a node with a connected, waypointed edge leaves the waypoint's absolute position unchanged.
- Attempting to connect two ports carrying different parts is rejected with no edge created.
- `pnpm --filter web test/build/typecheck` pass.

### Two real bugs found and fixed (neither anticipated going in)

Both were only discoverable by actually *dragging* a connection, which is exactly what Job 010 explicitly deferred to this job — Job 010's own verification only asserted handle presence/attributes via `querySelectorAll`, never a real drag.

1. **`RecipeNode.tsx`'s outer card had `overflow-hidden`.** React Flow's `<Handle>` elements render protruding slightly past the node's own edge (the standard visual — a connection line should touch the node's border). With `overflow-hidden` on the card, that protruding sliver was clipped both visually *and* for hit-testing: `document.elementsFromPoint()` at a handle's own reported center didn't include the handle at all, just the card underneath it — every drag-to-connect attempt silently missed. Fixed by dropping `overflow-hidden` from the outer div and adding `rounded-t-md` directly to the header div (the only child with its own background color that needed corner-clipping; the rows/footer sections have transparent backgrounds and never needed it).
2. **Edge labels/waypoints render *underneath* nodes by default.** `@xyflow/react` gives every `.react-flow__node` an inline `z-index: 1000`, while `<EdgeLabelRenderer>`'s container is a DOM sibling that comes *before* `.react-flow__nodes` in `.react-flow__viewport`'s children and has no z-index of its own — so whenever a label or waypoint's on-screen position overlaps a node (routine for a short edge between two nearby machines, since the label defaults to the path midpoint), every click on it was actually landing on the node behind it instead. Fixed with an explicit `zIndex: 10000` on the label div and `10001` on waypoint markers (`EDGE_OVERLAY_Z_INDEX` in `ConnectionEdge.tsx`) — comfortably above any z-index React Flow assigns a node, and the waypoint intentionally wins over a co-located label so the "double-click an existing waypoint" vs. "double-click a bare label" disambiguation (see gesture notes below) still resolves to the waypoint when both sit at the same point. Confirmed via direct `document.elementFromPoint` comparison before/after: `false` → `true` at the label's own geometric center.

Both were verified via live DOM/hit-test inspection during manual testing, not just visually — see "Verification actually performed" below.

### Gesture implementation, precisely

- **Connect, both directions:** `<ReactFlow onConnect={onConnect} isValidConnection={isValidConnection} />`. Verified live and empirically confirmed React Flow's own claim that `Connection.source`/`.sourceHandle` always resolve to the literal `type="source"` handle regardless of which side the user started dragging from: dragging output→input and, separately, dragging input→output on a *different* node pair both produced `fromPort` starting with `"out:"` and `toPort` starting with `"in:"` in the resulting `EdgeRecord`. `resolveEdgeEndpoints` still does its own symmetric check defensively (accepts either arrangement) rather than trusting this blindly — see the function's doc comment.
- **Reject mismatched parts:** `isValidConnection={isValidPortConnection}` (same underlying `resolveEdgeEndpoints` check) prevents React Flow from ever completing/highlighting an incompatible drag; `onConnect`'s own `connectPorts` call re-validates independently as defense in depth. Live-verified: dragging Iron Ore's `out:Iron Ore` onto a node's `in:Iron Ingot` produced zero new edges.
- **Remove by re-dragging elsewhere:** `onReconnectStart`/`onReconnect`/`onReconnectEnd` per React Flow's own documented pattern — see `useConnectionHandlers.ts`'s header comment. Live-verified by grabbing a connected edge's `react-flow__edgeupdater-target` circle (**not** the node's own `<Handle>` — React Flow renders a separate small reconnect-anchor `<circle>` at each end of a reconnectable edge; that's the actual drag-start target for this gesture, distinct from the handle used for a brand-new connection) and dropping on empty canvas: edge count went from 1 to 0.
- **Remove by right-clicking the part label:** a single `onContextMenu` on `PartRow`'s row div (see "What got built" above) — deliberately read as the *node's own part-row label* rather than the edge's floating on-canvas label, because PLAN.md's Connect row says "the part label" (singular gesture, no "double") while its Waypoints row separately and explicitly spells out *double*-right-click for the edge's own label — see "Deviations" below for the full reasoning. Live-verified: right-clicking a connected part row removed every edge touching that port in one click, with no Recipe Chooser popping up (confirmed `stopPropagation` keeps this from also bubbling into `onPaneContextMenu`).
- **Double-left-click a label or waypoint → add waypoint:** `nearestSegmentIndex` on the click's flow position picks which polyline segment to insert into; `addWaypoint(sfmDoc, edgeId, flowPos, index)`. Clicking exactly on an *existing* waypoint still routes through the same "nearest segment" logic (one of the two segments touching that waypoint wins), which is what makes "double-click an existing waypoint" insert a near-duplicate at that same spot rather than needing special-casing.
- **Double-right-click a waypoint → delete just that waypoint:** each waypoint marker owns its own `onContextMenu`; `removeWaypoint(sfmDoc, edgeId, index)`.
- **Double-right-click a bare label → delete the whole connection:** the label's own `onContextMenu`; `removeEdge(sfmDoc, edgeId)`. "Bare" (no waypoint under the cursor) falls out for free from DOM event targeting *once the z-index bug above was fixed* — a waypoint marker, now correctly stacked above the label, catches the right-click itself (and `stopPropagation`s) whenever the cursor is really over it; otherwise the label's own handler fires.
- **Waypoints are draggable and stay at absolute positions:** `onPointerDown`/`onPointerMove`/`onPointerUp` on each marker, local `dragIndex`/`dragPoint` state for smooth visual feedback (mirrors `useYjsSync.ts`'s node-drag pattern — no Yjs write per pointermove, one `updateWaypoint` commit on pointerup). Verified explicitly: created a waypoint, then dragged *both* of an edge's endpoint nodes (separately) and re-read `EdgeRecord.waypoints` after each — coordinates were byte-identical to before either drag, both live in the browser and in `connectionLogic.test.ts`'s dedicated "waypoint persistence across an endpoint node drag" test.

### The `labelPos` convention — confirmed, not changed

Job 007 assumed `labelPos` was "a 0..1 t-parameter along the edge's path" but flagged it unconfirmed. This job **confirms that convention as-is**: `pointAtT(points, t)` in `edgeGeometry.ts` is exactly that — arc-length-fractional position along `[source, ...waypoints, target]`. No drag-the-label-to-reposition-`labelPos` UI was built (not in this job's Scope/Deliverables/Acceptance criteria, only the double-click gestures were), so every edge's `labelPos` stays `null` for its whole life under this job's code, and `ConnectionEdge.tsx` treats `null` as `0.5` (path midpoint) via `record.labelPos ?? DEFAULT_LABEL_POS`. If a later job wants a real label-drag interaction, the geometry is already in place (`pointAtT` for rendering, and the inverse — projecting a drop point back onto the polyline to get a `t` — would be a natural addition to `edgeGeometry.ts`); only the drag-and-commit UI plumbing is missing.

### What Job 012 (selection & editing) needs to know

- **Edge identity/selection:** edges are plain React Flow edges (`id` = ydoc's deterministic hash, `selected` comes through as a normal `EdgeProps.selected` boolean — `ConnectionEdge.tsx` already reads it to highlight the label's border). Nothing about this job's edge type opts out of React Flow's default click-to-select/marquee-eligible behavior; Job 012's multi-select and cut/copy/paste should work against `useYjsSync.ts`'s existing `edges` array the same way it presumably will for `nodes`.
- **`data.record` is the full `EdgeRecord`** (including live `waypoints`), refreshed on every doc change via the pre-existing `sfmDoc.edges.observeDeep` resync in `useYjsSync.ts` (unchanged by this job) — no new observer wiring was needed since Job 008 already resyncs on any nested change inside an edge's `Y.Map`, including its `waypoints` `Y.Array`.
- **Deleting an edge is exactly `removeEdge(sfmDoc, id)`** — no cascade, no waypoint cleanup needed (`removeEdge` deletes the whole `Y.Map` including its nested `waypoints` array). If Job 012 implements node deletion, remember (per Job 007's own documented behavior, unchanged here) that `removeNode` does **not** cascade to edges — Job 012's delete/cut handling should explicitly call `removeEdge` for anything touching a deleted node, same as this job's `removeEdgesForPort` does for the single-port case.
- **The `react-flow__edgeupdater` anchors** (small circles React Flow renders at each end of a reconnectable edge, distinct from node `<Handle>`s) are the actual grab points for "drag an existing edge's endpoint" — worth knowing if Job 012 ever needs to simulate or reason about this gesture (e.g. for a test harness), since they're easy to miss/confuse with the node's own handles.
- **No multi-select/cut/copy/paste of edges was touched** — explicitly out of scope per this job's own Scope section, confirmed still true.

### Deviations from the spec / things flagged for later jobs

- **"Right-click the part label" (PLAN.md's Connect row) was implemented as a single right-click on the node's own `PartRow`, not the edge's floating on-canvas label** — which has its own, separately-specified *double*-right-click-when-bare gesture (PLAN.md's Waypoints row). The two PLAN.md rows use different wording ("the part label" vs. "a connection label") and pair different modifiers (unmodified vs. explicitly double-click), which reads most consistently as two distinct affordances rather than one gesture described twice. If this reading turns out wrong, the fix is confined to `PartRow`'s `onContextMenu` handler and/or `ConnectionEdge.tsx`'s label handler.
- **The two bugs in "Two real bugs found and fixed"** were both pre-existing (Job 010's `overflow-hidden`; React Flow's own default z-index ordering) but only became *observable* once this job actually tried to drag connections and click labels/waypoints — flagging here in case any other job's manual verification independently ran into either symptom and worked around it differently.
- **No visual/style polish** beyond "functionally correct and legible," per this job's own scope — straight-segment polyline, plain-div label/waypoint markers, no connection-style options (Direct/Curves/Horizontal/Vertical, `EdgeRecord.style`/`Settings.connectionStyle` both still unused/`null`-only). All explicitly Job 014's territory.
- **`reconnectEdge`'s no-op-on-mismatch behavior (old edge left untouched) is only reachable in practice via a direct unit-test call** — in the live UI, `isValidConnection` already blocks a mismatched reconnect target before `onReconnect` ever fires, so the "drag ended nowhere valid" cleanup path (delete old edge) in `useConnectionHandlers.ts`'s `onReconnectEnd` is what actually runs for a rejected reconnect attempt, not `reconnectEdge`'s own null-return branch. Both paths are tested/verified independently (see above), just worth knowing they're not literally the same code path a user hits.
