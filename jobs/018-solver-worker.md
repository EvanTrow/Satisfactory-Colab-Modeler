# Job 018: Solver Web Worker host

**Phase:** 4 · Calculators
**Status:** Done
**Depends on:** 017 (`packages/solver`), 016 (end of Phase 3 — needs a stable, persisted canvas to solve against)

## Context

Read [`PLAN.md`](../PLAN.md) section **5. Real-Time Sync Architecture → The multiplayer-specific hazard: the solver**, points 1-3 specifically (point 4, determinism, was already addressed in Job 017). Also **7. Project Structure**'s `apps/web/src/workers/` entry and **9. Verification**'s performance budget ("Basic solve under 200 ms").

This job is single-player-safe worker infrastructure — running the pure `packages/solver` functions off the main thread, debounced, cancellable, with dirty-subgraph caching. It does not yet need to handle multiple remote collaborators triggering solves (Job 020+), but must be architected so that works later without rework.

## Scope

In scope:
- A Web Worker (`apps/web/src/workers/solverWorker.ts`) that imports `packages/solver` and exposes a message-based API: submit a snapshot + mode, receive a result or a cancellation ack.
- Debounce (~150ms per PLAN.md) on the main-thread side: canvas edits trigger a debounced re-solve request rather than solving on every keystroke.
- **Cancellable**: if a new solve request arrives before the previous one completes, the in-flight solve is cancelled (the worker should actually stop wasted work, not just discard a late result — since Basic/Manual are fast this may be more about correctness of "only the latest result wins" than actual compute savings, but implement real cancellation semantics since Full mode in Job 023 will need genuine cancellation, and this is the natural place to build that contract).
- **Dirty-subgraph solving**: partition the graph into connected components (outposts already partition the graph per PLAN.md — use container boundaries as the natural partition unit), cache per-component results, and on an edit, only re-solve the component(s) containing the changed node/edge. Cache invalidation must be correct — a change to a node's limit invalidates only its own component; a change that adds/removes an edge crossing a component boundary invalidates both components it touches.
- Show the last result greyed/stale while recomputing (a UI-facing state flag the worker host exposes: `'fresh' | 'stale-recomputing'`) rather than blanking the display — this job wires the state machine; Job 019 consumes it in the summary panel/node highlighting.

Out of scope:
- The actual summary panel and per-node red/orange highlighting UI (Job 019) — this job only needs to expose the result data and staleness state for Job 019 to render.
- Full calculator support (Job 023) — build the cancellation/worker contract to accommodate a slower cancellable solver later, but don't implement Full mode itself.

## Deliverables

- `apps/web/src/workers/solverWorker.ts` — the worker entry point.
- `apps/web/src/workers/useSolver.ts` (or similar) — the main-thread hook/store: debounce, request/cancel lifecycle, dirty-subgraph partitioning and caching, staleness state.
- Tests: cancelling a stale in-flight request and confirming only the latest result is applied; a component-boundary edit invalidates exactly the right cached components (not more, not fewer); a ~200-node/component synthetic snapshot resolves within the performance budget.

## Acceptance criteria

- Rapid sequential edits (simulating fast typing in a limit field) result in exactly one final solve applied, not a queue of stale results racing to update the UI.
- Editing a node in one outpost does not trigger a re-solve of an unrelated, unconnected outpost's cached result (verify via a spy/counter on the solve call).
- Per PLAN.md §9's performance budget: a synthetic 500-node/800-edge factory's Basic solve completes under 200ms end-to-end through the worker (including message-passing overhead, not just `packages/solver`'s raw compute time).
- `pnpm --filter web test/build/typecheck` pass.

### Message protocol (`protocol.ts`)

`HostToWorkerMessage = SolveRequestMessage { type: "solve", requestId: number, snapshot: SolverSnapshot, mode: SolverMode }`. `WorkerToHostMessage = SolveResultMessage { type: "result", requestId, result: SolveResult } | SolveErrorMessage { type: "error", requestId, message: string }` (the error branch exists defensively — `solve()` itself never throws per Job 017's guarantee, so this is only reachable via a hypothetical transport/serialization failure). The worker is stateless: every message is independent, no session/handshake.

### Connected-components/caching algorithm, precisely

Every relevant document change (`sfmDoc.nodes`/`.edges`/`.settings` — see `useSolver.ts`) triggers, after the 150ms debounce:
1. `buildSolverSnapshot(sfmDoc)` — the **whole document's** recipe-node subgraph, real `listNodes`/`listEdges`, never container-scoped.
2. `partitionSnapshot(snapshot)` — union-find over the real graph into `SolverComponent[]`, each with its own `signature`.
3. For each component, check `cache.get(\`${mode}:${signature}\`)`. A hit is reused as-is (its `ComponentResult` — just `{nodes, edges}`, not a full `SolveResult`). A miss is added to a batch.
4. If there are ANY misses, they're all concatenated into **one** `SolverSnapshot` and sent to the worker in a **single** `postMessage` — even if several unrelated components are dirty at once, that's one worker round trip, not one per component. This is safe: components are, by definition, not connected by any edge, so `solve()`'s Basic-mode propagation (which only ever looks across an edge) can't let one dirty component influence another's numbers — solving them together is byte-identical to solving each alone. `mergeResults.test.ts` asserts this equivalence directly.
5. `splitResultByComponents()` slices the worker's one combined response back into one `ComponentResult` per component it covered, and each is cached under its own `${mode}:${signature}` key.
6. `mergeComponentResults(mode, [...hits, ...freshlySolved])` produces the final document-wide `SolveResult`, sorted by id, with `summary`/`valid`/`warnings` recomputed fresh over the merged node/edge list (see "Summary merging" below).

**Cache invalidation rules** (the job's own acceptance criterion, verified both by `partition.test.ts`/`solveScheduler.test.ts` and live in a browser — see "Manual verification" below):
- A component's `signature` is a hash of **its own nodes' and edges' full content** (not just ids), sorted before serializing. Editing a node's `limit`/`clock`/`shards`/`recipe`/`machine`/`purity` changes ONLY that node's own component's signature — every other component's signature (and cached result) is untouched, so it's never resent to a worker.
- Adding an edge that connects two previously-separate components merges them (`computeConnectedComponents`) into a single new component with a signature that never appeared before — both old cache entries simply go unused (not explicitly invalidated, just never looked up again), and the new merged component is a guaranteed cache miss, forcing a real resolve. Removing such an edge splits it back the same way, in reverse.
- Cache keys are `${mode}:${signature}` — switching `Settings.solverMode` (e.g. Basic → Manual) makes every existing entry a miss under the new mode, without needing to explicitly clear anything (the old-mode entries just sit unused; they'd become hits again if the mode were switched back to a mode/content combination already seen).
- The cache (`Map<string, ComponentResult>`) is never bounded/evicted — an acceptable tradeoff at this app's documented scale (PLAN.md §2: "tens to low hundreds per outpost"), flagged as a deviation below.

### Summary merging (a documented departure from naively concatenating `@scm/solver`'s own per-call `.summary`/`.warnings`)

`SolveSummary`'s `made`/`used` are, by `@scm/solver`'s own design (`result.ts`'s doc comment), "a pure production/consumption balance across every node in the snapshot" — additive over a disjoint node partition, with no edge/graph dependence. That means `mergeResults.ts`'s `summaryFromNodes()` can recompute the whole document's summary purely from the merged `NodeSolveResult.partRates`/`.power` list — summing `made`/`used` per part additively (exact, since it's just node-disjoint-partition addition) and recomputing `unmade`/`unused` from the TOTALS (`max(0, used-made)`/`max(0, made-used)`) rather than summing each component's own already-clamped `unmade`/`unused` (which would be wrong — `max()` doesn't distribute over addition; `mergeResults.test.ts` has a dedicated test for exactly this case: one component all-"unused", one all-"unmade", merging to a balanced zero on both sides). Similarly, the merged `valid`/`warnings` are recomputed as `nodes.every(valid) && edges.every(valid)` (byte-identical to how `basic.ts`/`manual.ts` compute it themselves) and the flattened `issues` of every merged node/edge — the latter is a deliberate, documented IMPROVEMENT over `@scm/solver`'s own top-level `.warnings` field, which is actually narrower (it omits `NodeProfile`-level issues like "unknown recipe" — see `basic.ts`/`manual.ts`'s `extraIssuesByNode`). **Job 019 should read `warnings` off this merged result, not assume it matches whatever a direct `solve()` call's own `.warnings` would say.**

### Cancellation strategy — read before touching `solveScheduler.ts`

Basic/Manual solves are synchronous and fast; there's no cooperative checkpoint inside `solve()` to poll a cancel flag against. "Actually stop wasted work" is achieved via **`Worker.terminate()`** — genuine JS-engine-level preemption, not a cooperative flag. To keep this off the 150ms debounce's critical path (a fresh worker's module graph pulls in `@scm/gamedata`'s real ~136KB `game_data.json`, parsed once at import time), the scheduler keeps a pre-warmed **spare** worker at all times: `acquireWorkerForNewRequest()` only calls `terminate()` when the current active worker is genuinely busy (a request in flight); an idle worker (previous request already completed) is reused directly, no termination needed at all. When termination does happen, the already-warm spare is promoted immediately and a new spare starts booting in the background. This is the contract Job 023's Full mode (an LP that will actually take long enough to want cooperative cancellation too) can build on without changing this module's shape — `terminate()` remains the backstop either way.

### Staleness state machine

`SolveStaleness = "fresh" | "stale-recomputing"`. `submit()` sets it to `"stale-recomputing"` **synchronously**, the instant it's called (before the debounce timer even starts) — so a UI consuming this should grey out immediately on keystroke, not after 150ms. It flips back to `"fresh"` only when a result is delivered AND no newer submission is already queued (`pendingSubmission === null`) — if a newer edit landed while a solve was in flight, the delivered result is real progress but not final, so it stays greyed for one more round rather than flashing "fresh". `result` itself is **never cleared** just because it's stale — PLAN.md §5 point 3's "show the last result greyed... rather than blanking."

### How Job 019 should consume this

```ts
import { useSolver } from "../workers"; // or "apps/web/src/workers"

const { result, staleness, nodeResultById, edgeResultById } = useSolver(sfmDoc);
```

- `result: SolveResult | null` — `null` only before the very first solve ever completes. `result.summary` for the summary panel; `result.warnings` for the flattened issue list (see "Summary merging" above for why this is more complete than `@scm/solver`'s own field).
- `staleness: "fresh" | "stale-recomputing"` — grey/dim while `"stale-recomputing"`.
- `nodeResultById`/`edgeResultById: ReadonlyMap<string, NodeSolveResult | EdgeSolveResult>` — O(1) lookup by id for per-node/per-edge rendering (validity highlighting) without re-deriving an index from `result.nodes`/`.edges` every render. Both are stable empty-Map singletons when `result` is `null` or empty, so a consumer can `.get(id)` unconditionally with no null-check dance.
- A second, optional `diagnostics?: { onDispatch?, onCancel? }` argument exists purely for manual verification/debugging (see `DevNodeTools.tsx`'s `SolverDebugPanel`) — Job 019 doesn't need it.
- Independent of `containerId` — solving covers the whole document regardless of which outpost is currently being viewed; looking up a rendered node's result by id works the same in any container.

### A real StrictMode bug found and fixed during manual verification (read this if `useSolver` ever "stops updating")

The first draft created the `SolveScheduler` via `useMemo(() => createSolveScheduler(...), [sfmDoc, useStore])`, separately from the `useEffect` that calls `scheduler.submit()`/attaches observers/disposes it. This is broken under React 19's `<StrictMode>` (enabled in `main.tsx`): React deliberately mounts every effect, cleans it up, then mounts it again on first render, specifically to catch effects that leak. Since the memoized `scheduler`'s identity survives that whole cycle (same `[sfmDoc, useStore]` deps), the interim practice-cleanup's `scheduler.dispose()` call permanently killed it (`SolveScheduler.dispose()` sets a `disposed` flag that makes every future `submit()` call a silent no-op) — the "real" second mount then submitted into an already-dead scheduler, so every subsequent document edit silently did nothing forever. Caught by manual browser testing (`window.__solveDebug` stayed at `{mode: "none", staleness: "fresh"}` no matter what was edited), **not** by any automated test (the `solveScheduler.test.ts` suite tests the scheduler in isolation, not this React-lifecycle interaction). Fixed by moving `createSolveScheduler(...)` **inside** the effect itself, so StrictMode's practice-mount creates and disposes its own throwaway scheduler, and the real mount gets a genuinely fresh one — the same fix pattern any StrictMode-sensitive `useEffect`-owned resource (a WebSocket, a subscription) needs. **If a future refactor moves scheduler creation back out to a `useMemo`/`useRef`, watch for this exact regression.**

### Deviations from the spec / things flagged for later jobs

- **`onDispatch`/`onCancel` diagnostic hooks** on `SolveSchedulerOptions` (and `useSolver`'s optional second `diagnostics` argument) are additive, not in the job file's literal deliverables — added specifically to make the "instrument a solve-call counter" verification the job's own Notes section asks for actually possible to observe live, and wired into `DevNodeTools.tsx` (dev-only) rather than left as untestable internal state.
- **The merged `warnings`/`valid` fields are recomputed from the merged node/edge list**, not concatenated from each component's own (discarded) `SolveResult.warnings` — see "Summary merging" above. This makes the worker-host's `warnings` a strict superset of (and more useful than) what a hypothetical single `solve()` call over the same full graph would report, since it includes `NodeProfile`-level issues `@scm/solver`'s own top-level field currently omits. Flagged for Job 019: don't assume `useSolver`'s `result.warnings` matches `@scm/solver`'s own convention byte-for-byte if you ever cross-reference the two.
- **The component result cache is unbounded** (no LRU/size cap) — acceptable at this app's documented node-count scale; if a future job pushes scale far beyond "tens to low hundreds per outpost," this is the first place to add an eviction policy.
