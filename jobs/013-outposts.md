# Job 013: Outposts (nested containers)

**Phase:** 2 · Solo canvas editor
**Status:** Done
**Depends on:** 012 (selection & editing)

## Context

Feature Scope → MVP → Structure** ("outposts with drill-in navigation and breadcrumbs; port mapping on the outpost node at the parent level"). Also re-read §10.3 (open question on blueprint semantics) for awareness — **blueprints themselves are out of scope** (Phase 7, Job 026), but this job's container model must not preclude that later work, since `containers` already has a `kind: 'outpost'|'blueprint'` field from Job 007.

## Scope

In scope:
- Outpost creation (e.g. via the Recipe Chooser's canvas context menu, or a dedicated "New Outpost" action — use judgement on exact entry point, consistent with PLAN.md's "like folders" framing) creating a `containers` entry via `packages/ydoc`.
- Drill-in navigation: double-clicking (or an explicit "open" affordance on) an outpost node switches the canvas view to render that container's contents instead of the parent's, with a **breadcrumb trail** back to root showing the container hierarchy.
- From outside (i.e. viewed from the parent container), an outpost renders as a **single node with input/output ports** — the port set is derived from which parts cross the outpost's boundary (edges whose `fromNode`/`toNode` live inside the outpost but connect to something outside). This is "port mapping" per PLAN.md §3 — implement it as a computed/derived view, not stored redundantly, so it can never drift from the actual internal edges.
- Moving a node into/out of an outpost (e.g. drag onto the outpost node, or a context-menu "move to container" action) updates its `containerId`.
- Deleting an outpost: per PLAN.md §5's integrity-reducer principle ("reparent orphaned nodes to the root container rather than deleting them"), deleting an outpost container must reparent its child nodes/edges to the container's parent rather than destroying them — implement this locally now (the full multiplayer-safe integrity reducer is Job 022, but the single-player deletion behavior should already follow this rule so it doesn't change later).

Out of scope:
- Blueprints (duplicable outposts) — Job 026.
- The formal cross-client integrity reducer pass (Job 022) — this job only needs correct behavior for a single local user's actions, not concurrent-edit repair.
- Any solver awareness of outpost boundaries (partitioning solve into per-outpost components is Job 018's "dirty-subgraph solving").

## Deliverables

- Outpost container creation + drill-in view switching + breadcrumb UI.
- Derived port-mapping logic (outpost node ports = boundary-crossing edges, computed not stored).
- Move-node-into/out-of-outpost interaction.
- Outpost deletion with reparent-to-parent behavior (not destroy).
- Tests: port mapping stays correct as internal edges change; deleting an outpost with children reparents them correctly; breadcrumb trail reflects actual nesting depth.

## Acceptance criteria

- Creating an outpost, adding nodes inside it, and connecting one of them to something outside correctly shows the outpost, from the parent view, with a port for that connection.
- Drilling in and back out via breadcrumbs correctly restores the parent view with all prior state intact.
- Deleting a populated outpost leaves its former children visible (reparented to the outpost's parent container), never silently destroyed.
- `pnpm --filter web test/build/typecheck` pass.

### The boundary-crossing-edge design decision (Job 007 left this genuinely unresolved)

Job 007's schema has no "boundary crossing" concept — an `EdgeRecord` just has `fromNode`/`toNode` (plain node ids) and its own `containerId` (which container's canvas it renders in). The open question this job had to resolve: when an outpost's boundary node needs to show a port for a connection, where does that connection's "truth" live, and how does it come into being?

**Resolution:** `EdgeRecord.containerId` is **not** treated as authoritative for "does this edge cross a boundary, and where." Whether an edge crosses a boundary — and which one — is derived **entirely from the current `containerId` of its `fromNode`/`toNode`**, walked up each node's container-ancestry chain (`portMapping.ts`'s `resolveNodeLocation`/`isContainerWithinSubtree`), recomputed fresh every render. `edge.containerId` still exists (the schema requires it, and `deleteOutpost` keeps it in sync when reparenting — see `reparentEdge` above) but nothing in the rendering path reads it to decide visibility or projection.

This falls out of a more fundamental interaction-model decision: **only one container's contents are ever rendered at a time** (the whole point of drill-in navigation), so a user physically *cannot* drag a fresh connection directly between two nodes that live in different containers — there's no view where both are simultaneously on screen with real, port-bearing handles. So the realistic, and in fact *only*, way a boundary-crossing edge comes into being is: **wire two nodes together while both are in the same container (an ordinary `connectPorts` call, unchanged from Job 011), then move one of them into (or out of) an outpost** via `moveNodeToContainer`/the "Move to container" context-menu action. The edge itself is never touched by that move — it still references the same two real node ids — but the moment the two endpoints' `containerId`s diverge, `computeOutpostPorts` starts finding it as a crossing on its own, with zero explicit "mark this edge as boundary" step anywhere. Deleting the outpost later (reparenting its contents back to a shared container) makes the same edge collapse back into an ordinary internal one, again with no explicit un-marking — it's a pure function of current state, so it can't drift.

One consequence, tested and manually verified: **you cannot drag a brand-new connection directly onto an outpost's boundary-node handles.** Each boundary handle's id (`boundary:<edgeId>:<in|out>`) doesn't parse as a valid `${"in"|"out"}:${part}` port handle (`connectionLogic.ts`'s `parsePortHandleId` requires exactly that shape), so `isValidConnection` rejects it automatically — no special-casing needed, it just falls out of the existing id-parsing contract. This is deliberate, not an oversight: ports are strictly *derived*, so there's no such thing as an "empty" port to author a new connection onto from outside.

A second consequence of "only the current container renders": a boundary-crossing edge's **stored waypoints are not reusable** for its projected rendering — they were captured in whatever container's coordinate space the edge was drawn in (Job 011: waypoints are absolute canvas coordinates), which is generally a *different* space than the container currently projecting it. `BoundaryEdge.tsx` is a separate, much simpler, non-interactive edge component specifically so it never tries to route through `record.waypoints` — it always draws a plain `getSmoothStepPath` line between wherever `sourceX/Y`/`targetX/Y` land. If you move a node back out of an outpost, the edge reverts to `ConnectionEdge.tsx` (its stored waypoints, valid again in the now-shared container, come right back).

### How "current container" is tracked and exposed

`CanvasDocContextValue` gained two things: `rootContainerId` (fixed, set once, for "what's the top") and `navigateToContainer(id)`. `containerId` itself changed from a fixed value to genuine React state, lifted into `CanvasView` (`useState(rootContainerId)`), rebuilt into the context value on every change. Every consumer that used to receive a static `containerId` (`RecipeChooser.tsx`, `useSelectionKeybinds.ts`'s paste, `useConnectionHandlers`) needed **no code changes** — they already read `containerId` off the context each render, so they automatically operate against "wherever the user currently is" once it became live. `useYjsSync(sfmDoc, containerId)` is the one hook that had to change its own signature to take `containerId` as an explicit second argument (rather than reading it off context itself, to keep the hook context-free/testable-in-principle) and put it in its resync effect's dependency array.

**Selection across a container switch:** confirmed by manual testing, not just theorized — selecting a node, drilling into an unrelated outpost, and drilling back out does **not** restore the original selection (it comes back deselected), even though the document state (positions, containers, ports) is fully intact. This is intentional, matches the job brief's own suggested fix ("clear selection on container switch"), and falls out for free from Job 012's existing "carry `selected` over by id from the store's *previous* rendered list" mechanism: the previous list right before returning to the parent view was the *child* view's own node list, which never contained the parent's node ids, so there's nothing to carry over. No dedicated "clear selection" call was added — it's an emergent property of the existing mechanism applied to a container switch, verified live via `.react-flow__node`'s `selected` class before/after a round-trip drill.

### Deviations from the spec / things flagged for later jobs

- **Outpost creation entry point:** a "+ New Outpost" button inside the existing Recipe Chooser modal (reusing the same double/right-click-empty-canvas gesture), rather than a separate dedicated modal or a canvas right-click submenu — the job file explicitly left this to judgement. Naming happens via a simple text field step inside the same modal (mirrors the existing MultiMachine variant-picker step's UI pattern), not a native `window.prompt()` (deliberately avoided — awkward for both the user and for automated verification).
- **Move-into/out-of-outpost is context-menu-only, not drag-onto-node.** The job file offered "drag onto the outpost node, or a context-menu action" as alternatives and left the choice to the worker; a context menu was chosen as more reliable/testable than detecting a drag-and-drop-onto-another-node gesture, which would have needed new hit-testing logic layered on top of React Flow's own node-drag handling.
- **`reparentEdge` is a new `packages/ydoc` export**, added by this job (see above) — a small, narrowly-scoped extension to a package a prior job marked "Done," justified by PLAN.md §7's own architecture (`packages/ydoc` is the only place allowed to know the CRDT shape; `apps/web` reaching around it to hand-patch an edge's `containerId` would have violated that).
