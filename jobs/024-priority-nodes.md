## Handoff notes

### The genuinely uncertain design call — how the Splurger fits into a solver that has no node type for it

This job's own prompt flagged a real tension: `@scm/solver`'s `SolverSnapshot` (Job 017) can only represent `kind: "recipe"` nodes (no recipe/machine ⇒ no way to resolve a rate), and this job's own scope note rules out touching `packages/solver` again. Three paths were on the table:

- **(a) UI-only convenience** — no real Splurger graph node at all; "creating a Splurger" would just mean selecting an existing recipe node's port and tagging tiers on *that port's* sibling edges.
- **(b) Genuine solver-side node** — teach `packages/solver` a new node kind, violating "no further solver logic changes."
- **(c) A real, persisted, canvas-visible `kind: "splurger"` node that is NEVER a `SolverNode`** — `buildSnapshot.ts` erases it before the snapshot reaches `@scm/solver`, rewriting its incident edges into direct recipe-to-recipe `SolverEdge`s that carry its tier assignment.

**I chose (c).** Reasoning: the job's own deliverables ask for "Node UI for the Splurger... visually distinct from a recipe node" and a dedicated creation path via the Recipe Chooser — i.e. the job title is "Priority Splurger **node type**," not "priority tagging UI." Path (a) would have satisfied the *solver* constraint just as well (Job 023's `SolverEdge.priorityTier` doesn't care where the tag comes from) but would have under-delivered on "a distinct kind of node users can visually route wires through," which is what PLAN.md's own node list and this job's acceptance criteria ("add a Splurger node, wire multiple outputs to it...") actually describe. Path (c) gets the real node experience with **zero changes to `packages/solver`** — the "Done" package Job 023 shipped is untouched (confirmed via `git diff --stat -- packages/solver`, empty).

**Why this is exact, not an approximation, for the shapes that matter:** `@scm/solver`'s Full-mode water-filling (Job 023) already operates per `(node, part, direction)` sibling group, anchored at a REAL recipe node's own ports. A Splurger with exactly one input edge and N output edges (a splitter) or N input edges and one output edge (a merger) rewrites into exactly the edges that group machinery already expects — the "one real node, several sibling edges" shape it was built for — just sourced from the Splurger's OTHER side's real endpoint instead of the Splurger's own (nonexistent) profile. This is **not** a best-effort/approximate translation for these two shapes; it produces the identical `SolverEdge` set a user would get if they'd wired those consumers directly off one real recipe node's own output port.

**The one shape genuinely NOT supported, and why it's excluded rather than approximated:** a Splurger wired with multiple inputs AND multiple outputs simultaneously has no correct rewrite. The naive "connect every input to every output" (a transportation-problem crossbar) would let two different OUTPUT groups' independent water-fills both believe they can draw from the SAME source's full capacity — a genuine double-counting bug, not a cosmetic gap. This also isn't an artificial solver limitation: **real Satisfactory splitter/merger hardware never combines both** either (a Smart Splitter is 1-in/3-out; a Conveyor Merger is 3-in/1-out — nothing is both). `workers/splurgerPassthrough.ts`'s `computeSplurgerPassthroughEdges` detects this per-part-group and excludes those edges entirely (reported via `unsupportedNodeIds`, surfaced as a visible warning banner in `SplurgerNode.tsx`), rather than silently dropping flow with no explanation or guessing at a wrong answer. A **chained** Splurger (one feeding directly into another, with no real recipe node between them) is similarly not resolved — the rewrite only looks one hop away, so a synthetic edge landing on another Splurger's id is filtered out by `buildSnapshot.ts`'s pre-existing "both endpoints must be a recipe node" rule, the same as any edge touching an unrepresentable node already was. Flagged as a known limitation for a follow-up, not attempted here — the common case ("one Priority Splurger, plain consumers on each output") that Job 023's own Handoff notes predicted is fully and exactly supported.

**Priority Splitter / Priority Merger were NOT built as separate node kinds.** Per the job's own "use judgement" note: a Splurger wired with only multiple outputs *is* a Priority Splitter; wired with only multiple inputs *is* a Priority Merger — same node, same code, differentiated purely by wiring (mirroring the real hardware distinction above). `SplurgerNode.tsx` computes and displays this classification live (`computeSplurgerShape`'s `"splitter" | "merger" | "passthrough" | "empty" | "unsupported"`) as the card's own subtitle, so a wired Splurger visibly reads as "Priority Splitter" or "Priority Merger" without needing a second node type.

### `@scm/ydoc` — no schema or mutation changes needed

The prompt suggested either extending `EdgeRecord` with a new `priorityTier` field or reusing `NodeRecord.priorityOrder: string[]` (Job 007's schema — defined, unused until now). **I reused `priorityOrder`, with zero `@scm/ydoc` changes** (no new field, no new mutation helper — the existing `setPriorityOrder(sfmDoc, nodeId, order: string[])` from Job 007 is sufficient). Encoding, in `workers/splurgerPassthrough.ts`:

- Each entry is `"top:<edgeId>"` or `"bottom:<edgeId>"`, where `<edgeId>` is one of the Splurger's own incident `EdgeRecord.id`s (not a port-handle string) — robust to reconnection, and directly matches what `computeSplurgerPassthroughEdges` needs to look up.
- An edge with no entry at all defaults to "top," mirroring `SolverEdge.priorityTier`'s own `undefined`-behaves-as-`"top"` convention exactly (Job 023) — an unconfigured Splurger's ports all pool together evenly.
- `decodePriorityOrder`/`encodePriorityOrder`/`tierForEdge`/`withDefaultedEdges`/`withoutStaleEdges`/`setTier`/`moveWithinTier` (all pure, all unit-tested in `splurgerPassthrough.test.ts`) are the full read/write API `SplurgerNode.tsx` uses to edit it via the existing `setPriorityOrder` call — no other package needed a new export.

I judged this the right call because a new `EdgeRecord.priorityTier` field would have meant touching a "Done" `@scm/ydoc` schema (Job 007) for a value that, per the design above, is **only ever set on a Splurger's own incident edges** anyway (a plain recipe-to-recipe edge has no UI path to set a tier at all under path (c) — see "Concerns" below) — reusing an already-defined, already-unused node-level field kept the CRDT schema exactly as Job 007 shipped it.

### STOP/progress — the mechanism, precisely (read before assuming "cooperative cancellation" alone does anything)

Job 023's Handoff notes suggested extending `protocol.ts` with a `cancel` message the worker turns into `signal.aborted = true`, plus relaying `onProgress` via a `progress` message — both are wired exactly that way. **But there is a real, load-bearing asymmetry between the two directions**, discovered while implementing this:

- **Worker → main thread (`progress`) genuinely works in real time.** A worker's `postMessage` calls are delivered to the main thread's own, independent event loop as they happen, even while the worker's own thread is still busy computing — confirmed live (see Verification below). This is why the "Solving…" progress text updates live during a slow solve.
- **Main thread → worker (`cancel`) generally CANNOT interrupt an already-executing synchronous call.** `solverWorker.ts`'s `onmessage` handler calls `solve()` synchronously; while that call is running, the worker's single JS thread is blocked and cannot process a queued `cancel` message until `solve()` already returns — at which point flipping `signal.aborted` is too late to matter. This isn't a bug in this job's wiring; it's an inherent property of a single-threaded synchronous worker with no `SharedArrayBuffer`-backed signal and no way for `packages/solver`'s `solve()` to yield mid-call.

**Consequence: the STOP button's mechanism that actually, verifiably halts computation is `Worker.terminate()`** — Job 018's real, JS-engine-level preemption, unconditionally effective regardless of what the worker's call stack is doing. `solveScheduler.ts`'s new `stop()` sends the cooperative `cancel` message first (cheap, harmless, matches Job 023's contract, and would become genuinely effective for free if a future job ever makes the worker's own solve invocation chunked/yielding or backs the signal with a `SharedArrayBuffer`), then calls `terminate()`, exactly mirroring the existing supersede-a-busy-worker path `acquireWorkerForNewRequest` already used. This is flagged prominently here per this job's own "flag genuine uncertainty" latitude — Job 023's Handoff notes described the cooperative path as "a strictly faster additional path... not a replacement" for `terminate()`, implicitly assuming the worker COULD check a shared signal mid-computation; in this specific worker architecture it currently cannot, so today `terminate()` is doing 100% of the real work. See "Concerns for later jobs" below.

`SolveHostState` gained `fullProgress: FullProgressInfo | null`; `SolveScheduler` gained `stop(): void` (cancels any pending debounce, sends the best-effort `cancel` message, `terminate()`s the active worker if genuinely busy, promotes the pre-warmed spare immediately so the next `submit()` isn't stuck re-paying a cold boot, and resets `staleness`/`fullProgress` — `result` is left exactly as it was, per PLAN.md §5 point 3's "show the last result... rather than blanking"). `useSolver.ts` exposes both through `UseSolverResult`, threaded through `SolverResultContext` (extended, not duplicated — **no second `useSolver` call was added anywhere**, per Job 019's own documented bug-class warning). `SolveStatusIndicator.tsx` renders only when `mode === "full" && staleness === "stale-recomputing"`.

### Concerns flagged for Job 025+

1. **Splurger-mediated rate-mismatch/overflow issues aren't visually highlighted on the real recipe nodes' ports** (discovered live, see Verification above). `computeValidity.ts`'s per-node edge lookup (`RecipeNode.tsx`'s `incidentEdges`) scans by the REAL `EdgeRecord.id`, but a Splurger-rewritten connection's solver-level id is the synthetic `sp:<a>><b>` composite — so `edgeResultById.get(realEdgeId)` always misses for any edge touching a Splurger, and the port never lights up red/orange even when the synthetic edge genuinely is invalid/mismatched. The underlying numbers are correct; only the decoration is missing. A future job should either (a) have `buildSnapshot.ts`/`splurgerPassthrough.ts` also expose a `realEdgeId -> syntheticEdgeId[]` map for `apps/web`'s own use (one real edge can map to several synthetic ones for a splitter's input side), or (b) extend `computeNodeValidityState`/`RecipeNode.tsx` to consult it. Node-level issues (e.g. "N/min could not be routed") DO still surface correctly via `NodeSolveResult.issues`/the card's own tooltip, since those key off the real node id — only the PORT-level red/orange decoration is affected.
2. **Cooperative cancellation (`CancelMessage`/`signal.aborted`) is wired end to end but is not what actually stops computation today** — see "STOP/progress" above. `Worker.terminate()` (Job 018's mechanism) is doing all the real work; making the cooperative path genuinely effective (meaningfully faster than a `terminate()`+respawn) would need either a `SharedArrayBuffer`+`Atomics`-backed signal (needs COOP/COEP headers — an infrastructure change) or restructuring how the worker invokes `solve()` to yield periodically (which `packages/solver`, explicitly out of this job's scope to touch again, would need to support). Not attempted here; flagged per this job's own "flag rather than guess" latitude.
3. **A Splurger wired with both multiple inputs AND multiple outputs is detected and excluded (with a visible warning), not modeled** — see "genuinely uncertain design call" above.
