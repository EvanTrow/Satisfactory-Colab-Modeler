# Job 015: Yjs ↔ Postgres persistence

**Phase:** 3 · Persistence
**Status:** Done
**Depends on:** 014 (visual pass — end of Phase 2), 006 (project CRUD, needs `projects` to attach documents to)

## Context

Read [`PLAN.md`](../PLAN.md) section **4. Data Model → Canvas state: snapshot + incremental log** in full — the exact split between `project_doc_state` (compacted snapshot) and `project_doc_updates` (append-only log), the load/write/compaction algorithm described right after the SQL, and `project_versions`. This is the job that turns Phase 2's "refresh loses it" canvas into something durable.

## Scope

In scope:
- Migrations for `project_doc_state`, `project_doc_updates`, and `project_versions` exactly as specified in PLAN.md §4 (add to `db/migrations/`, building on Job 004's setup).
- `apps/api` (or a shared persistence module usable by both `apps/api` and, later, `apps/realtime`) implementing:
  - **Load**: snapshot + every log row with `id > seq`, merged via `Y.applyUpdate`, returning a hydrated `Y.Doc`.
  - **Write**: append-only — every debounced flush from the client inserts one row into `project_doc_updates`, never rewrites the document.
  - **Compaction**: a background job (can be a simple periodic task for now, doesn't need a full job queue) that folds log rows into the snapshot once the log exceeds ~200 rows for a project, then deletes the folded rows, updating `seq`.
- Wire the client (`apps/web`, using the local Yjs doc from Job 007/008) to: on project open, fetch and apply the persisted state; on local changes, debounce (e.g. ~1-2s) and POST the incremental update to the server for appending. This job does **not** yet require a live WebSocket — a simple debounced REST push/pull is sufficient groundwork; Job 020 (Hocuspocus) will later replace/extend this transport, not the storage model, which stays as-is.
- Fix Job 006's "duplicate project" limitation now that `project_doc_state` exists: duplicating a project should also duplicate its current doc snapshot.

Out of scope:
- Real-time multi-client sync over WebSocket (Job 020) — this job is single-client load/save durability only.
- `y-indexeddb` local caching and the autosave *indicator* UI, and `project_versions` restore UI (Job 016).
- Any use of `project_versions` beyond having the table and an insert path ready for Job 016 to build restore UI on top of.

## Deliverables

- Migrations for the three tables.
- Server-side load/write/compaction logic (with the compaction threshold configurable, defaulting to ~200 rows per PLAN.md).
- Client-side debounced push + on-open pull wired into the canvas from Job 008.
- Fixed project duplication (Job 006) to include the doc snapshot.
- Tests: load = snapshot + logs merges correctly; compaction folds and deletes correctly and preserves identical resulting doc state (byte-compare `Y.encodeStateAsUpdate` before/after compaction); a crash mid-flush loses at most one debounce window (simulate by not compacting and reloading from snapshot+partial-log).

## Acceptance criteria

- Per PLAN.md §8's Phase 3 exit criterion: "Factory survives reload and server restart" — build a factory in the canvas, reload the page, and it's still there; restart the API/DB containers and it's still there.
- Compaction is verified to produce a byte-identical merged document compared to not compacting (i.e. compaction is purely an optimization, never lossy).
- Writes are O(change) — verify a single node move results in one small `project_doc_updates` row, not a full-document rewrite.
- `pnpm --filter api --filter web test` passes.

## Notes for the worker

- Keep the persistence module's interface transport-agnostic where reasonable (a plain "given bytes, load/append/compact" API) since Job 020 will likely want the same logic accessible from `apps/realtime`, not just `apps/api`'s REST layer.

## Handoff notes

### Migrations & schema

- `db/migrations/0006_project_doc_state.ts`, `0007_project_doc_updates.ts`, `0008_project_versions.ts` — Kysely schema-builder, matching PLAN.md §4's SQL exactly (columns, `bytea`/`bigint`/`bigserial` types, the two indices — `project_doc_updates(project_id, id)` and `project_versions(project_id, created_at)` — and `project_versions`'s `kind` check constraint). All three cascade off `projects.id` (`on delete cascade`), matching every other per-project table.
- `db/schema.ts` gained `ProjectDocStateTable`/`ProjectDocUpdatesTable`/`ProjectVersionsTable` (+ `Selectable`/`Insertable`/`Updateable` convenience types, `ProjectVersionKind` union) and added all three to `Database`. **`seq`/`id` (the `bigint`/`bigserial` columns) are typed `string`, not `number`** — `postgres.js` returns 64-bit integer columns as strings by default to avoid silent precision loss, and `docStorage.ts` follows suit (`BigInt(row.seq)` to compare, `String`/back to the DB as the literal Kysely-returned string). Job 016 (or anyone else querying these tables) should keep doing the same rather than casting to `Number` for anything beyond display — the 200-ish-row threshold makes `Number` "work" today, but the type is honestly `string` and future code shouldn't assume otherwise.

### Server-side persistence module — `apps/api/src/projects/docStorage.ts`

Deliberately transport-agnostic (no Fastify types anywhere in the file) — plain functions taking/returning bytes and project ids:

- `loadProjectDoc(projectId)` → `{ doc: Y.Doc, snapshotSeq: bigint, appliedLogRows: {id:bigint}[] }` — the actual "snapshot + every log row with `id > seq`, merged via `Y.applyUpdate`" algorithm from PLAN.md §4. A project with nothing persisted resolves to an empty `Y.Doc()`, not an error — this matches `@scm/ydoc`'s `createDocument({ doc })`, which only fills default `meta`/`settings` when those maps are empty, so "nothing persisted yet" and "genuinely empty doc" are the same representation on both ends.
- `loadProjectDocUpdate(projectId)` → `Uint8Array` (`Y.encodeStateAsUpdate` of the merged doc) — what the GET route sends over the wire.
- `appendUpdate(projectId, update, actorUserId, threshold = DEFAULT_COMPACTION_THRESHOLD)` — inserts exactly one `project_doc_updates` row (never rewrites `project_doc_state`), then checks the project's current (un-folded) row count and calls `compactProject` inline if it exceeds `threshold` (default `200`, matches PLAN.md's "~200 rows" — `DEFAULT_COMPACTION_THRESHOLD` exported so a caller can override it, which is exactly how the tests exercise compaction without inserting 200 rows). No job queue/cron — this is a synchronous check on the request that happens to cross the threshold, per the job file's own "can be a simple periodic/synchronous check" guidance.
- `compactProject(projectId)` → `CompactionResult | null` (`null` = nothing to fold, safe no-op). Runs as a **single Postgres transaction** (`db.transaction()`, with `forUpdate()` on the snapshot row read) so a crash mid-compaction can never leave a stale snapshot next to already-deleted log rows, or vice versa — either the whole fold-and-delete lands, or none of it does. The new snapshot is written via `insertInto(...).onConflict((oc) => oc.column("project_id").doUpdateSet(...))` (upsert, since `project_doc_state`'s PK *is* `project_id` — there's at most one row per project).
- `duplicateDocState(sourceProjectId, targetProjectId)` — the Job 006 TODO fix (see below). Loads the source's merged doc, writes it as a **fresh** `project_doc_state` row for the target with `seq = "0"` (the target has zero log rows of its own at that point — `seq` only ever means "this project's own log folded into this project's own snapshot," never a copy of the source's). No-ops if the source has no persisted state at all (nothing to copy; the target is left exactly like a normal empty `createProject` would leave it).
- `createProjectVersion(projectId, { label?, kind, createdBy? })` — inserts one `project_versions` row snapshotting the current merged doc. **Not called from anywhere yet** — this job's scope is "have the table and an insert path ready," Job 016 builds the actual named/auto-save + restore UI on top of it.

**Lossless-compaction verification** (explicit acceptance criterion): `docStorage.test.ts`'s `"is lossless"` test merges snapshot+logs twice — once before calling `compactProject`, once after (from the now-compacted snapshot alone, asserting `appliedLogRows` is empty on the second load to prove the log really was folded, not just left there) — and byte-compares `Y.encodeStateAsUpdate` of both resulting docs. They're identical. This works because Yjs's encoded state is a deterministic function of *which structs a doc contains*, not of how many `applyUpdate` calls it took to get there — compaction only changes storage shape, never content.

**A real gotcha hit writing the tests, worth knowing for Job 016 or anyone else asserting "the latest edit wins" against these tables**: two *independent* `new Y.Doc()`s that each set the same key exactly once are, from Yjs's point of view, truly concurrent writes with no causal relationship — which one "wins" after merging is resolved by comparing each write's `(client, clock)` id, **not** by which one was `appendUpdate`d later. A naive test (or, more importantly, naive production code) that fires off unrelated fresh docs for a sequence of edits to the *same* key will get non-deterministic results. `docStorage.test.ts`'s `createMarkerEditor()` helper works around this by reusing **one evolving `Y.Doc`** and capturing each transaction's *incremental* diff (`Y.encodeStateAsUpdate(doc, priorStateVector)`) — this is also exactly what real client edits look like (see `apps/web`'s `doc.on('update', ...)` below), so it's not just a test trick, it's the realistic shape. This isn't a bug in anything shipped — real client edits are always causally chained through one `Y.Doc` — but it's a sharp edge if a future job (e.g. Job 022's integrity reducer, or Job 020's Hocuspocus wiring) ever synthesizes updates from multiple independent docs and expects a specific one to win.

### REST routes — `apps/api/src/projects/docRoutes.ts`

- `GET /api/projects/:id/doc` → `{ update: string }` (base64) — any project member (owner/editor/**viewer**) can load; 404 for a non-member or nonexistent/soft-deleted project (same "don't leak existence" pattern as `routes.ts`).
- `POST /api/projects/:id/doc/updates`, body `{ update: string }` (base64) → `204` — owner/editor only; **a viewer gets `403` and the update is not persisted** (verified in `docRoutes.test.ts` — pushes 0 rows). This is the "cheap, correct check to add now" the job file's Notes section flagged — it is *not* the hard, server-enforced read-only boundary PLAN.md §9 eventually requires (there's no realtime transport yet for that to matter against); Job 020 (Hocuspocus `onAuthenticate`/`readOnly`) is where a viewer's connection becomes genuinely unable to send writes at all.
- **Wire format is base64-in-JSON, not raw `application/octet-stream`.** Fastify has no built-in parser for arbitrary binary content types (would need a custom `addContentTypeParser`); given the update sizes here are small (PLAN.md's own "O(change)" framing — the manual verification below saw 20-50 byte rows for single-field edits, 505-706 bytes for a full node-creation-plus-defaults batch), base64's ~33% overhead is immaterial and every route stays on the same default JSON body parser. If a future job needs to stream genuinely large blobs (e.g. `.sfmd` import), that's the point to revisit this choice, not now.
- Both routes registered in `apps/api/src/app.ts` as a sibling plugin (`projectDocRoutes`), same registration pattern as `projectRoutes`.

### Client wiring — how a real `projectId` reaches the canvas

`apps/web/src/App.tsx`'s `<CanvasView>` now receives `projectId={view.project.id}` and `role={view.project.role}` alongside the existing `projectTitle`/`projectShortId` (`view.project` is the full `ProjectSummary` from `api/projects.ts`, already carrying `id`/`role` — no new fetch needed to get these into `App.tsx`). This is the "thread a real project id down into `CanvasView`" gap Job 008's handoff notes flagged explicitly.

**`apps/web/src/canvas/CanvasView.tsx` was split into three pieces**:
- `CanvasView` (the export) — calls the new `useProjectDocument(projectId, role)` hook and renders one of three things based on its `status`: a loading screen, an error screen (with a Retry button — `useProjectDocument` exposes a `retry()` closure that bumps an internal state token to re-run the effect), or `CanvasViewReady`.
- `CanvasStatusScreen` — the shared loading/error chrome (same back-button affordance as the real header, so a stuck load never traps the user).
- `CanvasViewReady` — everything Jobs 008-014 built, unchanged in substance, now taking `sfmDoc`/`rootContainerId`/`undoManager` as **props** instead of creating them itself via the old `createLocalCanvasDocument()` (deleted). `CanvasFlow` (the `<ReactFlow>` instance) is unchanged.

**The hydration sequence — `apps/web/src/canvas/persistence/useProjectDocument.ts`** (the direct replacement for `createLocalCanvasDocument`), in order, all inside one `useEffect` keyed on `[projectId, role]`:
1. `fetch`+base64-decode the project's doc bytes (`docApi.ts`'s `fetchProjectDoc`).
2. `new Y.Doc()`, then `Y.applyUpdate(doc, bytes)` if non-empty — **before** anything else touches the doc, and critically **before** `useYjsSync`'s observers ever attach (they only attach once `CanvasViewReady` mounts, which only happens after this hook reaches `status: "ready"`) — this is what satisfies the job's "first render already reflects persisted state, not an empty-then-fill flash" requirement.
3. **Only if `role` is `"owner"` or `"editor"`** (see "viewer gating" below): create the debounced push queue and attach `doc.on('update', ...)` to it — attached *before* step 4/5's own mutations, specifically so those mutations get pushed too (see next point).
4. `createDocument({ doc })` — fills default `meta`/`settings` only if the doc came back empty (brand-new project).
5. Find an existing `kind: "root"` container in the (now-hydrated) doc; only call `addContainer(...)` to create one if none exists. **This replaces the old unconditional `addContainer` call** — Job 008's version always created a fresh root with a new random id on every mount, which would have been actively wrong once real persistence existed (every reload would mint a *second* root container, since the persisted one from a prior session would already be there).
6. `createUndoManager(sfmDoc)` — created **last**, deliberately, so none of steps 3-5's hydration/default-filling mutations show up as an undo step once the user presses Ctrl/Cmd+Z.

Without step 3 happening *before* steps 4-5, a brand-new project would mint a new root-container id on every single reload until the user made their first real edit — nothing would ever persist the very first `addContainer` call. This was caught in code review of my own draft, not by a test; there's no automated regression test guarding this ordering specifically (`useProjectDocument.ts` isn't unit-tested — it's a thin React-effect wrapper around already-tested pieces: `fetchProjectDoc`/`pushProjectDocUpdate`, `createUpdateQueue`, and `@scm/ydoc`'s own tested functions). **If Job 016 refactors this hook, preserve the ordering** (comment in the file spells it out) or add a regression test for it — a manual/RTL-based test would need `apps/web`'s Vitest config to grow a DOM environment, which it doesn't have yet (see Job 008/014's handoff notes on this same gap).

**Debounced push — `apps/web/src/canvas/persistence/updateQueue.ts`** (`createUpdateQueue`), pure and independent of React/DOM/`fetch` (the `push` function is injected), so it's unit-tested directly with fake timers and a mock `push` (11 tests in `updateQueue.test.ts`, including a same-key-write-ordering-safe design using one evolving editor doc, and a test that overlapping `flushNow()` calls serialize rather than firing two concurrent POSTs). Behavior:
- Debounce delay: **1500ms** (`DEBOUNCE_MS` in `useProjectDocument.ts`), matching the job file's "~1-2s" suggestion.
- Several `doc.on('update', ...)` events inside one debounce window are merged via `Y.mergeUpdates` into a single blob before the one POST for that window — one `project_doc_updates` row per window, not one per Yjs transaction. A single update in the window is pushed as-is (no unnecessary `Y.mergeUpdates` call over a 1-element array).
- On a failed push (network/HTTP error), the batch is **re-queued** (prepended ahead of anything enqueued since) and retried on the next flush — `onError` is called (currently just `console.error`s; Job 016 owns the user-visible autosave-status indicator, not this job) but the edit itself is not dropped until the tab actually closes with it still pending. This is the mechanism behind "a crash mid-flush loses at most one debounce window."
- `flushNow()` — cancels any pending timer and flushes immediately (awaits and returns once settled); serializes against an already-in-flight push rather than firing a second concurrent one. Called from `useProjectDocument`'s effect cleanup (project switch / unmount) as a best-effort final flush — fire-and-forget from React's perspective (effect cleanups can't be awaited), but strictly better than not trying.

**Wire bytes — `apps/web/src/canvas/persistence/docApi.ts`** (`fetchProjectDoc`/`pushProjectDocUpdate`) and **`base64.ts`** (`bytesToBase64`/`base64ToBytes`, chunked at 32KB to avoid `RangeError: Maximum call stack size exceeded` from spreading a large `Uint8Array` into `String.fromCharCode(...)` — this is a real, easy-to-hit browser limit for anything beyond a few tens of KB, not theoretical). Both browser-safe (`btoa`/`atob`, no `Buffer` — `apps/web` has no Node polyfill for it).

**Viewer gating — a judgement call, not a hard security boundary**: `useProjectDocument` only wires the push queue/listener when `role !== "viewer"`. The job file's own Notes section explicitly left this to judgement ("use judgement, PLAN.md's later multiplayer phase (Job 020) is where read-only enforcement becomes a hard security requirement"). What this does and doesn't do:
- Does: avoid a viewer's browser generating doomed 403 requests and noisy console errors on every edit.
- Does not: stop a viewer from *locally* editing the in-memory doc — there's no read-only canvas UI (disabled inputs, blocked drag, etc.) built here. `apps/api`'s 403 on the push route is the actual enforcement (verified server-side in `docRoutes.test.ts`); a viewer's local edits currently just silently fail to persist, with no user-facing indication. **Building real read-only canvas UI is explicitly deferred to Job 020** per this job's own scope notes — flagging again here so it isn't mistaken for an oversight.

### Job 006's "duplicate is metadata-only" TODO — fixed

`apps/api/src/projects/store.ts`'s `duplicateProject` now calls `docStorage.ts`'s `duplicateDocState(source.id, project.id)` after the transaction that creates the new project row/membership commits (not inside that transaction — `duplicateDocState` reads from a different pair of tables and there's no reason to hold the `projects`/`project_members` transaction open across a Yjs merge). If `duplicateDocState` throws, the new project row still exists with no doc content (same as every pre-Job-015 duplicate) — this surfaces as a 500 to the caller rather than being silently swallowed.

**The `metadataOnly: true` response flag is gone, not kept around always-`false`.** Decision, per the handoff-notes instruction in Job 006 to "decide whether to remove it, flip it to `false`, or keep a real/metadata distinction": duplication is now a real, full clone, so a flag whose entire meaning was "this *isn't* a full clone" has nothing left to communicate — keeping it as dead weight (`false` forever) seemed more confusing than useful, and no code (in this repo) treats its absence differently from its presence. `apps/web/src/api/projects.ts`'s `DuplicatedProject` type is now just `= ProjectSummary` (was `extends ProjectSummary { metadataOnly: true }`); `ProjectsPage.tsx`'s post-duplicate notice text changed from "only settings were copied" to "including a copy of its current canvas content" (verified live in manual browser testing — see below). If a *future* job wants a genuine metadata-only duplication mode again (e.g. "duplicate without history," a deliberate feature), it should mint a new, differently-named field rather than resurrecting this one — `metadataOnly` no longer has any live meaning to overload.

### Deviations from the spec / things flagged for Job 016

- **Wire format is base64-JSON, not raw binary** — see "REST routes" above. Revisit only if payload size becomes a real concern.
- **`project_versions` has zero callers** beyond the ready-to-use `createProjectVersion` insert helper — exactly what the job file scoped ("having the table and an insert path ready," not restore UI). Job 016's restore UI will need a corresponding "load a specific version's bytes" read path, which doesn't exist yet (trivial to add: `db.selectFrom("project_versions").selectAll().where("id", "=", versionId)`, no helper function was written for it since nothing calls it yet).
- **No autosave-status UI** — the canvas footer text says "autosaves ~1.5s after your last edit (Job 016 adds a live indicator)," a plain static string, not a real indicator reflecting in-flight/failed/synced state. `updateQueue.ts`'s `onError` callback is the natural hook point for a real indicator; it currently just `console.error`s.
- **No `y-indexeddb` anywhere yet** — this job's canvas still round-trips through the network on every open (a `GET` for the full merged doc). Job 016 is explicitly where local IndexedDB caching lands per PLAN.md §5/§7's key-libraries table; nothing here precludes it (the `Y.Doc` `useProjectDocument` constructs is a completely ordinary one, `y-indexeddb`'s `IndexeddbPersistence` can attach to it the same way any Yjs provider would).
- **Viewer's local edits silently don't persist**, with no user-facing signal — see "Viewer gating" above. Acceptable per this job's own scope note, but a real UX gap Job 020 (or an earlier polish pass) should close alongside building actual read-only canvas UI.
- **`useProjectDocument.ts` has no automated test of its own** (only its dependencies — `docApi`/`updateQueue`/`@scm/ydoc` — are unit-tested) since `apps/web`'s Vitest config is still node-environment-only with no React Testing Library, a pre-existing gap every prior canvas job has flagged and worked within (Jobs 008/012/014). The hydration-ordering invariant described above ("push listener attaches before the root-container-creation mutation") is the single most important thing to preserve if this file is refactored, and is currently guarded only by a code comment, not a test.
