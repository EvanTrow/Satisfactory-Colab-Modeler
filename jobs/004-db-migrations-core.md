# Job 004: Core DB migrations (users, sessions, projects, sharing)

**Phase:** 1 · Auth & projects
**Status:** Done
**Depends on:** 001 (monorepo scaffold — needs `db/migrations/`, the Postgres docker-compose, and `apps/api`)

## Context

Read [`PLAN.md`](../PLAN.md) section **4. Data Model (Postgres)**, specifically the "Identity, projects, sharing" subsection (the `users`, `sessions`, `projects`, `project_members`, `project_invites` tables). Do **not** create the CRDT/doc-state tables (`project_doc_state`, `project_doc_updates`, `project_versions`) or the relational projection tables (`proj_nodes`, `proj_edges`) yet — those belong to Jobs 015 and 025 respectively.

## Scope

In scope:
- Migration tooling setup in `db/migrations/` (per PLAN.md's DB choice: `postgres.js` + Kysely, typed SQL, no heavy ORM). Pick a migration runner compatible with that stack (Kysely has its own migration API — use it) and wire a `pnpm db:migrate` script in `apps/api` or root.
- The exact schema from PLAN.md §4 for: `users`, `sessions`, `projects`, `project_members`, `project_invites`, including all constraints (`check` clauses, foreign keys, `on delete cascade`, the partial index on `projects (owner_id) where deleted_at is null`, and the index on `project_members (user_id)`).
- Kysely type definitions generated or hand-written for these tables, exported from `apps/api` (or a shared location if `packages/shared` is more appropriate — use judgment, but keep DB types close to the migrations to avoid drift).
- A `apps/api/src/db.ts` (or similar) setting up the `postgres.js` + Kysely connection using `DATABASE_URL` from `.env`.
- Seed/reset scripts for local dev convenience (optional but recommended: `pnpm db:reset`).

Out of scope:
- `project_doc_state`, `project_doc_updates`, `project_versions` (Job 015).
- `proj_nodes`, `proj_edges` (Job 025).
- Any actual auth logic — this job only creates the tables auth will use (Job 005 implements the OAuth flow against them).

## Deliverables

- Migration files under `db/migrations/` creating all five tables in the correct dependency order, matching PLAN.md §4's SQL exactly (including comments where they carry design intent, e.g. "Discord access/refresh tokens are deliberately NOT stored").
- Kysely `Database` interface types matching the schema.
- `apps/api/src/db.ts` connection setup.
- `pnpm db:migrate` (and ideally `db:reset`) scripts that work against the `infra/docker-compose.yml` Postgres instance from Job 001.

## Acceptance criteria

- `docker compose -f infra/docker-compose.yml up -d` then `pnpm db:migrate` creates all five tables with correct columns, types, constraints, and indices — verify with `\d+ <table>` in `psql` or an equivalent introspection check.
- Foreign key and check constraints actually reject bad data (e.g. inserting a `project_members.role` outside `('owner','editor','viewer')` fails; deleting a `users` row cascades to `sessions`).
- Kysely queries against these tables type-check.
- Migrations are idempotent/re-runnable in a fresh database with no manual intervention.

## Notes for the worker

## Handoff notes

**New workspace package: `@scm/db` (`db/`).** `db/` was added to `pnpm-workspace.yaml`'s `packages` list so it's a real pnpm workspace member with its own `node_modules` — this is what lets `db/migrations/*.ts` do a bare `import { sql } from "kysely"` (Node resolves it by walking up from `db/migrations/` to `db/node_modules`, which only exists if `db/` is a workspace package with `kysely` declared as a dependency; without this, migrations would fail to resolve `kysely` at all when dynamically imported from a different package's process). `db/package.json` is JIT-style like `packages/rational`/`packages/gamedata` (`main`/`types`/`exports` all point at `./schema.ts`, no build step) — `db/schema.ts` is the package's only "real" export, `db/migrations/` isn't re-exported from anywhere, it's read directly by the migration runner.

**Migration tooling — Kysely's own `Migrator` + `FileMigrationProvider` (from `kysely/migration`, *not* the root `kysely` export — root `kysely` re-exports `Migrator`/`FileMigrationProvider` as `KyselyTypeError` stubs on purpose, to force the subpath import).**
- Migration files: `db/migrations/0001_users.ts` … `0005_project_invites.ts`, in dependency order (users → sessions → projects → project_members → project_invites), each exporting `up(db: Kysely<any>)`/`down(db: Kysely<any>)` per Kysely's `Migration` interface. Built entirely with Kysely's schema builder (`addColumn`/`addCheckConstraint`/`addForeignKeyConstraint`/`addPrimaryKeyConstraint`/`createIndex().where(...)`), not raw SQL strings, except for `sql` tag usage for defaults (`gen_random_uuid()`, `now()`, `'{}'::jsonb`) and the `inet` column type (not in Kysely's built-in `ColumnDataType` union, so it's `sql\`inet\`` as the data-type expression).
- **Windows gotcha that would silently break this job in Windows dev environments (this box included):** `FileMigrationProvider`'s default behavior calls `import(filePath)` with a raw filesystem path. On Windows, `D:\...\0001_users.ts` gets parsed by Node's dynamic `import()` as if `"D:"` were a URL scheme, throwing `ERR_UNSUPPORTED_ESM_URL_SCHEME`. Fixed by passing a custom `import` prop to `FileMigrationProvider` that wraps the path in `pathToFileURL(...).href` first — see `apps/api/src/db/migrate.ts`. If you ever refactor the migrator, keep this; it's the difference between working and completely broken on Windows.
- Runner: `apps/api/src/db/migrate.ts` exports `migrateToLatest()` and doubles as a CLI entrypoint (guarded by `process.argv[1] === fileURLToPath(import.meta.url)`, not top-level side effects, so it's safely importable — `reset.ts` imports `migrateToLatest` directly). Migration folder path is resolved relative to the compiled/run file's own location (`../../../../db/migrations` from `apps/api/src/db/`), so it works the same whether invoked via `tsx` (dev) from any cwd.
- **How to run:** `pnpm db:migrate` (root) → `pnpm --filter @scm/api db:migrate` → `tsx src/db/migrate.ts`. Also `pnpm db:reset` (drops+recreates the `public` schema, then re-runs `migrateToLatest` — see `apps/api/src/db/reset.ts`; useful for local dev when migrations change during development, not meant for anything with real data). Both read `DATABASE_URL` the same way `db.ts` does (see below), so `DATABASE_URL=postgresql://... pnpm db:migrate` overrides the default for one-off runs (this is how verification below was actually done, against a non-default port).
- Migrations only run once each (Kysely tracks applied migrations in a `kysely_migration` bookkeeping table it creates itself) — re-running `db:migrate` against an already-migrated database is a confirmed no-op ("already up to date, nothing to do"), satisfying the idempotency acceptance criterion.

**Kysely `Database` type — `db/schema.ts`, import via `import type { Database } from "@scm/db"`** (also re-exported from `apps/api/src/db.ts` for convenience: `import type { Database } from "../db.js"`). Exports the `Database` interface (`{ users, sessions, projects, project_members, project_invites }`) plus per-table `Selectable`/`Insertable`/`Updateable` convenience types (`User`/`NewUser`/`UserUpdate`, `Session`/`NewSession`/`SessionUpdate`, `Project`/…, `ProjectMember`/…, `ProjectInvite`/…) and the narrow union types `ProjectVisibility`, `ProjectMemberRole`, `ProjectInviteRole` matching each `check` constraint's allowed values — **Job 005/006 should use these unions instead of raw strings** when constructing insert/update objects, so a typo in a role/visibility value is a compile error, not a runtime constraint violation. `UsersTable.id`/`SessionsTable.id`/etc. are `Generated<string>` (server-side `gen_random_uuid()` default) — don't pass `id` on insert. `SessionsTable.token_hash`/`ProjectInvitesTable.token_hash` are typed `Buffer` (matches what `postgres.js` returns/accepts for `bytea`) — Job 005 computing a SHA-256 hash of the session cookie should produce a `Buffer` (e.g. `crypto.createHash("sha256").update(token).digest()`), not a hex string, to insert directly.

**Connection — `apps/api/src/db.ts`.** Exports `db: Kysely<Database>` (the shared connection — import this one instance, don't construct a second `Kysely`/`postgres()` client anywhere else) and `closeDb(): Promise<void>` (call at the end of any short-lived script or test suite that imports `db`, or the process hangs on the open pool). Uses `kysely-postgres-js`'s `PostgresJSDialect` wrapping a `postgres()` client (per PLAN.md's "`postgres.js` + Kysely" choice — note this is *not* Kysely's built-in `PostgresDialect`, which is `pg`-based; the community `kysely-postgres-js` package is what bridges Kysely to the `postgres.js` driver). `DATABASE_URL` resolution order: real `process.env.DATABASE_URL` (sourced from the shell, CI, prod platform, etc.) wins if set; otherwise `dotenv` loads `infra/.env` (silently no-ops if that file doesn't exist yet); otherwise falls back to the same hardcoded default as `infra/.env.example` (`postgresql://scm:scm@localhost:5432/scm`), so `pnpm dev`/tests work against a freshly-`docker compose up -d`'d Postgres with zero config. `postgresClient` is constructed with `onnotice: () => {}` — `postgres.js` logs every Postgres server `NOTICE` to the console by default, which is pure noise for `db:reset`'s `drop schema public cascade` (which emits a 5-line "drop cascades to table X" notice on every run).

**What Jobs 005/006 need to know, concretely:**
- `import { db } from "../db.js"` (or wherever `apps/api/src/db.ts` sits relative to your new file — remember `apps/api` is `NodeNext`, so relative imports need the explicit `.js` extension even though the source file is `.ts`).
- `users.discord_id` is `unique not null` — Job 005's login flow should `select ... where discord_id = $1` first and only `insert` on miss (or use an upsert), not blind-insert.
- `sessions.token_hash` and `project_invites.token_hash` are both `unique not null bytea` — collisions on insert will throw a Postgres unique-violation error (Kysely surfaces this as a normal thrown error from `.execute()`); Job 005 should catch/handle that rather than assume hashes never collide.
- `projects.owner_id` has **no** `on delete cascade` (verified directly, see below) — deleting a `users` row that still owns a project fails with a foreign-key-violation error instead of silently orphaning/cascading. If Job 006 ever needs to support "delete my account," it'll need to explicitly reassign or delete owned projects first; this is a deliberate PLAN.md choice, not an oversight.
- `project_members`/`project_invites`/`sessions` **do** cascade off their respective parent (`users` for sessions, `projects` for members/invites; `project_members.user_id` and `project_members.invited_by` are two separate FKs to `users` — only `user_id` cascades, `invited_by` does not, matching PLAN.md exactly).
- `projects.doc_settings` is typed `Generated<unknown>` in `Database` (it's an arbitrary `jsonb` blob per PLAN.md — "solver mode, multipliers, grid, formats" — with no fixed shape defined yet). Job 006 (or wherever `doc_settings` first gets a real shape) should probably narrow this with a `zod` schema and a more specific type rather than reading it as `unknown` forever; not done here since this job's scope is the relational tables only, not the settings shape.
- The partial index `projects_owner_id_index` only covers `owner_id` `where deleted_at is null` — a query listing a user's projects should filter on `deleted_at is null` to actually hit this index (Job 006's project-list query).
